# 项目经验库（L1 · smart-router）

> 收尾时从本项目复盘与操作记录中提炼，只收「可复用 + 非显而易见 + 可核实」的条目。
> 来源标记：CH 编号 / FB 编号，便于回溯现场。

---

## 前端

### FE-01 按钮位置与尺寸的一致性靠「规范 + 单一基准页」维持

- **现象**：同类按钮在不同页面各在一处（标题下方 / 右上角 / 左下角），且尺寸参差。
- **根因**：`BaseButton` 有默认尺寸（32px/13px）与 `size="sm"`（28px/12px）两档，只要有一处漏写 `size`，就会比旁边大一圈；位置则完全靠各页面自由发挥。
- **做法**：确立「聚合模型页」为基准（`BaseSection` 的 `#actions` 插槽 = 标题行最右），把规范写进架构设计（6.7），并要求新页面照抄。
- **可复用结论**：组件库必须同时约束「位置」与「尺寸」两件事，只封组件不写规范，最终仍会漂移。

### FE-02 拖拽排序：只给手柄可拖，别包裹整卡

- **现象**：卡片内有开关、按钮、下拉，整卡可拖会与点击冲突，误触率极高。
- **做法**：`sortablejs` 的 `handle: '.drag-handle'`，手柄单独放在标题行最左，`cursor: grab`。项目内已有两处成熟范例（`MemberEditor.vue` 纯前端排序、`useUpstreamModels.ts` 落库排序）。
- **可复用结论**：拖拽交互的第一决策不是「用什么库」，而是「热区划在哪」；热区与操作区必须物理分离。

### FE-03 展开/收起抖动 = 两种状态的高度计算方式不同

- **现象**：侧边栏收起再展开，整条导航上下跳动。
- **根因**：展开态高度 = `padding + 行高`（文字撑高），收起态 = `padding + 图标高`，两者不等；纯文字节点收起时直接 `v-show` 消失，行高归零。
- **做法**：`.nav-item` 改 `height: 36px` + `box-sizing: border-box`，文字标签固定 `line-height`；收起态只改 `justify-content` 与 `padding`，不改 `height`。
- **验证方式**：连续收起/展开 5 次，比较每个导航项的 `getBoundingClientRect().top` 差值（应为 0）。
- **可复用结论**：任何「同一元素两种形态」的布局，必须用固定尺寸而非内容撑开，否则必然抖动。

### FE-04 别用「实时拉远端」的接口喂表单下拉

- **现象**：路由规则的「模型」下拉在演示环境退化成手动输入框。
- **根因**：用了 `GET /admin/api/upstreams/{id}/models`——该接口会实时请求上游 `/v1/models`，上游不可达就返回空数组，前端 `v-if` 判空后退化成 input。
- **做法**：表单候选改用读库接口（`/admin/api/model-groups/source-models`，读 `up_upstream.models`）。
- **可复用结论**：**「拉取远端」与「读取已配置」是两个语义完全不同的接口**，前者用于「同步远端模型清单」这类主动动作，后者才能喂表单。

## 后端

### BE-01 基线建表脚本 + 增量脚本 = 必须有一个统一的执行入口

- **现象**：全新环境跑完 `seed.py` 服务直接崩溃（`no such table: up_upstream_key`）。
- **根因**：`01_建表.sql` 是**早期基线**，后续 4 个列 + 1 张表都靠增量脚本补；而 `seed.py` 只跑基线和种子，不跑增量；`startup()` 又只自动补 06/07/08。中间 01~05 成了「谁都以为别人会跑」的空档。
- **做法**：`seed.py` 里维护一个显式的 `SQL_FILES` 有序清单，一次执行全部 11 个脚本；`drop_all()` 同步补全到 13 张表以保证重跑幂等。
- **可复用结论**：**只要存在「基线 + 增量」双轨，就必须有一个地方完整列出执行顺序**。分散在多处自动执行 = 迟早漏。

### BE-02 启动加载链上的 try 边界要覆盖整条链

- **现象**：`AppConfig.load()` 里 10 个 repository 调用包在 `try/except OperationalError` 内，唯独漏了紧随其后的 `_load_upstream_keys()`，于是「表不存在」的容错在最后一步失效。
- **可复用结论**：写容错时按「调用链」而不是「代码块」划边界——把整段初始化逻辑都放进去，或者干脆让每个 repo 自己容错。

### BE-03 顺序类配置存 `sys_setting` 而不是加表字段

- **背景**：聚合列表要支持人工拖拽排序，但「自动发现」的聚合在 `agg_unified` 里根本没有行。
- **做法**：顺序存 `sys_setting.aggregation_order`（JSON 名字数组），读取时按数组排序、未列入的排末尾、已删除的名字自动忽略。
- **可复用结论**：**当需要排序的对象集合 ≠ 表里实际存在的行集合时，排序不能靠表字段**，应独立存一份「名字 → 序号」映射。

### BE-04 流式转发要分成两个超时阶段

- **现象**：非流式有 `asyncio.wait_for` 保护，流式只保护了「等首包」，没保护「等响应头」，最坏要等 `httpx` 全局超时（300s）。
- **做法**：`response_timeout`（等响应头）+ `first_chunk_timeout`（等首包）两段独立；`response_timeout=None` 时不包 `wait_for`，保持旧行为。
- **可复用结论**：流式请求的耗时天然分成「连上 → 给头 → 给首字节 → 持续吐字」四段，**每段的合理超时量级不同，不能用一个大超时兜全部**。

### BE-05 签名密钥的三级取值：环境变量 > 数据库 > 首次生成并落库

- **背景**：密钥硬编码在源码里（公开即失效）；但若每次启动随机生成，重启就会把所有用户踢下线，体验极差。
- **做法**：`SR_JWT_SECRET` 环境变量（多实例/容器化运维统一）> `sys_setting.jwt_secret`（单机零配置）> 首次启动 `secrets.token_urlsafe(48)` 生成并写库（重启不变）。进程内缓存 + `threading.Lock` 防并发首次调用各生成一份。数据库不可用时降级为进程内随机密钥并 WARNING，**服务不能因此起不来**。
- **可复用结论**：**「不硬编码」和「重启不踢人」是两个约束，必须同时满足**——只做前者（每次随机）会让用户体验崩坏，只做后者（固定默认值）等于没改。三级取值是同时满足两者的最小方案。

## 架构

### AR-01 v4 → v5 重构后，旧目录必须清理并加护栏

- **现象**：根目录长期留着 v4 的 `router.py` / `core/` / `upstream/` / `admin/` / `.streamlit/`，且 `start.bat` 指向的是 v4 入口。
- **风险**：新人（或另一个 AI）会误以为那是现行代码；运维点 `start.bat` 会启动一个无鉴权、无 SQLite 的旧服务。
- **做法**：删前实测 `backend/app/**` 与 `test/` 对旧模块的 import 数为 0；删除 git 跟踪文件（可 `git revert` 恢复）；`start.bat` 改指 `backend/run.py`。**保留未跟踪的本地 `config.yaml`**（可能是唯一真实配置备份）。
- **可复用结论**：重构收尾必须包含「旧实现物理删除 + 启动入口改指 + 依赖清零验证」三件事，缺一件就会留下误用入口。

### AR-02 文档声称的开关，代码里必须有调用点

- **现象**：`auto_same_name_enabled()` 有定义、有注释、有 CH-019 的文档承诺，但全仓 0 调用点，设置页也没有开关。
- **做法**：在需求规格新增「待完善事项」一节，写清现状 / 实际行为 / 原承诺 / 影响 / 后续做法，避免以后误当已实现。
- **可复用结论**：审计时不能只看「有没有这个函数」，要 grep **调用点**；文档写「已支持」不等于代码已生效。

## 流程

### PR-01 「文档 vs 代码」全仓审计应该在每次收尾前跑一遍

- **收获**：CH-029 的审计一次揪出 1 个 P0 部署阻断（全新环境起不来）+ 8 处文档漂移（版本号 4 处不一致、SQL 清单漏 2 个、API 契约写反、`start.bat` 指错入口）。
- **可复用结论**：**功能测试全绿 ≠ 可以部署**。功能回归只覆盖「已跑起来的环境」，覆盖不到「从零建库」和「文档与实现是否同源」。

### PR-02 文件「看似被删除」时先查 Git 索引，别急着恢复

- **现象**：`git status` 显示几十个文件 M，但逐个比对 worktree 与 HEAD 的 blob hash 完全一致。
- **做法**：`git hash-object <file>` vs `git rev-parse HEAD:<file>` 逐项比对；确认为索引 stat 陈旧后，`git add -u` 刷新即可，不要 `checkout` 覆盖。
- **可复用结论**：**`git status` 的 M 不代表内容变了**（可能是 mtime/大小缓存过期，CRLF 配置下尤其常见）；判断内容是否变化要用 hash，不要用 status。

### PR-03 部署脚本会随目录改名、服务器迁移而整体失效

- **现象**：`test/deploy_*.py` 全部硬编码 `E:\...\04_smart-router(starting)\...` 与旧 IP（`10.10.0.2` / `8.137.195.192`）。
- **可复用结论**：部署脚本不要硬编码本机绝对路径与服务地址，应从环境变量或配置文件读；否则每次换机就全废，还会误导为「可复用资产」。

### PR-04 历史隐私清洗必须在首次推送之前完成

- **现象**：`test/verify_prod_ch016.py` 在 CH-016 提交里硬编码了管理员密码与客户端 Key，虽然 CH-018 已改为读环境变量，但 `git log -p` 仍能翻出真值；`.git/config` 的 remote URL 还内嵌了明文账号密码。
- **做法**：`uv tool install git-filter-repo`（venv 无 pip 时比 `filter-branch` 更安全快），替换规则文件放 `.git/` 下（不受跟踪，自身不会泄露），执行 `git filter-repo --replace-text`，用后立即删除规则文件。
- **验证方法**：①对每个真实敏感值跑 `git grep --fixed-strings <值> $(git rev-list --all)`，必须 0 命中；②比对清洗前后 `HEAD^{tree}` 是否一致（一致 = 内容零变化，只有 hash 变了）；③确认提交数与 tag 未丢。
- **可复用结论**：**密钥只要进过一次 commit，改代码没用，必须重写历史**。而重写历史只有「首次推送前」这个窗口成本最低——一旦推到远端，平台缓存 / 他人克隆 / fork 都让清理不可能彻底。推送前跑一遍「全历史敏感值扫描」应当成为固定门禁。

### PR-05 破坏性 git 操作必须有「工作区外的」灾备

- **做法**：历史重写前做双备份——工作区文件副本（排除 node_modules/.venv/dist/*.db）+ `git bundle create <项目目录外路径> --all`。
- **关键点**：备份必须放在**项目目录之外**，否则会被 `git add` 或推送带出去（bundle 里含清洗前的泄露内容，外传等于白洗）。
- **可复用结论**：备份放哪比备份做不做更重要。

### PR-06 提交元数据也是隐私面，别只扫文件内容

- **现象**：文件内容已清洗干净，但 `git log --format="%ae"` 显示作者邮箱是「手机号@qq.com」，推 GitHub 后每条提交都公开显示。
- **做法**：写一份 mailmap（`新名 <新邮箱> 旧名 <旧邮箱>`）放 `.git/` 下，`git filter-repo --mailmap .git/mailmap.txt`；再改仓库级 `git config user.email`，防止后续提交又用回旧邮箱。
- **补充坑**：写「脱敏记录」的文档时，很容易为了说明「我把 X 脱敏了」而把真实 X 抄一遍，等于二次泄露。**脱敏记录只写位置和类型，不写原值**。
- **可复用结论**：隐私审计要分三层扫——①工作区文件内容 ②历史每个版本的文件内容 ③提交元数据（author/committer/tag message）。
