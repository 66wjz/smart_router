## 一、设计原则

| 维度 | 设计选择 | 理由 |
|------|---------|------|
| 配置状态源 | SQLite 数据库（内存缓存 + 热重载） | 结构化存储、并发安全，启动全量加载到内存保证路由性能 |
| 路由决策归属 | 后端引擎计算（core/router_engine） | 决策逻辑纯 Python 可单测，动态权重结合实时延迟 |
| 鉴权模型 | 两层 Key（客户端白名单 + 上游自有密钥） | 客户端密钥不透传上游，隔离安全 |
| 故障兜底 | 引擎内自动（候选重试 + 冷却 + 降级） | 无需外部编排，请求链路自愈 |
| 延迟感知 | 后台定时探测（asyncio 循环） | 实时延迟驱动动态权重，慢模型自动排除 |

## 二、核心流程图

### 流程 1：客户端智能路由（核心链路）

```mermaid
sequenceDiagram
    participant C as 客户端
    participant L as 请求上下文中间件
    participant R as 路由代理(/v1/chat/completions)
    participant S as RouterService
    participant E as 路由引擎
    participant U as 上游API

    C->>L: POST /v1/chat/completions (带 Key)
    L->>L: 缓存请求体，解析 model/stream/messages
    L->>R: 交还请求体
    R->>R: API Key 白名单校验 + 注入分组
    alt Key 无效
        R-->>C: 401 (OpenAI 错误格式)
    else Key 有效
        R->>R: 请求体校验（CH-025）
        alt body 非法 / 非对象 / 缺 model / messages 非数组
            R-->>C: 400 (各协议规范错误格式)
        else 校验通过
            R->>S: route_request(model, body, groups)
            alt 模型别名
                S->>S: 查找指针，替换目标模型
            else 聚合模型名（显式配置的 static / rule）
                S->>S: 聚合级分组校验（CH-034，只看聚合 groups；成员分组不参与）
                S->>E: 规则匹配 + 候选排序 + 加权选择
                E-->>S: 选中模型 + upstream + 调整后的 max_tokens
            else 具体模型名
                S->>S: 查找模型所属上游，成员级分组校验后直接透传
            end
            S->>S: 出站前规范化消息角色（CH-037：developer → system）
            S->>U: 用 upstream 自己的 Key 转发
            alt 成功
                U-->>S: 结果
                S-->>R: 成功响应
            else 失败
                S->>U: 换下一个候选模型重试
                alt 全部失败
                    S-->>R: 503 无可用模型
                end
            end
            R-->>C: 返回结果
        end
    end
    Note over L,C: 任何未捕获异常 → 全局 handler 按协议返回规范错误体
    L->>L: 写 access 日志（状态/耗时/模型/请求体摘要，落文件）
```

### 流程 2：延迟探测与动态权重

```mermaid
sequenceDiagram
    participant T as 探测循环(asyncio)
    participant P as LatencyProbe
    participant C as AppConfig
    participant U as 各上游API
    participant E as 路由引擎

    T->>C: collect_probe_plan()
    C->>C: 规则候选 ∪ 别名目标 ∪ static 成员 ∪ 各 rule 聚合按绑定裁剪后的候选并集
    C->>C: 按 (upstream, 真实模型) 去重<br/>多聚合引用取最小间隔
    C->>C: 生效节奏 = 模板 → 自配 → 全局
    C-->>T: {unit: interval, groups, group_kinds, schedules}
    loop 每 1s tick
        T->>C: probe_plan_active(unit)?
        alt 时段外（多引用方取并集）
            T->>T: 跳过，保留旧数据（标记时段外）
        else 已到期
            T->>U: 并发探测（信号量限流）
            U-->>T: 延迟/状态
            T->>T: 写回内存 data + last_check
        end
    end
    P-->>E: get_dynamic_weight / sort_group_candidates
    E->>E: rule 聚合：priority + 动态权重 = base × (base_latency/latency)²
    E->>E: static 聚合：T0正常 → T1偏慢/未知 → T2 down/冷却<br/>全不可用回退配置顺序
```

> CH-021：探测单元由全局去重计划决定（聚合只引用不拥有）；调度改为按单元到期；支持独立间隔与探测时段；探测失败默认不计入 Key 冷却。
> CH-023：聚合统一为 `agg_unified`（`kind` = static / rule）；探测节奏可按**模板**定义（模板值优先，不可被聚合覆盖）；rule 聚合的探测对象是**全部规则候选的并集**；单元上记录 `groups` / `group_kinds` / `schedules`，排班表据此渲染。
> CH-024：rule 聚合的探测对象改为**该聚合按 `rule_bindings` 裁剪后的候选并集**（无绑定 = 全部规则并集），故不同 rule 聚合的单元数与探测成本可区分；保存规则后自动清理失效绑定（`prune_rule_bindings`）。
> **排序语义未变**：rule 聚合仍走 `get_ordered_candidates`（priority + 动态权重），静态聚合走 `sort_group_candidates`（stable/latency 分层），两者互不影响。

### 流程 3：故障转移（冷却）

```mermaid
sequenceDiagram
    participant U as 上游API
    participant H as ModelHealth
    participant E as 路由引擎

    loop 每次请求
        U-->>H: 模型失败(HTTP错误/超时)
        H->>H: record_fail: 失败计数+1
        alt 连续失败 ≥ max_fails
            H->>H: 进入冷却期 (cooldown_seconds)
            Note over H: 冷却期内 is_available=false
            E->>E: 该模型不被选中
        else 未达阈值
            E->>E: 该模型仍可被选中
        end
        U-->>H: 模型成功
        H->>H: record_success: 清零失败计数
    end
```

### 流程 5：流式转发的两段超时（CH-027）

流式请求（`/v1/chat/completions`、`/v1/messages`、`/v1/responses`）在 `try_stream*` 内部按**两个独立阶段**计时，任一阶段超时都视为该 Key 失败，换下一个 Key 重试。

```mermaid
sequenceDiagram
    participant S as RouterService
    participant A as 流式适配器
    participant K as Key 池
    participant U as 上游API

    S->>A: try_stream(..., first_chunk_timeout, response_timeout)
    loop 每个候选 Key（预算 = Key 数 + 智能重试额外次数）
        A->>K: pick(upstream)
        K-->>A: api_key
        A->>U: POST (stream=true)
        Note over A,U: 阶段一：等响应头<br/>asyncio.wait_for(response_timeout)
        alt 响应头超时 / 连接异常
            A->>K: record_fail
            A->>A: 换下一个 Key
        else 响应头返回 HTTP 401/403/429/可重试5xx
            A->>K: record_fail
            A->>A: 换下一个 Key
        else 响应头 200
            Note over A,U: 阶段二：等首包内容<br/>asyncio.wait_for(first_chunk_timeout)
            alt 首包超时 / 空响应
                A->>K: record_fail
                A->>A: 换下一个 Key
            else 首包到达
                A-->>S: StreamingResponse（开始持续转发）
            end
        end
    end
    A-->>S: 全部失败 → None（由上层返回 503）
```

> **两个超时的分工**：`response_timeout`（`retry.response_timeout`，默认 20s）只管「上游多久给出响应头」；`first_chunk_timeout`（`retry.first_chunk_timeout`，默认 8s）只管「响应头已返回后多久出第一个数据块」。模型思考很久属于第二阶段，不受 `response_timeout` 影响。
> **兼容旧行为**：`response_timeout` 传 `None` 时不包 `wait_for`，仍由 `httpx` 全局超时兜底。
> **与非流式对齐**：`try_non_stream` 一直有该保护，本次补齐流式三适配器（`openai_adapter` / `anthropic_adapter` / `responses_adapter`）的同类缺口。

## 四、外部依赖与兜底链

### 外部依赖

| 依赖 | 用途 | 不可用影响 | 兜底方案 |
|------|------|-----------|---------|
| 上游模型提供商（NewAPI/小米） | 模型推理 | 该上游的模型全部失败 | 故障转移切换到其他候选模型 |
| 无外部数据库依赖 | SQLite 本地文件 | - | - |
| 无消息队列/调度器 | 探测用 asyncio 循环 | - | - |

### 兜底链

| 场景 | 降级链（从左到右） | 说明 |
|------|-------------------|------|
| 某候选模型失败 | 失败模型 → 同规则下一候选 → 降级候选（P3）→ 503 | get_ordered_candidates 排序后按序重试 |
| 所有候选权重为 0 | 跳过加权选择 → 返回原始候选列表 → 交给上游判定 | 避免直接 503，让真实请求裁决 |
| 全部模型不可用 | 所有候选失败 → 503 "所有模型均不可用" | 返回尝试过的模型列表 |
| 探测超时 | 该模型延迟记为超时 → down 状态 → 动态权重归 0 | 冷却恢复后自动回归 |
