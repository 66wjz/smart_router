## 〇、心智模型对齐（1.0）

### 参考系统对标分析

无直接对标产品，但可参考两类现有系统的设计范式：

| 参考系统 | 借鉴点 | 不借鉴点 |
|---------|--------|---------|
| one-api / new-api（AI 中转站） | 两层 Key 架构（客户端入场券 + 上游通行证）、上游源管理、模型路由 | 过度复杂的计费/分成体系、多租户 |
| OpenAI 官方网关 | 协议兼容层（chat/completions、Anthropic 格式）、统一模型名入口 | 单一供应商绑定 |

**核心差异点**：Smart Router 的定位是"智能路由决策"——根据请求内容（是否含图片/工具）、模型实时延迟、健康状态、上下文长度，动态选择最佳模型，而不是简单转发。

### 系统心智模型描述

Smart Router 是一个"AI 模型智能路由网关"：客户端只需要知道一个统一的模型名（如 smart-latest），网关会根据请求内容、各模型的实时延迟和健康状态，自动选择最合适的底层模型完成推理，并在模型失败时自动切换备选模型。管理员通过 Web 管理后台配置上游模型提供商、路由规则、访问密钥等。系统的"大脑"是路由决策引擎，"数据"是配置（上游源、规则、密钥），"操作台"是管理后台。

### 核心实体清单（7 个）

1. **API Key（客户端密钥）**：客户端访问网关的"入场券"，有白名单校验和分组权限（如 free/premium），不同分组能访问不同上游源
2. **Upstream（上游源）**：一个模型提供商接入点，含地址、密钥、协议格式（OpenAI/Anthropic）、所属分组
3. **Rule（路由规则）**：一组匹配条件（含图片 / 含工具调用 / 默认）+ 候选模型列表，决定请求往哪个方向路由
4. **Candidate（候选模型）**：路由规则中的单个模型项，含权重、优先级、上下文限制等参数
5. **Model Pointer（模型别名）**：一个"指针"，客户端请求别名时直接转发到指定模型，不走路由规则，可在后台随时切换指向
6. **Aggregated Name（聚合模型名）**：客户端使用的统一模型名（如 smart-latest），触发智能路由
7. **系统配置**：延迟探测参数、重试参数、故障转移参数、管理后台账号等

### 实体关系

一个 Upstream 可被多条 Rule 引用；一条 Rule 包含多个 Candidate；一个 Model Pointer 指向一个 Upstream 下的一个模型；多个 Aggregated Name 是智能路由的统一入口；API Key 通过分组关联到可访问的 Upstream。

## 一、项目概述

Smart Router v5 是 v4 的重构升级版。v4 已实现完整的智能路由能力（多上游源、动态权重、延迟探测、故障转移、Anthropic 格式兼容、Streamlit 管理后台），但存在三个问题：

1. **管理后台技术栈落后**：Streamlit 页面受框架限制，交互体验和扩展性差
2. **配置存储弱**：YAML 文件存储，并发修改易冲突，无版本管理
3. **代码结构混乱**：路由处理逻辑与业务逻辑耦合在单一文件，缺少分层

v5 重构目标：
- 前端从 Streamlit 迁移到 Vue3 + Element Plus，提供现代管理后台体验
- 配置从 YAML 迁移到 SQLite 数据库，支持结构化存储
- 后端按 Router → Service → Schema 分层重组，代码结构清晰可维护
- 补齐缺失流程文档，实现文档与代码对齐

目标用户：使用 OpenAI/Anthropic 兼容接口的开发者（客户端）、系统运维管理员（管理后台）。

## 三、客户端用户需求（API 服务）

**核心目标：** 提供稳定、智能、兼容的 AI 模型调用入口，客户端无需感知底层模型切换。

### 1. 智能路由

#### 功能点 1.1: 统一模型名智能路由
- **用户故事**：作为客户端用户，我想要用一个固定模型名调用接口，以便由网关自动选择最佳底层模型
- **详细描述**：
  - 支持聚合模型名（smart-latest / smart-chat / auto-chat）作为入口
  - 网关根据请求内容（含图片 → 视觉规则、含工具 → 工具规则、否则 → 默认规则）匹配路由规则
  - 每个规则内按优先级和动态权重（结合实时延迟）加权随机选择模型
- **关键交互**：POST 请求携带统一模型名 → 网关返回推理结果
- **状态**：已明确

#### 功能点 1.2: 上下文感知路由
- **用户故事**：作为客户端用户，我想要网关自动估算请求 token 数，以便长上下文请求不会被路由到上下文不足的模型
- **详细描述**：
  - 自动估算请求 token 数（文本约 2 字符/token，图片约 768 tokens/张）
  - 请求超模型上下文限制时自动排除该模型
  - max_tokens 超过模型输出上限时自动调低
- **状态**：已明确

#### 功能点 1.3: 故障转移与自动重试
- **用户故事**：作为客户端用户，我想要模型失败时网关自动换备选模型重试，以便请求尽量成功返回
- **详细描述**：
  - 模型连续失败达到阈值进入冷却期，冷却期内不被选中
  - 请求失败自动换下一个候选模型，最多重试可配置次数
  - 流式请求首包超时自动切换，避免长时间等待卡死的模型
- **状态**：已明确

### 2. 模型别名（指针）

#### 功能点 2.1: 别名固定转发
- **用户故事**：作为客户端用户，我想要用一个固定别名（如 my-model）调用接口，以便管理员切换底层模型时客户端无需改配置
- **详细描述**：
  - 请求别名时直接转发到别名指向的真实模型，不走路由规则
  - 管理员在后台可随时切换别名指向
- **状态**：已明确

### 3. 直接透传

#### 功能点 3.1: 指定模型直连
- **用户故事**：作为客户端用户，我想要直接指定具体模型名调用，以便不经过路由直接使用某个模型
- **详细描述**：
  - 请求具体模型名时，网关查找该模型所属上游源并直接转发
  - 不路由、不重试
- **状态**：已明确

### 4. 协议兼容

#### 功能点 4.1: 多协议格式支持（2026-08-10 修订为协议矩阵）
- **用户故事**：作为客户端用户，我想要用我熟悉的协议格式接入，以便使用对应 SDK 调用
- **详细描述**（协议矩阵，内部以 OpenAI chat 格式为中间语言）：
  - **入站**（客户端 → 网关）：OpenAI chat/completions ✅；Anthropic Messages ✅（CH-009，/v1/messages，兼容 x-api-key 鉴权）；Responses ✅（CH-010，/v1/responses，Codex 可用）
  - **出站**（网关 → 上游）：openai / anthropic / responses 三协议齐备（CH-011 模型级协议覆盖 + CH-014 responses 出站），每个上游模型可单独指定协议
  - 支持流式（SSE）与非流式
- **状态**：3×3 协议矩阵全部上线（2026-08-11）

### 5. 鉴权

#### 功能点 5.1: 两层 Key 鉴权
- **用户故事**：作为客户端用户，我想要用自己的密钥访问网关，以便按密钥控制访问范围
- **详细描述**：
  - 客户端请求必须携带白名单内的有效密钥，否则 401
  - 密钥有分组权限（free/premium），只能访问对应分组的上游源
  - 路由后网关使用上游源自己的密钥访问模型提供商，客户端密钥不透传
- **状态**：已明确

#### 功能点 5.2: 入站请求体校验与错误规范化（CH-025）
- **用户故事**：作为客户端使用者，当我的请求有问题时，我想要收到能看懂的错误，而不是莫名其妙的连接中断
- **详细描述**：
  - 三个入站（`/v1/chat/completions`、`/v1/messages`、`/v1/responses`）统一校验请求体
  - 请求体不是合法 JSON → 400；不是 JSON 对象（数组/null/字符串）→ 400
  - `model` 缺失 → 400；`messages` 缺失或非数组（仅 chat）→ 400
  - 未捕获异常按入站协议返回规范化错误体，不再返回 FastAPI 默认纯文本 500
  - 容错工具函数（`estimate_tokens`/`extract_text`/`has_image`）对非 list 的 `messages` 返回默认值，避免 `for None` 崩溃
- **状态**：已明确（CH-025 实现）

## 四、管理员需求（Web 管理后台）

**核心目标：** 通过现代 Web 界面可视化配置和管理整个路由系统。

### 1. 登录与安全

#### 功能点 1.1: 后台登录认证
- **用户故事**：作为管理员，我想要登录后才能进入管理后台，以便保护系统配置不被未授权访问
- **详细描述**：
  - 用户名密码登录，返回 JWT token
  - token 有效期可配置（默认 24 小时）
  - 登录失败（账号或密码错）应提示「用户名或密码错误」，**不得**提示「未登录或登录已过期」（CH-049）
- **状态**：已明确

#### 功能点 1.2: 修改后台密码
- **用户故事**：作为管理员，我想要修改后台登录密码，以便保证账号安全
- **详细描述**：
  - 需验证当前密码，新密码至少 6 位
  - 修改后立即生效
  - **改密后所有已签发的旧 token 立即失效**，客户端需重新登录（CH-049：JWT 内携带密码指纹 `pv`，服务端每次校验比对）
- **状态**：已明确

- **详细描述**：

### 8. 聚合模型管理（CH-023 统一）

#### 功能点 8.1: 两类聚合统一管理
- **用户故事**：作为管理员，我想要在同一个页面管理"固定成员聚合"和"规则聚合"，并能分别看到它们的候选与探测情况，而不是两套割裂的机制
- **详细描述**：
  - 统一实体 `agg_unified`，`kind` 区分两类：
    - `static`（固定成员）：自己勾选上游源与各源真实模型名（支持异名），顺序即优先级
    - `rule`（规则聚合）：候选由「路由规则」页在运行时按请求内容匹配；不可配置成员
  - **rule 聚合的规则绑定（CH-024）**：一张规则表 + 每个聚合引用其子集
    - 可只启用部分规则（不启用的规则对本聚合不生效）
    - 每条规则可选「全部候选跟随」或「显式勾选部分候选」
    - 不配置绑定 = 全跟随（使用所有规则、每条规则的全部候选，兼容旧数据）
    - 规则页删除/改名规则 → 自动清理引用它的聚合绑定；清理后为空则回退全跟随
    - 规则页移除候选 → 聚合绑定里的该项变为失效，卡片显示黄标提示（运行时静默跳过）
    - 每个 rule 聚合的探测对象 = 其绑定裁剪后的候选并集，探测成本可区分
  - 两类都可：单独启用/关闭、配置探测、配置排序模式、挂探测模板
  - **会话亲和（CH-052）**：每个聚合可单独设置 `affinity`（跟随全局 / 开启 / 关闭，默认跟随全局=开启）；开启后同一会话固定同一成员与 Key，关闭后按权重轮询
  - 列表徽标区分：固定成员 / 规则匹配、手动配置 / 自动发现、模板名、稳定优先 / 速度优先、探测开·间隔·限时段、规则绑定摘要（N 条规则 · M 个候选）、亲和开/关（显式设置时）
  - 自动发现的同名聚合（跨 ≥2 源、未人工配置）仍展示，标记「自动发现」
- **状态**：已明确（CH-023 统一 + CH-024 绑定，本地验证通过）

#### 功能点 8.1.1: 新建聚合时选择类型
- **用户故事**：作为管理员，我想要在新增聚合时先选"固定成员"还是"规则匹配"，选规则匹配后直接从现有规则里勾选要用的规则与候选
- **详细描述**：

#### 功能点 9.7: 请求过滤引擎（CH-041）
- **用户故事**：作为管理员，上游渠道对「非官方 agent 客户端」有黑名单（按 system 首行精确匹配），别人反复用 DSH 之类客户端打同一个源，会让号池里的号被上游封禁；我想要在中转站里配置过滤规则，命中就**不发出去**，并在回执里明确告知，以便保护号池、且不依赖客户端配合
- **详细描述**：
  - **匹配对象**：`system_first_line`（首条 system 消息文本）/ `system_any`（全部 system/developer 文本）/ `body_regex`（整个请求体序列化后正则）。文本类用「包含」判定（宁可多拦，漏拦要付一次上游调用代价）
  - **动作**：`skip`（静默跳过该候选，换下一个）/ `reject`（直接拒绝请求，返回 400）
  - **作用域**：规则可绑定一个/多个上游源；留空 = 全部源。**注意**：预置规则把作用源限定为 `buddy` / `workbuddy`，不可留空——实测只有这两个渠道会拦，其他渠道（`trae`/`loomy`/`lobsterai`）是放行的；不限源会把放行渠道一起拦掉，聚合候选被清空后客户端拿到 503，而非设计的「无感换成员」
  - **路由语义（用户 2026-10-21 拍板方案 A）**：
    - 聚合类（rule 聚合 `aggregated` + static 聚合门面 `static_agg`）→ **无感切换**：命中 `skip` 的成员被移除，继续路由剩余候选，客户端完全无感知
    - 聚合类但命中 `reject`，或全部候选被拦 → 返回 400/503，不静默成功
    - 直连 / 别名（`direct` / `pointer`）→ 命中即返回 **400**，回执写明命中的规则名与被保护的上游源
  - **执行位置**：候选解析之后、真正转发**之前**（Pre-flight），被拦候选不产生任何上游请求，违规计数为 0
  - **全局开关默认关闭**：`filter_engine_enabled` 默认 `false`，关闭时零开销短路（不抽取文本、不跑正则）
  - **预置规则**（默认不启用，需管理员手动开）：`DSH 身份声明`、`Claude Code 身份声明`，两条的**作用源均预置为 `buddy` + `workbuddy`**
  - **试跑**：可在后台粘贴一段请求体，直接看到「哪些候选会被拦、命中哪条规则」，不影响线上
  - **可观测性**：被拦请求照常写入用量表，`error_msg` 以 `【已过滤】` 前缀标记，用量页可筛选「已过滤」；详情里的尝试链把这些候选记为 `http_status=null`（未发送）
- **位置**：侧边栏「请求过滤」页（规则表格 + 全局开关 + 试跑面板）；用量页新增「已过滤」统计卡片与筛选项
- **状态**：已明确（CH-041 实现，本地验证 43 项通过，已随 v5.2.3 部署生产）

### 9.2 聚合模型独立分组（聚合作为权限门面）—— ✅ 已实现（CH-034）

| 项 | 内容 |
|----|------|
| 用户诉求 | 聚合模型要像普通模型一样能被「加进来」，并拥有自己的分组。**聚合的分组只约束聚合自身，和它内部用到的模型彻底隔离**——即使成员是 `vip` 分组，只要聚合本身属于 `free`，`free` 的 Key 就能用该聚合。本质是让聚合成为「对外门面」，权限只看门面，不看成员 |
| 原现状（问题） | `agg_unified` 表**没有分组字段**，聚合名不具备任何权限属性。只有**成员级**校验：`_check_group()` 逐个检查候选所属上游源的分组，无权限的候选被跳过。后果是聚合无法跨分组编排——`free` 的 Key 请求一个只含 `premium` 成员的聚合，会被全部跳过而返回 403（**不是越权放行，而是能力缺失**）；生产上实际表现为把分源统一放进 `no_single_use` 分组后，聚合一用就 `403 API Key 无权访问分组 ['no_single_use']` |
| 实现的设计（CH-034） | ①**只在聚合上校验**，成员分组完全不参与；②`groups` 为空 = 所有 Key 可用（兼容存量）；③**static 与 rule 一视同仁**，都按聚合自身 `groups` 判断；④上游源禁用 / 模型级禁用 / 候选全部不可用仍按原逻辑（属可用性，不是权限）；⑤只有**显式配置过**的聚合享受门面语义，自动发现的同名聚合不算门面（否则会隐式放宽成员级保护） |
| 影响面 | 数据库：`agg_unified` 加 `groups` 列（增量 SQL 09）。后端：新增 `_check_aggregation_group()`、`is_static_aggregation()`、`get_aggregation_groups()`、`is_aggregation_visible()`；rule 聚合 `allowed_groups` 改为 `None`，static 聚合跳过逐候选 `_check_group`；`/v1/models` 聚合条目按聚合分组过滤；分组删除保护纳入聚合引用。前端：聚合新建/编辑弹窗加「可用分组」多选；卡片显示分组徽标与「所有分组可用」 |
| 风险 | 这会**主动削弱成员级保护**——只要聚合分组配得宽松，`free` Key 就能用到 `premium` 上游的真实额度。属用户明确要求的设计取舍，UI 已提示「聚合分组决定谁能用，成员分组不再生效」；自动发现聚合不享受门面语义，避免误放宽 |
| 状态 | **已实现并本地验证通过（CH-034）**，待部署 |
| 登记时间 | 2026-10-18（2026-10-18 由「暂不实现」转为实现） |

### 9.4.2 会话亲和（缓存优先路由）—— ✅ 已实现（CH-052）

| 项 | 内容 |
|----|------|
| 用户诉求 | 聚合不能每请求换一家：上游 prompt cache 按「提供商 + 账号/Key + 前缀」隔离，同一会话来回切源会导致缓存全量重算、费用升高。要求同一会话固定用同一家，只有那家失败才换，且不依赖客户端改造 |
| 实现（CH-052） | ①会话识别：`hash(模型 + 请求体 user 字段或第一条 user 消息)`，不 hash 全量、不存原文；②新会话按 `score =（近 5 分钟请求数 + 活跃会话数）/ weight` 选最小者并钉住 `(上游, 模型, Key)`；③同会话后续请求钉住目标排首位，忽略权重/负载；④目标不健康或不在候选时重新放置；⑤请求中切换成功则把钉子改到成功那家，**不切回**；⑥`KeyPool` 优先复用钉子 Key，同上游因 Key 冷却换号后钉子跟随实际 Key；⑦短请求（估算 < 2000 tokens）不钉；⑧按聚合可关（`affinity=null` 跟随全局 / `0` 关 / `1` 开，默认开）；⑨`log_usage` 记 `affinity_key / affinity_hit / switch_reason` |
| 边界 | 不依赖客户端、不改号池内部账号机制；跨提供商缓存物理上无法共享；重启后重新钉（内存态，TTL 45 分钟 / LRU 2 万条） |
| 状态 | **已实现 + 本地验证 38 项（CH-052）**，待部署 |
| 登记时间 | 2026-10-28 |

### 9.6 模型标识命名空间（源前缀 + 歧义报错）—— ⏸ 已搁置（CH-035）

| 项 | 内容 |
|----|------|
| 现状 | 模型名是**全局唯一标识**：客户端请求 `deepseek-v4-flash` 时，网关按上游源展示顺序自动挑第一个可用源，客户端无法指定「我要 buddy 的那个」。别名 / 聚合名 / 真实模型名共享同一命名空间，优先级为 别名 → 聚合 → 真实模型 |
| 用户诉求 | 同名模型分布在多个源时，客户端希望能指定走哪个源，而不是被动接受网关的默认选择 |
| 方案（用户 2026-10-19 拍板「方案 B」） | ①**可选前缀** `{上游源ID}/{模型名}`（如 `dsh/deepseek-v4-flash`）强制指定源；②不带前缀时行为完全不变，保证现有调用不破坏；③不带前缀且**跨源存在歧义**时报错，提示改用 `<源>/<模型>` 指定，而不是静默挑一个 |
| 为什么不做「强制前缀」 | 上游返回的模型名本身常含 `/`（`01-ai/yi-large`、`buddy/deepseek-v4.1-flash`），强制加前缀会与这些名字冲突，并破坏所有现有客户端调用 |
| 与 dsh 重名问题的关系 | `dsh`（premium）保留了 3 个与聚合成员同名的模型，带 premium 的 Key 可绕过 `no_single_use` 直连。用户 2026-10-19 实测确认「门面」语义已实际生效、无需清理 dsh，故本项不是必需项 |
| 状态 | **已搁置**——方案已定但未建变更文档、未改代码；当前有更紧急的问题（聚合分组 403）打断了实施，之后一直未重启 |
| 登记时间 | 2026-10-19 |
