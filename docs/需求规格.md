## 〇、心智模型对齐（1.0）

### 参考系统对标分析

无直接对标产品，但可参考两类现有系统的设计范式：

| 参考系统 | 借鉴点 | 不借鉴点 |
|---------|--------|---------|
| one-api / new-api（AI 中转站） | 两层 Key 架构（客户端入场券 + 上游通行证）、上游源管理、模型路由 | 过度复杂的计费/分成体系、多租户 |
| OpenAI 官方网关 | 协议兼容层（chat/completions、Anthropic 格式）、统一模型名入口 | 单一供应商绑定 |

**核心差异点**：Smart Router 的定位是"智能路由决策"——根据请求内容（是否含图片/工具）、模型实时延迟、健康状态、上下文长度，动态选择最佳模型，而不是简单转发。

### 系统心智模型描述

Smart Router 是一个"AI 模型智能路由网关"：客户端只需要知道一个统一的模型名（如 smart-latest），网关会根据请求内容、各模型的实时延迟和健康状态，自动选择最合适的底层模型完成推理，并在模型失败时自动切换备选模型。管理员通过 Web 管理后台配置上游模型提供商、路由规则、访问密钥等。系统的"大脑"是路由决策引擎，"数据"是配置（上游源、规则、密钥），"操作台"是管理后台。

### 核心实体清单（7 个）

1. **API Key（客户端密钥）**：客户端访问网关的"入场券"，有白名单校验和分组权限（如 free/premium），不同分组能访问不同上游源
2. **Upstream（上游源）**：一个模型提供商接入点，含地址、密钥、协议格式（OpenAI/Anthropic）、所属分组
3. **Rule（路由规则）**：一组匹配条件（含图片 / 含工具调用 / 默认）+ 候选模型列表，决定请求往哪个方向路由
4. **Candidate（候选模型）**：路由规则中的单个模型项，含权重、优先级、上下文限制等参数
5. **Model Pointer（模型别名）**：一个"指针"，客户端请求别名时直接转发到指定模型，不走路由规则，可在后台随时切换指向
6. **Aggregated Name（聚合模型名）**：客户端使用的统一模型名（如 smart-latest），触发智能路由
7. **系统配置**：延迟探测参数、重试参数、故障转移参数、管理后台账号等

### 实体关系

一个 Upstream 可被多条 Rule 引用；一条 Rule 包含多个 Candidate；一个 Model Pointer 指向一个 Upstream 下的一个模型；多个 Aggregated Name 是智能路由的统一入口；API Key 通过分组关联到可访问的 Upstream。

## 一、项目概述

Smart Router v5 是 v4 的重构升级版。v4 已实现完整的智能路由能力（多上游源、动态权重、延迟探测、故障转移、Anthropic 格式兼容、Streamlit 管理后台），但存在三个问题：

1. **管理后台技术栈落后**：Streamlit 页面受框架限制，交互体验和扩展性差
2. **配置存储弱**：YAML 文件存储，并发修改易冲突，无版本管理
3. **代码结构混乱**：路由处理逻辑与业务逻辑耦合在单一文件，缺少分层

v5 重构目标：
- 前端从 Streamlit 迁移到 Vue3 + Element Plus，提供现代管理后台体验
- 配置从 YAML 迁移到 SQLite 数据库，支持结构化存储
- 后端按 Router → Service → Schema 分层重组，代码结构清晰可维护
- 补齐缺失流程文档，实现文档与代码对齐

目标用户：使用 OpenAI/Anthropic 兼容接口的开发者（客户端）、系统运维管理员（管理后台）。

## 三、客户端用户需求（API 服务）

**核心目标：** 提供稳定、智能、兼容的 AI 模型调用入口，客户端无需感知底层模型切换。

### 1. 智能路由

#### 功能点 1.1: 统一模型名智能路由
- **用户故事**：作为客户端用户，我想要用一个固定模型名调用接口，以便由网关自动选择最佳底层模型
- **详细描述**：
  - 支持聚合模型名（smart-latest / smart-chat / auto-chat）作为入口
  - 网关根据请求内容（含图片 → 视觉规则、含工具 → 工具规则、否则 → 默认规则）匹配路由规则
  - 每个规则内按优先级和动态权重（结合实时延迟）加权随机选择模型
- **关键交互**：POST 请求携带统一模型名 → 网关返回推理结果
- **状态**：已明确

#### 功能点 1.2: 上下文感知路由
- **用户故事**：作为客户端用户，我想要网关自动估算请求 token 数，以便长上下文请求不会被路由到上下文不足的模型
- **详细描述**：
  - 自动估算请求 token 数（文本约 2 字符/token，图片约 768 tokens/张）
  - 请求超模型上下文限制时自动排除该模型
  - max_tokens 超过模型输出上限时自动调低
- **状态**：已明确

#### 功能点 1.3: 故障转移与自动重试
- **用户故事**：作为客户端用户，我想要模型失败时网关自动换备选模型重试，以便请求尽量成功返回
- **详细描述**：
  - 模型连续失败达到阈值进入冷却期，冷却期内不被选中
  - 请求失败自动换下一个候选模型，最多重试可配置次数
  - 流式请求首包超时自动切换，避免长时间等待卡死的模型
- **状态**：已明确

### 2. 模型别名（指针）

#### 功能点 2.1: 别名固定转发
- **用户故事**：作为客户端用户，我想要用一个固定别名（如 my-model）调用接口，以便管理员切换底层模型时客户端无需改配置
- **详细描述**：
  - 请求别名时直接转发到别名指向的真实模型，不走路由规则
  - 管理员在后台可随时切换别名指向
- **状态**：已明确

### 3. 直接透传

#### 功能点 3.1: 指定模型直连
- **用户故事**：作为客户端用户，我想要直接指定具体模型名调用，以便不经过路由直接使用某个模型
- **详细描述**：
  - 请求具体模型名时，网关查找该模型所属上游源并直接转发
  - 不路由、不重试
- **状态**：已明确

### 4. 协议兼容

#### 功能点 4.1: 多协议格式支持（2026-08-10 修订为协议矩阵）
- **用户故事**：作为客户端用户，我想要用我熟悉的协议格式接入，以便使用对应 SDK 调用
- **详细描述**（协议矩阵，内部以 OpenAI chat 格式为中间语言）：
  - **入站**（客户端 → 网关）：OpenAI chat/completions ✅；Anthropic Messages ✅（CH-009，/v1/messages，兼容 x-api-key 鉴权）；Responses ✅（CH-010，/v1/responses，Codex 可用）
  - **出站**（网关 → 上游）：openai / anthropic / responses 三协议齐备（CH-011 模型级协议覆盖 + CH-014 responses 出站），每个上游模型可单独指定协议
  - 支持流式（SSE）与非流式
- **状态**：3×3 协议矩阵全部上线（2026-08-11）

### 5. 鉴权

#### 功能点 5.1: 两层 Key 鉴权
- **用户故事**：作为客户端用户，我想要用自己的密钥访问网关，以便按密钥控制访问范围
- **详细描述**：
  - 客户端请求必须携带白名单内的有效密钥，否则 401
  - 密钥有分组权限（free/premium），只能访问对应分组的上游源
  - 路由后网关使用上游源自己的密钥访问模型提供商，客户端密钥不透传
- **状态**：已明确

### 8. 聚合模型管理（CH-023 统一）

#### 功能点 8.1: 两类聚合统一管理
- **用户故事**：作为管理员，我想要在同一个页面管理"固定成员聚合"和"规则聚合"，并能分别看到它们的候选与探测情况，而不是两套割裂的机制
- **详细描述**：
  - 统一实体 `agg_unified`，`kind` 区分两类：
    - `static`（固定成员）：自己勾选上游源与各源真实模型名（支持异名），顺序即优先级
    - `rule`（规则聚合）：候选由「路由规则」页在运行时按请求内容匹配；不可配置成员
  - **rule 聚合的规则绑定（CH-024）**：一张规则表 + 每个聚合引用其子集
    - 可只启用部分规则（不启用的规则对本聚合不生效）
    - 每条规则可选「全部候选跟随」或「显式勾选部分候选」
    - 不配置绑定 = 全跟随（使用所有规则、每条规则的全部候选，兼容旧数据）
    - 规则页删除/改名规则 → 自动清理引用它的聚合绑定；清理后为空则回退全跟随
    - 规则页移除候选 → 聚合绑定里的该项变为失效，卡片显示黄标提示（运行时静默跳过）
    - 每个 rule 聚合的探测对象 = 其绑定裁剪后的候选并集，探测成本可区分
  - 两类都可：单独启用/关闭、配置探测、配置排序模式、挂探测模板
  - 列表徽标区分：固定成员 / 规则匹配、手动配置 / 自动发现、模板名、稳定优先 / 速度优先、探测开·间隔·限时段、规则绑定摘要（N 条规则 · M 个候选）
  - 自动发现的同名聚合（跨 ≥2 源、未人工配置）仍展示，标记「自动发现」
- **状态**：已明确（CH-023 统一 + CH-024 绑定，本地验证通过）

  - 规则全选 = 存「跟随」（`candidates: null`）；取消任一候选 = 存显式候选子集

  - 规则页无候选时提示「请先去路由规则页配置候选」
- **状态**：已明确（CH-024 实现，本地验证通过）

#### 功能点 8.2: 探测模板（CH-023）
- **用户故事**：作为管理员，我想要定义几套探测节奏模板，让多个聚合共用，改一次全生效，而不是逐个重复配置
- **详细描述**：
  - 模板字段：名称 / 探测间隔 / 慢阈值 / 排序模式 / 探测时段 / 备注
  - 聚合可选挂一个模板；**挂模板后模板值完全覆盖聚合自配**（不可被组覆盖），UI 对应输入框置灰

#### 功能点 8.3: 聚合独立探测（CH-021，CH-023 扩展）
- **用户故事**：作为管理员，我想要每个聚合自己控制探测节奏与排序方式，以便让慢的成员自动往后排，同时不浪费上游额度

  - 每个聚合独立配置：启用开关 / 探测间隔 / 慢阈值 / 排序模式（稳定优先 / 速度优先）
  - 留空跟随全局；组配置优先（未挂模板时）
  - **探测对象全局去重**：以 `(上游源, 真实模型名)` 为单元，多聚合共享成员只探一次；多聚合引用同一单元时间隔取最小值
  - **rule 聚合的探测对象 = 该聚合按绑定裁剪后的候选并集**（CH-024；无绑定则为全部规则候选并集）
  - 排序分层：正常（未超慢阈值且未冷却）→ 偏慢/未知 → 不可用/冷却；全部不可用时回退配置顺序，不返回空候选
  - **rule 聚合仍沿用 priority + 动态权重排序**（`base_weight × (base_latency/latency)²`），探测结果直接参与排序
- **状态**：已明确（CH-021 / CH-023 实现，本地验证通过）

#### 功能点 8.4: 探测排班表（CH-023）
- **用户故事**：作为管理员，我想要像看排班表一样直观看到每个探测单元一天中什么时候探、成本多少，以便判断额度消耗是否合理
- **详细描述**：
  - 行 = 探测单元（上游源 · 真实模型），列 = 0~23 小时
  - 色块：探测中 / 时段外 / 探测已关闭（斜纹）
  - 视图切换：合并（每天一样）/ 按星期（周一~周日各一行）
  - 行尾给出：间隔、次/时、次/日、引用聚合（规则聚合用不同颜色标注）
  - 表头汇总：单元数、去重省掉的次数、每天约请求数、覆盖聚合数
  - 附带单元明细表（状态 / 最近延迟 / 最近探测时间 / 陈旧标记）与全局探测默认值

## 五、非功能性需求

### 5.1 性能要求
- 路由决策本身无网络 IO，决策耗时 <10ms
- 管理后台接口响应 <500ms
- 页面加载 <2s

### 5.2 兼容性
- 客户端协议：OpenAI chat/completions、Anthropic Messages，流式 + 非流式
- 浏览器：Chrome / Edge / Firefox 最新版本

### 5.3 安全要求
- 客户端密钥白名单校验，未携带或无效密钥返回 401
- 管理后台 JWT 鉴权，所有管理接口必须登录
- API Key 列表中密钥完整值仅管理后台可见，列表接口脱敏
- 路由后使用上游密钥，不透传客户端密钥

### 5.4 可用性
- 单机部署即可，支持热重载，无需停机升级配置
- 模型故障自动转移，不影响客户端
