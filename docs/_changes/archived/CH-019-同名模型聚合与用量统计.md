## 一、变更背景与动机

用户将 dsh-codearts-auth 网关（本机 127.0.0.1:8326，聚合多家提供商账号）作为 upstream 接入中转站后，暴露四类问题：

1. **同名模型无法跨源聚合**：中转站现有聚合只支持"手动建规则把不同名字的模型凑一起"，不支持"同一个模型名分布在多个 upstream 时自动互为候选"。dsh 网关一次性暴露全部提供商模型后，与 trae/glm 等既有 upstream 大量同名，同名模型本应天然互为 fallback，现在却只能走 direct 单源（失败即 503）。
2. **健康/探测按模型名串台**（既有隐性 bug，本次必须修）：`ModelHealth` 以纯模型名字符串记 key，trae 池的 `glm-5-3-flashx` 连续失败会把 dsh 源同名模型一并打入冷却；延迟探测 `_init_models` 按模型名去重，同名只探第一个 upstream。503 故障根因即"死候选 + 单 Key 被同名串台冷却打死"。
3. **模型粒度管理缺失**：upstream 内单个模型无法禁用（dsh 网关同步进来的聚合伪模型 `glm-5-3-flashx` 等死模型想去掉只能整条删），也无法调整模型顺序（影响 direct 命中优先级与展示顺序）。
4. **用量统计为零**：无任何请求日志/usage 表；流式转发逐行透传零解析；无法回答"今天用了多少 token、哪个 Key 消耗最多、哪个模型最活跃"。

## 二、详细设计

### 2.1 同名模型自动聚合（隐式多候选直连）

**方案**：不动 rule_rule/rule_candidate 手动规则体系，在 `_resolve_candidates` 的 direct 分支做"隐式扩展"——

```
解析顺序（不变）：pointer 别名 → aggregated 手动聚合 → direct
direct 分支改造：
  旧：find_model_upstream() 返回第一个命中 upstream → 单候选
  新：collect_model_upstreams(model) 返回所有【已启用 upstream 且模型未被禁用】
      → 每个生成一个候选 {model, upstream, weight=基准, priority=upstream 顺序}
      → 单个命中时行为与旧版完全一致（退化为原 direct）
```

- **优先级**：候选 priority 取 upstream 在列表中的顺序（id 升序，即管理页展示顺序），`get_ordered_candidates` 现有排序逻辑直接复用（priority 升序 + 动态权重降序 + 全 0 退化原序）。
- **与手动规则关系**：手动聚合规则优先级更高（先匹配先返回）；自动聚合只填补"没有任何规则覆盖的同名 direct 模型"，**存量规则零影响**。
- **全局开关**：`sys_setting` 新键 `auto_same_name_aggregate`（默认 `1` 开启），设置页加开关，可一键回退旧行为。
- **/v1/models**：同名模型去重后仍按名字展示一次（客户端视角不变，但该名字背后已是多候选）。

### 2.2 健康与探测按 (upstream, model) 隔离（修串台）

| 位置 | 现状 | 改造 |
|------|------|------|
| `health.py` ModelHealth | `fails[model]`、`cooldown_until[model]` | key 改为 `f"{upstream_id}:{model}"`；对外接口加 upstream_id 参数 |
| `router_engine.get_ordered_candidates` | `get_dynamic_weight(model, ...)` | 改传 `(upstream_id, model)` |
| `probe.py _init_models` | 按模型名 set 去重 | 探测任务改为 (upstream_id, model) 二元组，同名全探 |
| `probe.py probe_one` | 规则候选里找第一个匹配 upstream | 直接按 (upstream_id, model) 定位，不再"找第一个" |
| 管理页探测展示 | 按模型名一行 | 同名多源时按 `model @upstream名` 展示多行（前端小改） |
| 规则页健康标记 | 按模型名查 health | 候选逐项按 (upstream_id, model) 查 |

- 冷却语义随之修正：trae 池死掉不再殃及 dsh 源同名模型——503 根因链（死候选毒化唯一健康 Key）被切断。

### 2.3 模型级 enabled / order

**存储**：复用 `up_upstream.models` JSON 数组，每项扩展为 `{name, protocol?, enabled?, order?}`：
- `_parse_models` 解析新字段，缺省 `enabled=1`、`order=数组下标`（存量数据零迁移）。
- **增量 SQL 06** 仅建 `log_usage` 表（见 2.4）+ 写入 `sys_setting` 新键，models 无 DDL。

**过滤点（6 处，比调研报告多 1 处）**：
1. `/v1/models` 列表（models.py）
2. `find_model_upstream` / 新 `collect_model_upstreams`（config.py，direct 与自动聚合共用）
3. `probe.py _init_models`（禁用模型不探测）
4. 管理页 upstream 详情模型列表（展示但置灰标记禁用态）
5. upstream 全量测试（批量测试跳过禁用模型）
6. `/v1/models` 的聚合与别名解析（别名/规则候选引用的 upstream 模型被禁用时，该候选跳过——`get_ordered_candidates` 候选生成处统一过滤）

**新 API**：

| 方法 | 路径 | 说明 |

| PATCH | `/admin/api/upstreams/{id}/models/{name}` | `{enabled: bool}` 单模型启停 |

**前端**（Upstreams.vue 模型管理抽屉）：
- 每行加 el-switch（禁用置灰 + tag"已禁用"）
- 排序先做"上移/下移"按钮（稳妥、无新依赖）；sortablejs 拖拽列为可选后续
- 同名跨源聚合可在模型行显示"聚合候选 n 个源"徽标（只读提示，不做编辑）

### 2.5 同名聚合可控化（二期，2026-10-16 追加）

**动机**：一期是"隐式自动聚合"——用户看不到某个模型到底聚合了哪几个源、顺序如何，也无法只挑部分源参与，出问题难排查（用户原话："希望也可以可以选择编辑，可控的，不然不好看怎么聚合的"）。

**方案**：新增人工覆盖表 `agg_model_group`，一行 = 一个模型名的聚合配置。

```sql
CREATE TABLE agg_model_group (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    model TEXT NOT NULL UNIQUE,
    upstreams TEXT NOT NULL DEFAULT '[]',  -- JSON [{"upstream":"x","weight":1}]，顺序即候选优先级
    enabled INTEGER NOT NULL DEFAULT 1,     -- 0 = 关闭同名聚合，退化为单源直连
    created_at TIMESTAMP, updated_at TIMESTAMP
);
```

**生效规则**（`collect_model_upstreams` 优先级）：

| 状态 | 行为 |
|------|------|
| 无配置行 | 自动发现（一期行为，零侵入，存量模型不受影响） |
| 有配置 + enabled=1 | 严格按配置的源与顺序，并仍过滤"上游禁用/模型禁用" |
| 有配置 + enabled=0 | 退化为单源直连（取配置里第一个可用源） |
| 删除配置 | 回到自动发现 |

**新 API**（模型名走 query 参数，因为可能含 `/`）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/api/model-groups` | 列出同名多源模型：生效顺序 + 是否手动配置 + 自动发现基线 |
| PUT | `/admin/api/model-groups?model=xxx` | 保存配置 `{upstreams:[{upstream,weight}], enabled}` |
| DELETE | `/admin/api/model-groups?model=xxx` | 删除配置，回到自动发现 |

**前端**（Aggregated.vue 重构）：
- 新增"同名模型聚合（跨源自动兜底）"区块：每个模型一张卡片，用 `1 源A 首选 → 2 源B 兜底` 的链路条直观展示当前聚合方式
- 徽标区分「自动发现 / 已手动配置」「N 源聚合 / 聚合已关闭」
- 「编辑候选」弹窗：**拖拽排序**（sortablejs，拖手柄）+ 勾选参与源 + 单源权重 + 实时"首选"标记
- 「启用聚合」开关、「恢复自动」按钮
- 原有"聚合模型名（手写规则聚合）"区块保留在下方，并加说明区分两套机制

### 2.6 模型排序改为拖拽（二期，2026-10-16 追加）

一期用上移/下移按钮，实测"不好用"。二期改为 sortablejs 拖拽：

- 每行左侧加拖拽手柄（`⠿`），拖完即落库并热重载
- **折叠态禁用拖拽**（只显示前 5 行时拖动会打乱全量顺序），展开后可拖
- 落库以 **DOM 实际顺序**为准（不用 `oldIndex/newIndex` 推算），避免折叠切片与全量数组错位
- 先同步 `modelsByUpstream` 再发请求，避免 Vue 用旧数组回写覆盖拖拽结果

### 2.4 三层用量统计

**新表 `log_usage`**（增量 SQL 06）：

```sql
CREATE TABLE log_usage (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    ts REAL NOT NULL,                  -- 请求完成时间 epoch
    api_key_id INTEGER,                -- 客户端 Key（未认证失败不记）
    api_key_name TEXT,
    upstream_id INTEGER,               -- 实际命中的 upstream（重试取最终成功者；全败记 last）
    upstream_name TEXT,
    model TEXT,                        -- 客户端请求的模型名
    protocol TEXT,                     -- chat / anthropic / responses
    stream INTEGER DEFAULT 0,
    status TEXT,                       -- success / error
    http_status INTEGER,
    prompt_tokens INTEGER DEFAULT 0,
    completion_tokens INTEGER DEFAULT 0,
    total_tokens INTEGER DEFAULT 0,
    estimated INTEGER DEFAULT 0,       -- 1=上游未返回 usage，按字符估算
    duration_ms INTEGER,
    first_token_ms INTEGER,            -- 流式首包耗时（可空）
    error_msg TEXT,                    -- 失败摘要（截断 500 字）
    created_at TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX idx_usage_ts ON log_usage(ts);
CREATE INDEX idx_usage_key_ts ON log_usage(api_key_id, ts);
CREATE INDEX idx_usage_model_ts ON log_usage(model, ts);
```

**采集链路（router_service 单点埋点）**：
- **Key 贯穿**：`contextvars.ContextVar` 在三入站端点认证处 set（api_key_id/name），router_service 统一读取。
- **非流式**：openai 上游响应 JSON 自带 usage，200 分支直接取。
- **流式**：generate() 外包一层解析器——
  - 请求体无 `stream_options` 且上游为 openai 兼容时，注入 `stream_options.include_usage=true`；解析到 usage 的末 chunk **从客户端流中剥离**（客户端没要就不给，避免污染）；客户端自己要求 usage 的则透传不剥。
  - 上游不支持（解析全程无 usage）→ 降级估算：prompt ≈ 请求体文本长度/4，completion ≈ 累计输出文本长度/4，置 `estimated=1`。
  - anthropic / responses 入站的流式最终由统一转换层输出，解析器挂在转换层上游的 openai 流上，入站协议无感。
- **anthropic 出站适配器顺带修**：非流式 usage 硬编码 0 改为映射 openai usage（Claude Code 客户端可见真实用量）。
- **失败请求**：503/超时等也记（status=error，upstream 取最后尝试者），成功率才真实。

**清理**：启动时清一次 + 守护线程 24h 周期清理；保留天数 `sys_setting.usage_retention_days` 默认 30。

**查询 API（admin，全部走现有鉴权）**：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/admin/api/usage/summary` | `?range=today\|7d\|30d` → 总请求/总 tokens/成功率/活跃 Key 数/错误 Top |
| GET | `/admin/api/usage/by-model` | 模型级聚合（请求次数/tokens/平均耗时/错误率），按 tokens 降序 |
| GET | `/admin/api/usage/by-key` | Key 级聚合（同上维度） |
| GET | `/admin/api/usage/logs` | 明细分页 `?page=&size=&key_id=&model=&status=` |

**前端新增 Usage.vue**（侧边栏"用量统计"）：
- 顶部 4 卡片：今日请求 / 今日 tokens / 成功率 / 活跃 Key
- 时间范围切换（今日 / 7 天 / 30 天）
- 按模型表 + 按 Key 表（可排序）
- 最近请求明细表（分页，含协议/流式/耗时/错误摘要）

## 四、决策点（已由用户确认）

1. **同名聚合粒度**：采用方案 A（direct 隐式多候选），并追加二期"人工可编辑覆盖"（`agg_model_group`）——既保持默认零配置，又能显式控制。
2. **注入 stream_options 剥离末 chunk**：采用。客户端未要求 usage 时，注入产生的末尾 chunk 被剥离，透传行为与旧版一致。
3. **排序交互**：一期先做上移/下移按钮 → 用户实测反馈"不好用" → **二期改为 sortablejs 拖拽**。
4. **503 缓解调参**：已在 FB-022 落地（`response_timeout 20→60`、`first_chunk_timeout 8→30`，按 dsh 网关实测 20~40s 取值）。

## 五、验证清单（迷你 stage-5）

- 自动聚合：同名模型分布于 2+ upstream → 请求走第一候选；手动 kill 第一候选 upstream 模拟失败 → 自动 fallback 第二候选；单 upstream 名字行为与旧版一致
- 开关关闭 `auto_same_name_aggregate` → 回退单候选旧行为
- 串台修复：trae 池 glm-5-3-flashx 打死冷却，dsh 源同名模型仍可请求
- 模型禁用：禁用某模型后 /v1/models 不出现、direct 不命中、不探测；启用恢复
- 排序：**拖拽**后顺序落库，重启保持；direct 命中顺序随 priority 变化；折叠态不可拖
- 同名聚合可控：手动配置后按配置顺序生效；关闭开关退化为单源；「恢复自动」回到自动发现；不存在的源/空列表被拒绝
- 用量：非流式 chat / 流式 chat / anthropic messages / responses 四入口各打若干请求 → 明细与三层聚合数字对得上；流式客户端收到的 chunk 序列与旧版一致（注入的 usage chunk 已剥离）
- 估算降级：对不支持 include_usage 的上游造流式请求 → estimated=1 且 tokens 合理
- 存量回归：手动聚合规则、别名、Key 分组、智能重试行为不变
- 部署：`test/deploy_ch019_incremental.py`（**须先修 miniconda 旧路径**）+ 生产四入口冒烟
