## 一、变更背景

opencode 类上游源：同一域名、同一把 Key，但**不同模型绑定不同协议/端点路径**：

| 模型 | 端点路径 | 协议 |
|------|---------|------|
| deepseek-v4-pro/flash、minimax-m3 | `/zen/v1/chat/completions` | OpenAI Chat |
| grok-4.5、grok-build-0.1 | `/zen/v1/responses` | OpenAI Responses |
| qwen3.5/3.6/3.7 系列 | `/zen/v1/messages` | Anthropic Messages |
| gemini-3.1-pro/flash | `/zen/v1/models/{model}` | Google（AI SDK 私有映射） |

现状数据模型中 `format` 是**源级**字段（一个源一种协议），适配器写死路径（openai → `/v1/chat/completions`，anthropic → `/v1/messages`），`RouterService._forward` 只按 `upstream.format` 分发。接 opencode 只能按协议拆 4 个源，同一把 Key 配 4 遍、Key 池/探测/分组状态割裂，管理体验差。

**根因**：协议绑定错了层级——opencode 的协议是"模型级"的，不是"源级"的。

**已否决方案**：按协议拆多源（零改动但 Key 池割裂、体验差）；用指针逐模型路由（职责错配、配置最乱）。

## 二、目标与非目标

### 第一期目标（本变更）

- 上游源模型条目从纯字符串升级为可携带**协议覆盖**：`{name, protocol?}`
- 转发/测试按"模型级 protocol → 缺省回退源级 format"选适配器
- 仅支持继承已有的 openai / anthropic 两种**出站**协议
- opencode 单源即可接入 7 个模型（openai×3 + anthropic×4）

### 非目标（后续分期）

- ❌ responses 出站适配器（grok 类）→ 第二期（CH-012 候选）
- ❌ google 出站适配器（gemini 类，AI SDK 私有映射，价值存疑）→ 单独评估
- ❌ 模型级 endpoint 路径覆盖 → 第一期不需要：`_build_endpoint` 按协议拼标准路径，`base_url=https://opencode.ai/zen` 时 openai/anthropic 路径均正确
- ❌ 入站协议（客户端用什么协议调我们）→ 仍属 PLAN P1/P2，不动

## 三、详细设计

### 3.1 数据模型（无表结构变更）

`up_upstream.models` 列保持 JSON 文本不变，**元素从 string 升级为 object**：

```json
[
  {"name": "deepseek-v4-flash"},
  {"name": "qwen3.7-max", "protocol": "anthropic"}
]
```

- `protocol` 缺省 = 继承源级 `format`；取值第一期仅允许 `openai` / `anthropic`
- **向后兼容**：存量数据是纯字符串数组，repo 层 `_parse_models` 归一化：`"m1"` → `{"name": "m1"}`；读取处统一拿到对象列表，无迁移脚本
- 所有对 models 做字符串比较/展示的位置同步改为取 `.name`

### 3.2 协议解析助手（config.py）

```python
def get_model_protocol(self, upstream_id: str, model: str) -> str:
    """模型级 protocol 覆盖 → 缺省回退源级 format"""
```

遍历该上游 models，命中且有 `protocol` 则返回，否则返回 `upstream.format`（默认 openai）。

### 3.3 分发改造（2 处）

| 位置 | 现状 | 改为 |
|------|------|------|
| `services/router_service.py` `_forward` | `fmt = upstream.get("format")` | `fmt = cfg.get_model_protocol(upstream_id, model)` |
| `api/admin/upstreams.py` `test_upstream` | 同上 | 同上 |

适配器函数签名不变（协议决定走哪个适配器，路径由适配器按协议拼）。

### 3.4 接口与 Schema

| 项 | 改动 |
|----|------|
| `UpstreamCreate.models` / `UpstreamUpdate.models` / `UpstreamModelsRequest.models` | `list[str]` → `list[ModelEntry]`（`{name: str, protocol: str \| None}`），protocol 非法值 422 |
| `PUT /upstreams/{id}/models` | 入参改为对象数组 |
| `DELETE /upstreams/{id}/models?model=` | 字符串比较改为按 `.name` 匹配 |
| `GET /upstreams` 返回 | models 字段返回归一化对象数组 |

### 3.5 前端（Upstreams.vue）

- 模型表格/行内每行加「协议」下拉：`继承源默认` / `openai` / `anthropic`
- 拉取勾选加入、手动添加的模型默认不带 protocol（继承）
- `modelsByUpstream` 类型 `string[]` → `ModelEntry[]`，展示取 `.name`，徽标显示非继承协议
- 批量删除/全量测试逻辑按 `.name` 取值

### 3.6 探测（probe）

第一期**不改**：探测沿用源级 format。影响：opencode 源 format=openai 时探测走 openai 协议，anthropic 模型的探测结果可能不准——可接受，探测样本本就只挑部分模型。
