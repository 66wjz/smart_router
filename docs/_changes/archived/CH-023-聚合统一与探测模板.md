> 分类：B 线-大（数据模型统一 + 调度语义扩展 + 信息架构重组）
> 流程：维护迭代模式 · 迷你 stage-1→5
> 日期：2026-10-17
> 状态：设计待用户确认（未动代码）

---

## 一、背景与问题

### 1.1 现状：两套互不相通的"聚合"

| | 手写聚合名（`agg_aggregated_name`） | 模型聚合组（`agg_model_group`） |
|---|---|---|
| 存的内容 | 只有一个名字 | 名字 + 成员列表（源 + 真实模型） |
| 候选来源 | 请求内容匹配到的路由规则 | 配置的成员列表 |
| 能否配成员 | ❌ | ✅ |
| 能否配探测 | ❌ | ✅ |
| 能否配排序 | ❌ | ✅ |

**核心矛盾**：手写聚合名（`smart-latest` / `auto-chat` / `smart-chat`）本质是"允许客户端用这个名字"，实际走哪个模型由运行时规则匹配决定。它既不能在页面上看到会走哪些模型，也不能单独配探测节奏与排序策略。

### 1.2 探测配置粒度问题

CH-021 实现为"每个聚合组自己配"。当模型数量变多后：

- 多个组想要同样的节奏时，需要逐个重复配置
- 改一次节奏要改 N 个组
- 无法回答"我们现在有几种探测节奏"

### 1.3 探测计划不可读

现在只有"间隔 60s"这种数字，看不出：

- 什么时候探、什么时候不探（时段外）
- 一天到底探多少次
- 频率是被哪个组拉高的

### 1.4 已确认决策（2026-10-17）

| # | 决策 |
|---|---|
| 1 | 探测模板**不可被组覆盖**：选了就完全跟随模板 |
| 2 | 两套聚合**统一成一个实体**，用 `kind` 区分 `static` / `rule`；rule 类型没有成员列表 |
| 3 | 延迟面板移除，内容并入聚合模型页「探测计划」；路由参数页移除 |
| 4 | 请求重试 / 智能重试 / 故障转移（**全局容错**）搬到系统设置 |
| 5 | 旧表保留做回滚兜底，验证稳定后再删 |
| 6 | rule 聚合的探测对象 = **所有规则候选的并集** |
| 7 | **探测结果必须继续参与路由排序**：rule 聚合沿用 `get_ordered_candidates`（priority + 动态权重），static 聚合沿用 `sort_group_candidates`（stable/latency 分层）；统一表不得丢掉动态权重行为 |
| 8 | 所有改动只在本地 + demo 库验证，**不 push、不部署**，等用户明确说"推"才上线 |

## 二、目标

1. 聚合模型统一：一个页面管理全部聚合（固定成员 / 规则匹配），两者都能配探测与排序
2. 探测模板：定义若干节奏模板，多个聚合引用同一模板，改模板即全组生效
3. 排班表：按小时直观展示每天何时探测、每个单元成本多少
4. 信息架构归位：探测相关 → 聚合模型页；容错相关 → 系统设置

## 三、数据模型

### 3.1 新表 `agg_probe_template`

```sql
CREATE TABLE IF NOT EXISTS agg_probe_template (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,              -- 模板名（如"高频-限时"）
    interval_seconds INTEGER NOT NULL,
    slow_threshold_seconds REAL,            -- NULL = 跟随全局
    sort_mode TEXT NOT NULL DEFAULT 'stable',
    schedule TEXT NOT NULL DEFAULT '{}',    -- 同 CH-021 的 schedule 结构
    remark TEXT,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 3.2 统一聚合表 `agg_unified`

```sql
CREATE TABLE IF NOT EXISTS agg_unified (
    name TEXT PRIMARY KEY,                  -- 聚合名（客户端请求用）
    kind TEXT NOT NULL,                     -- 'static' | 'rule'
    members TEXT NOT NULL DEFAULT '[]',     -- 仅 static：JSON [{upstream, model, weight}]
    enabled INTEGER NOT NULL DEFAULT 1,
    template_id INTEGER,                    -- 探测模板（NULL = 用组自配）
    sort_mode TEXT NOT NULL DEFAULT 'stable',
    interval_seconds INTEGER,               -- 仅 template_id 为空时生效
    slow_threshold_seconds REAL,
    schedule TEXT NOT NULL DEFAULT '{}',
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### 3.3 迁移（幂等）

```sql
-- 1) 旧手写聚合名 → rule 类型
INSERT OR IGNORE INTO agg_unified (name, kind)
SELECT name, 'rule' FROM agg_aggregated_name;

-- 2) 旧聚合组 → static 类型（upstreams 字段改名为 members，结构一致）
INSERT OR IGNORE INTO agg_unified (name, kind, members, enabled)
SELECT model, 'static', upstreams, enabled FROM agg_model_group;

-- 3) 旧探测配置 → 合并进对应行（仅对已存在的行）
UPDATE agg_unified
SET interval_seconds = (SELECT p.interval_seconds FROM agg_probe_config p WHERE p.model = agg_unified.name),
    slow_threshold_seconds = (SELECT p.slow_threshold_seconds FROM agg_probe_config p WHERE p.model = agg_unified.name),
    sort_mode = COALESCE((SELECT p.sort_mode FROM agg_probe_config p WHERE p.model = agg_unified.name), sort_mode),
    schedule = COALESCE((SELECT p.schedule FROM agg_probe_config p WHERE p.model = agg_unified.name), schedule)
WHERE EXISTS (SELECT 1 FROM agg_probe_config p WHERE p.model = agg_unified.name AND p.enabled = 1);
```

> 注：`agg_probe_config.enabled = 0` 的组不迁移探测配置（保持"不探测"语义，由 `agg_unified.enabled` 之外的默认值表达）。
> 旧表 `agg_aggregated_name` / `agg_model_group` / `agg_probe_config` **保留不删**，代码切换到新表读取，验证稳定后再单独出清理脚本。

### 3.4 schedule 结构（沿用 CH-021）

```json
{"mode": "always"}
{"mode": "window", "days": [1,2,3,4,5], "windows": [{"start":"08:00","end":"23:00"}]}
```

## 四、探测模板语义

### 4.1 优先级

```
模板（若 template_id 非空） → 组自配 → 全局 latency_probe → 内置默认
```

- 选了模板：`sort_mode` / `interval_seconds` / `slow_threshold_seconds` / `schedule` **全部**取模板值，组自配字段不生效（UI 置灰并显示"由模板「xxx」决定"）
- 未选模板：按组自配字段，缺失项回退全局

### 4.2 多组共用同一模型时的间隔

仍沿用 CH-021 的 **min 规则**：同一 `(上游源, 真实模型)` 被多个聚合引用时，取最小间隔。

模板的价值在于**消除大部分混搭场景**：把需要 5 分钟的组都挂同一模板，就不会与"另一个组 10 分钟"冲突。物理上只发一次请求，这是无法回避的约束。

### 4.3 删除模板

- 删除前列出引用它的聚合组数量
- 确认后：相关组的 `template_id` 置空，回退到组自配（若组自配为空则回退全局）
- 不删除聚合组本身

## 五、探测计划与排班表

### 5.1 归属修正（把 rule 聚合纳入）

现状：`collect_probe_plan` 对规则候选只记 `source=rule`，看不出为哪个聚合名服务。

改后：

```
rule 聚合（smart-latest / auto-chat）
  → 展开为「所有规则的候选并集」
  → 每个单元记录 groups: ["smart-latest", "auto-chat"]
```

**为什么取并集**：rule 聚合的候选在运行时按请求内容决定（带图→视觉规则、带工具→工具规则、其他→默认规则），探测时无法预知，只能全探。这是"宁可多探也不漏"的取舍。

**间隔与时段**：rule 聚合也有自己的探测模板/配置。若同一单元同时被 static 组和 rule 聚合引用，仍按 min 规则与时段并集处理。

### 5.2 排班表（新视图）

```
① 汇总条
   N 个探测单元 · 去重省 M 次 · 每天约 X 次请求 · 覆盖 P 个聚合

② 排班表（核心）
   ┌──────────────────────────────┬───────────────────────────────┬────────┬──────┬──────┬─────────┐
   │ 探测单元                      │ 00 01 02 ... 22 23            │ 间隔    │ 次/时 │ 次/日 │ 引用聚合 │
   ├──────────────────────────────┼───────────────────────────────┼────────┼──────┼──────┼─────────┤
   │ buddy · deepseek-v4.1-flash   │ ░░░░░░░░████████████████████   │ 60s    │ 60   │ 900  │ ds-flash│
   │ loomy · DeepSeek-V4.1-Flash   │ ░░░░░░░░████████████████████   │ 60s    │ 60   │ 900  │ ds-flash│
   │ trae  · deepseek-v4.1-flash   │ ████████████████████████████   │ 300s   │ 12   │ 288  │ qwen3   │
   │ dsh   · glm-4.6               │ ──────────────────────────     │ —      │ 0    │ 0    │ glm-4-6 │
   └──────────────────────────────┴───────────────────────────────┴────────┴──────┴──────┴─────────┘

   ██ 探测中   ░░ 时段外   ── 探测已关闭

③ 视图切换：[合并] [按星期]（周一~周日各一行）
④ 单元明细：状态 / 最近延迟 / 上次探测 / 陈旧标记 / 错误
⑤ 全局探测默认值（原路由参数的探测部分）
```

色块规则：
- 按 `schedule` 计算每小时是否可探（`always` → 全彩；`window` → 窗口内彩、窗口外灰）
- 按 `days` 决定按星期视图中的行是否可探
- 探测关闭（聚合未启用或未开探测）→ 整行 `──`

### 5.3 计算方式

纯前端计算，无需新接口：

```
每小时可探 = schedule_is_active(该小时的代表时刻)
次/时 = 3600 / interval（四舍五入，最小 1）
次/日 = Σ(每个可探小时的 次/时)
```

## 六、聚合组卡片与配置抽屉

### 6.1 卡片（统一列表）

```
┌────────────────────────────────────────────────────────────────┐
│ deepseek-v4-1-flash  [手动成员]  [模板: 高频-限时]  [速度优先]  │
│  buddy·deepseek-v4.1-flash → loomy·DeepSeek-V4.1-Flash → ...   │
│  近 7 天 297 次 · 268.7K tokens              [探测设置] [配置]  │
├────────────────────────────────────────────────────────────────┤
│ smart-latest  [规则匹配]  [模板: 标准]  [稳定优先]              │
│  默认对话 / 视觉理解 / 工具调用（3 条规则，运行时按内容匹配）    │
│  近 7 天 120 次 · 98.3K tokens               [探测设置] [配置]  │
└────────────────────────────────────────────────────────────────┘
```

差异：
- `static`：显示成员链路 + 可「编辑成员」
- `rule`：显示匹配的规则名列表 + 不可编辑成员（提示"候选由路由规则决定"）

### 6.2 配置抽屉

```
[探测]
  使用模板  [下拉：不使用 / 高频-限时 / 标准 / ...]
  （选模板后以下置灰，显示"由模板「xxx」决定"）
  探测间隔 / 慢阈值 / 排序模式 / 探测时段

[成员延迟]（仅 static）
  实时表格：源 · 真实模型 · 状态 · 延迟 · 上次探测

[生效预览]
  按当前排序策略，列出"现在来请求会按什么顺序尝试"
  static：按排序策略排成员
  rule：显示当前命中的规则与候选顺序（无请求上下文时按默认规则）
```

├── 路由规则        （保留：规则是候选库，被 rule 聚合引用）

### 7.3 容错参数归位的理由

这三个参数是**全局**的，与聚合无关：

| 参数 | 作用范围 | 证据 |
|---|---|---|
| 请求重试 | 每次请求（规则聚合 / 直接透传 / 别名统统生效） | `router_service.chat_completions` 无条件读取 |
| 智能重试 | 按上游源开关，全局共享一套退避参数 | `_RetryLoop` 读 `smart_retry_config` |
| 故障转移 | 全局模型冷却 + Key 池冷却 | `main.py` 初始化 `ModelHealth` |

放在"路由参数"页会让人误以为只影响路由。

## 十三、风险与不做

### 风险

| 风险 | 缓解 |
|---|---|
| 迁移丢配置 | 旧表保留；迁移前后逐条比对；先备份 demo.db 和正式库 |
| rule 聚合的候选并集导致探测变多 | 排班表直接显示成本；可对 rule 聚合单独关探测 |
| 模板改动影响面大 | 修改前展示"将影响 N 个聚合" |
| 旧接口转调出 bug | 保留旧端点 + 单测逐一比对响应 |

### 15.2 与设计的偏差

| 项 | 设计 | 实际 | 原因 |
|---|---|---|---|
| 旧表读取 | 代码全部切新表 | `_sync_legacy_views()` 把统一表投射回 `_aggregated_names` / `_model_groups` 内存视图 | 既有路由链路（`resolve_group_candidates` / `collect_model_upstreams` / `is_model_group`）零改动即继续工作，降低回归面 |
| 自动发现聚合 | 未提 | 列表接口额外并入 `configured=false` 的同名自动发现组 | 升级后这些聚合不能从页面上消失 |
| 模板编辑表单 | 复用同一张表单 | 增加 `mode="template"`，隐藏「使用模板 / 启用探测」两项 | 模板不该引用模板，也不该有独立开关 |
| 显式清空 | 未提 | `PUT /aggregations` 用 `model_fields_set` 区分「未提供」与「传 null」 | 前端解绑模板 / 清空自配间隔原本会静默失效（实测发现） |
