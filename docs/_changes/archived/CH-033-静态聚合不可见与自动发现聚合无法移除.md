# CH-033 静态聚合不出现在 /v1/models + 自动发现聚合无法移除

> 类型：A 线（Bug 1）+ B 线-小（Bug 2）
> 状态：待实现
> 日期：2026-10-18

---

## 一、背景

用户配置了一个 static 聚合 `deepseek-v4-1-flash`，客户端拉取模型列表时**看不到它**；聚合页还出现 4 个「自动发现」聚合，点「移除」无反应。

### Bug 1：static 聚合不出现在 `/v1/models`

**现象**：`GET /v1/models` 返回 29 条，全部是上游源的真实模型名，不含 `deepseek-v4-1-flash`；但直接 `POST /v1/chat/completions` 用该聚合名**返回 200**（路由正常）。

**根因**：`backend/app/core/config.py` 的 `_sync_legacy_views()`：

```python
self._aggregated_names = [
    name for name, a in self._aggregations.items()
    if a.get("kind") == "rule" and a.get("enabled", True)   # ← 只收集 rule
]
```

而 `api/v1/models.py` 的聚合条目**只遍历 `cfg.aggregated_names`**，因此 static 聚合被完全遗漏。

**历史原因**：CH-019 时「同名聚合」的聚合名就等于真实模型名，天然出现在上游模型列表里，不需要额外输出。CH-020 引入**异名聚合**（聚合名与任何真实模型名都不同）后，这个盲区才暴露。

### Bug 2：自动发现的聚合无法移除

**现象**：聚合页出现 `accio/deepseek-v4-1-flash`、`buddy/deepseek-v4.1-flash`、`loomy/DeepSeek-V4.1-Flash`、`trae/deepseek-v4.1-flash` 四条「自动发现」聚合，点「移除」提示失败。

**根因**：
1. 这些聚合由 `collect_group_members()` **在内存中即时推导**（同名模型分布在 >=2 个启用上游源），`agg_unified` 表里**没有对应行**
2. `delete_aggregation()` 只执行 `DELETE FROM agg_unified WHERE name=?`，删不到行 → 返回 `False` → 接口 404
3. 前端 `removeGroup()` 收到 404 → 报「操作失败」

**触发条件（本次场景）**：`dsh` 仍启用且保留 4 个模型，这 4 个模型与分源同名 → 系统判定为「跨源同名」，自动聚合成 4 组。因 `dsh` 与分源实际指向同一号池（`http://127.0.0.1:8326`），这类聚合无实际收益。

## 三、方案

### 3.1 Bug 1：`/v1/models` 补 static 聚合条目

**改动**：`backend/app/api/v1/models.py`

在现有「聚合模型条目」循环之外，**另加一段**遍历 static 聚合（`entities` 中 `kind == "static"` 且 `enabled`），产出条目：

```python
{
    "id": 聚合名,
    "object": "model",
    "created": 0,
    "owned_by": "smart-router",
    "type": "aggregation",
    "aggregation_kind": "static",
    "member_count": len(members),
}
```

**约束**：
- 必须先去重——若某个 static 聚合名恰好等于某个真实模型名（CH-019 旧行为），不能重复输出
- `enabled=False` 的聚合不输出（与 rule 聚合语义一致）
- 不改 `aggregated_names` 属性本身（它还被路由链路 `_resolve_candidates()` 用作「是否为 rule 聚合」的判据，改动会误伤路由）

> 采用「在 models.py 里单独遍历 static」而不是「改 `aggregated_names`」，是为了把改动限制在展示层，零风险影响路由。

### 3.2 Bug 2：自动发现聚合支持「移除」

**改动**：`backend/app/services/config_service.py` + `backend/app/api/admin/aggregations.py`

`delete_aggregation()` 改为两段逻辑：

1. 先尝试删 `agg_unified` 行（人工配置的聚合）
2. 若删不到（`False`）且该名字在 `collect_group_members()` 中（即自动发现的聚合），则**落库一条 `enabled=false` 的 static 行**，达到「关闭该聚合」的效果

> 为什么不直接删上游模型？因为那会破坏用户的模型配置。用「落库关闭」既满足「移除」意图（聚合不再生效、不再出现在列表），又完全可逆（「恢复自动」按钮会把 `enabled` 改回 true）。

**前端**：`Aggregated.vue` 的 `removeGroup()` 无需改动（后端语义变了，前端照旧调用）。

**幂等**：重复移除同一个自动发现聚合，第二次走「已存在行 → 置 enabled=false」，仍返回成功。

### 3.3 不做的事

- 不改 `aggregated_names` 的语义（避免误伤路由）
- 不改同名自动聚合的判定规则（属 CH-019 既定设计）
- 不自动清理 `dsh` 的重复模型（需用户决策，见第四节）

## 四、遗留：dsh 与分源重名

本次 4 个自动发现聚合的**根因**是 `dsh` 与分源存在同名模型。修复 Bug 2 后可逐个「移除」，但更彻底的做法是清空 `dsh` 的模型列表（保留空壳）或删除 `dsh`。**需用户确认后再做**，本次不改。

## 六、验收标准

1. **Bug 1**：`GET /v1/models` 含 `deepseek-v4-1-flash`，且带 `type: "aggregation"`
2. **无重复**：若聚合名与真实模型同名，列表中只出现一次
3. **禁用不显示**：`enabled=false` 的 static 聚合不出现在列表
4. **Bug 2**：对「自动发现」聚合点移除 → 返回 200，刷新后该聚合消失
5. **可逆**：移除后点「恢复自动」→ 聚合重新出现
6. **不影响路由**：直接调用聚合名仍 200；rule 聚合行为不变
7. **回归**：`verify_api_ch023` / `verify_rule_binding_ch024` / `verify_aggregation_ch023` 全通过
8. **编译**：`compileall` 0 错误；前端 `npm run build` 通过

## 七、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 改 `/v1/models` 导致模型列表膨胀 | 客户端看到更多条目 | 只加聚合名（数量远小于真实模型数） |
| 名字与真实模型冲突 | 客户端调用歧义 | 聚合条目优先级低于真实模型（真实模型先加入，聚合后加入并去重） |
| 「移除」自动发现聚合被误解为删除上游模型 | 用户预期落差 | 前端确认弹窗文案改为「关闭该聚合（不影响上游模型）」 |

回退：`git revert` 本次提交。
