## 一、需求（迷你 stage-1）

用户原话要点：

1. **聚合模型也要有测试按钮**，像上游源那样可以点一下测试。
2. **聚合成员的调度要均衡**：三个提供商的模型都能用，就按权重分请求。例：A=2、B=1、C=1，则 100 次请求里 A 约 50 次、B 25、C 25（2/4、1/4、1/4）。
3. **成员不可用时重新归一化**：C 挂了，就按 A=2、B=1 重新分配（100 次 ≈ A 67 / B 33），允许 66/34 这类整取。
4. 先按「请求次数」做，不按 token 数。

用户已确认的两个决策：

- 权重分发给**所有固定成员聚合**默认生效；权重全为 1 时即平均轮询（不再「第一个永远优先」）。
- 测试按钮 = **逐个成员测试 + 走聚合路由再测一次**。

## 二、设计（迷你 stage-2）

### 2.1 加权分发

| 项 | 决定 |
|---|---|
| 算法 | **平滑加权轮询 SWRR**（nginx 同款）：每个成员维护 current 值，每次 `current += weight`，选最大者并把该成员的 current 减去总权重。一个周期（权重和）内严格按比例，无需持久化 |
| 生效对象 | 显式配置的**固定成员聚合**（static），成员 ≥ 2；规则聚合（rule）维持原优先级+动态权重逻辑不变 |
| 权重来源 | 复用聚合成员已有的 `members[].weight`（面板 1-10，后端夹到 1-100，缺省 1） |
| 失败重归一 | 复用现有健康冷却：连续失败 3 次进入冷却（默认 120 秒），冷却中的成员**从权重池剔除**，其余成员按剩余权重重新归一；冷却结束自动回归。探针状态 `down` 的成员同样剔除 |
| 兜底 | 可用成员 < 2 时保持原顺序（含冷却成员），绝不因权重把请求打成 503 |
| 顺序语义 | 被选中的成员排到候选第一位，其余维持「稳定/速度优先」的排序作为失败兜底链 |
| 状态 | 进程内存（每个聚合一份 current 表），成员或权重变化时自动重置；重启后从零开始 |
| 日志 | `[weight] 聚合 X 权重分发 [A×2, B×1, C×1] → 命中 A` |

### 2.2 聚合测试端点

`POST /admin/api/aggregations/test?name=<聚合名>`，body `{prompt?: string, include_aggregate?: boolean}`。

- **成员逐个测试**：static 用配置成员（含异名模型，去重）；rule 用该聚合绑定的规则候选并集（去重，最多 20 个）。逐个调用 `test_non_stream*`（与上游源测试同一条路径），**不写用量、不动健康状态**。
- 已禁用/模型已禁用的成员返回 `skipped`，不发请求。
- 返回每个成员的 `status / latency_ms / content / error / weight / share / cooling`。
- **走聚合再测一次**：复用 `RouterService` 的候选解析（含权重分发与兜底顺序），按候选顺序最多试 `max_attempts` 个，返回实际命中的成员、耗时、回复，以及失败尝试链。
- 两者串行，一次请求返回两段结果。

### 2.5 不做

- 不按 token 加权（用户明确先按请求次数）。
- 不持久化轮询状态（重启从头开始，比例会自然收敛）。
- 不改规则聚合的选路逻辑。
- 不改数据库表结构（weight 字段已有）。

### 2.6 验收

1. 权重 2/1/1，连续 100 次解析 → 命中次数 50/25/25（允许顺序不同）。
2. 其中一个成员进入冷却 → 剩余按 2/1 分配（100 次 ≈ 67/33），冷却结束后回归 2/1/1。
3. 所有成员冷却 → 仍按原顺序返回候选，不 503。
4. 聚合测试端点：成员逐个返回真实结果；聚合路由测试返回实际命中成员；中文上游 ID 不再触发响应头异常。
5. 前端构建通过；卡片有「测试」与权重角标；弹窗两段结果正常渲染。
