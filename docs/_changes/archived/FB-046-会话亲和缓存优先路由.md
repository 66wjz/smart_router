# FB-046 会话亲和：缓存优先路由（CH-052）

> 日期：2026-10-28 ｜ 类型：B 线-大（路由行为调整 + 新状态层 + 观测字段）
> 模式：维护迭代迷你 5 阶段（不走门禁，收尾统一同步）

## 一、背景与目标

用户在排查缓存命中时发现：

- `test_demo`（单成员 opendesign）缓存命中 ≈99%；
- `deepseek-v4-1-flash`（trae 4 / opendesign 2 / loomy 1）整体命中率不低（opendesign 94%、trae 80%），但**新会话前几轮**几乎全 miss；
- 根因不是显示错误（`estimated=0`，数值都是上游真实返回），而是缓存按「提供商 + 账号/Key + 前缀」隔离，且链路上有多次「换人」：聚合按请求换源、路由器 Key 池轮询、号池内部轮换账号、前缀变化/TTL。

用户决策（2026-10-29）：

1. **不依赖客户端改动**（多人使用，不能要求人人传 session id）。
2. 新会话按 `负载/权重` 选一家，**钉住**；之后同一会话一直用它。
3. 只有那一家失败才换，换完不切回。
4. **不依赖号池**的账号机制；我们只保证本层「聚合成员不每请求换」，号池内部轮换算残余风险。
5. 权重保留（语义从「每请求配额」改为「新会话容量比例」），统计保留。
6. 短请求不钉；按聚合可单独开关，默认开。

## 二、设计

### 2.1 会话识别（无客户端改动）

`affinity_key` 优先级：

1. 请求体 `user` 字段（如果客户端本来就有）→ `hash(model + user)`；
2. **前缀指纹**：`hash(model + 第一条 user 消息文本)`（多模态取 text 部分）；
3. 没有 user 消息 → `hash(model + 第一条消息文本)`；
4. 都没有 → 不钉。

只 hash 第一条 user 消息，不 hash 全量（每轮都在增长）。哈希用 SHA-256 截断 16 位，不落原文。

### 2.2 亲和表

内存 `affinity_key -> {upstream, model, key, expires_at, last_seen}`：

- TTL：空闲 **45 分钟**（可配），每次请求续期；
- LRU 上限 **2 万条**；
- 重启后清空（活跃会话各冷一次，可接受）；
- 记录每个上游的「近 5 分钟请求数 + 活跃会话数」，用于新会话放置。

### 2.3 路由规则

| 场景 | 行为 |
|---|---|
| 新会话首次请求 | 在健康候选里按 `score = 负载 / weight` 取最小，钉住 `(upstream, model, key)` |
| 同会话后续请求 | 钉住目标健康且在候选里 → 排到首位，忽略权重/负载 |
| 钉住目标冷却/不在候选 | 重新放置并改钉，`switch_reason=health/candidate_missing` |
| 请求中该目标失败 | 请求本身按候选兜底切下一家；**成功后把钉子改到成功那家**（最新前缀已在它那儿），`switch_reason=failover` |
| 切走之后 | 不切回原家 |
| 短请求（估算 prompt < 2000 tokens） | 不钉，走原权重轮询/SWRR，`switch_reason=short` |
| 聚合 `affinity=0` / 全局关闭 | 不钉，走原逻辑 |

### 2.4 Key 钉住

- `KeyPool.pick` 支持 `preferred key`（contextvar 传入）：会话内优先用上次成功的 Key；
- preferred 不可用或该 Key 失败 → 同上游换 Key；全部 Key 不可用才换上游；
- 成功后把实际使用的 Key 写回亲和表。

### 2.5 观测

`log_usage` 增加：

- `affinity_key`：会话指纹（16 位 hash，不存原文）；
- `affinity_hit`：本次是否命中了钉子（0/1）；
- `switch_reason`：`none/new/health/candidate_missing/failover/short/disabled/no_key`。

`agg_unified` 增加 `affinity`（NULL=跟随全局，0=关，1=开）。

## 四、验收

1. 同一会话连续 100 次请求 → 首位始终同一上游（短请求/关闭开关除外）。
2. 1000 个新会话按权重 4:2:1 分布，允许 ±5% 误差。
3. 钉住的上游失败 → 下一次自动换到另一家并**保持**；不切回。
4. 同上游多 Key → 同一会话固定同一 Key；Key 冷却才换。
5. 短请求（<2000 tokens）不产生亲和条目。
6. 测试端点/探测不写亲和表。
7. `log_usage` 能看到 `affinity_key/affinity_hit/switch_reason`。
8. 旧库自动补列，不需要手工迁移。

## 五、不做

- 不改客户端、不要求 session header；
- 不改号池（8326）内部账号选择；
- 不保证跨提供商缓存共享（物理上限）；
- 不做持久化（重启后重新钉）。

## 六、实施结果（2026-10-28）

按上述设计全部落地，实施中补齐三处细节：

- **单候选不钉**：聚合/直连只剩 1 个候选时直接返回原顺序，不占亲和表（`switch_reason=single`）。
- **非流式观测时序**：`_log` 在 `_finish_affinity` 之前落库，因此 `_UsageTracker` 记录钉住目标 `affinity_target`，落库前若实际命中不同源，先改写 `affinity_hit=0 / switch_reason=failover`，保证用量表与真实情况一致。
- **Key 钉子跟随实际 Key**：同上游因 Key 冷却/重试换了账号时，成功后把钉子更新为实际成功的 Key（原实现只在钉子无 Key 时更新，会导致缓存对不上）。
