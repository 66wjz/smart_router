# CH-048 分组管理改为展示型列表 + 弹窗编辑

> 类型：B 线-小（交互形态调整，纯前端）
> 状态：已实现 + 浏览器逐项验证通过，待用户验收
> 日期：2026-10-22
> 来源：用户验收 CH-047 后指出「分组管理要和上游源一样，条目是展示的，点右侧修改按钮才弹窗编辑；添加分组也弹窗填写」（FB-040）
> 前置：CH-042 ~ CH-047

---

## 一、问题

CH-047 把分组管理从裸 `el-table` 改成了 `ListPage` + `DataTable`，但保留了**行内输入框**：

- 「分组名」「描述」两列是 `BaseInput`，点进去就能改；
- 新增分组是往表格里 push 一个空行，然后在新行里输；
- 因为后端 `updateGroups` 是全量替换语义，不得不再挂一个「保存分组」按钮兜着。

结果是：**列表看着是只读表格，实际却是可编辑表单**——与上游源「卡片展示 + 右侧按钮 + 弹窗编辑」的形态不一致，也与其它所有列表页不一致。

---

## 二、目标形态（对齐上游源）

| 项 | 目标 |
|---|---|
| 列表条目 | 纯展示文本，不可直接编辑 |
| 行操作 | 右侧「修改」「删除」两个按钮 |
| 添加 | 右上角「+ 添加分组」→ 弹窗填写 → 确定 |
| 修改 | 点「修改」→ 弹窗预填 → 确定 |
| 保存时机 | **即时提交**（弹窗确定 / 删除确认后立刻调接口） |
| 「保存分组」按钮 | **移除**（不再需要） |

---

## 三、关键决策

### 3.1 即时提交后，全量替换语义不再需要「暂存」

后端 `PUT /admin/api/groups` 传的是完整数组，不在数组里的分组会被删。改成弹窗后，每次操作都是「拿当前完整列表 + 本次这一处改动」组成新数组提交，行为与原来的「点保存一次性提交」等价，只是提交时机提前到每一步。

**好处**：不需要「保存分组」按钮，不需要「改了没保存」的提示，界面与上游源完全一致。

### 3.2 成功后重新拉取，失败后也重新拉取

- 成功 → `load()` 重拉，保证本地数组与服务端一致（后端会 `strip()` 名字、过滤空名）；
- 失败 → 也 `load()`，把本地临时改动冲掉，避免界面显示「已改」但库里没改。

失败最常见原因是**删除/改名了仍被引用的分组**，后端返回 400 并列出是哪些分组被引用——前端直接把 `detail` 弹出来。

### 3.3 允许改名，但要提示

上游源的 ID 编辑时禁用，但分组名是唯一标识、用户确实有改名需求，所以编辑弹窗里「分组名」可改。改名在数据层面等价于「删旧名 + 加新名」，因此：

- 若旧名仍被上游源 / API Key / 聚合引用 → 后端拒绝，弹窗提示原因；
- 若未被引用 → 改名成功，但这几个引用方需自行改到新分组名。

弹窗里加一条 `BaseHint` 说明这点。

### 3.4 名称唯一性前端先挡一道

后端 `set_groups` 只做去空、不去重。前端在弹窗里先校验：
- 新增时不允许与已有分组重名；
- 编辑时不允许改成其它分组的名字（改回自己原名算无变更）。

避免提交出「两个同名分组」的脏数据。

## 五、验证方案

| 项 | 预期 |
|---|---|
| 列表展示 | 分组名/描述为纯文本，无输入框 |
| 添加分组 | 点右上角 → 弹窗 → 填名+描述 → 确定 → 列表立刻出现新行 |
| 修改 | 点「修改」→ 弹窗预填 → 改名/改描述 → 确定 → 列表更新 |
| 重名校验 | 新增填已有名字 → 提示「分组名已存在」，不发请求 |
| 删除未被引用的分组 | 确认后立刻从列表消失 |
| 删除被引用的分组 | 后端 400，前端提示「分组 X 仍被上游源或 API Key 引用」 |
| 空名 | 弹窗确定时提示「分组名不能为空」 |
| 保存按钮 | 页面不再有「保存分组」按钮 |
| 构建 | `npm run build` 通过 |
