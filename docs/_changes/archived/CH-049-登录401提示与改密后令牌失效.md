# CH-049 登录 401 提示纠正 + 改密后令牌失效

> 类型：A 线（bug）1 项 + B 线-小（设计调整）1 项
> 状态：已实现 + 回归全通过（2026-10-22）
> 日期：2026-10-22
> 来源：用户实测「改了密码后登不上去，只提示未登录或登录已过期」（FB-043）
> 前置：CH-032（JWT 密钥动态化）

## 一、现象与定位

### 1.1 现场

用户在后台点「修改密码」改成新密码，之后登录一直失败，提示「未登录或登录已过期」。

生产访问日志：

```
22:54:56  PUT /admin/api/admin-password   → 401 Unauthorized
22:55:02  POST /admin/api/login           → 401 Unauthorized
22:55:03  POST /admin/api/login           → 401 Unauthorized
22:55:05  GET  /login                     → 200
22:56:16  POST /admin/api/login           → 401 Unauthorized
22:57:17  POST /admin/api/login           → 401 Unauthorized
```

库侧：`sys_setting.admin.updated_at` 仍是 8 天前，`password` 长度未变 —— **新密码从未写入**。

### 1.2 两个独立问题

| # | 问题 | 分类 | 性质 |
|---|---|---|---|
| A | 登录接口返回 401（用户名或密码错误）时，前端统一提示「未登录或登录已过期」，并执行 `removeToken()` + 跳登录页 | **A 线 bug** | 提示语义错误 + 无意义的状态清理 |
| B | 改密码后旧 JWT 仍然有效，不会失效 | **B 线-小** | 设计缺口（安全维度） |

问题 A 掩盖了真实原因（密码不对），是用户这次「看不懂为什么登不上」的直接原因。

## 二、改动方案

### 2.1 A 线：`request.ts` 的 401 分流

**现状**（`frontend/src/utils/request.ts`）：

```ts
if (status === 401) {
  msg = '未登录或登录已过期'
  removeToken()
  router.push('/login')
}
```

**问题**：登录接口本身就是「未登录」状态，返回 401 表示**账号密码不对**，不是会话过期。

**改法**：登录请求的 401 单独分流 —— 用后端 `detail`（「用户名或密码错误」）作为提示，**不**清 token、**不**跳转（本来就在登录页）。

```ts
const isLoginApi = (error.config?.url || '').includes('/admin/login')
if (status === 401) {
  if (isLoginApi) {
    msg = error.response.data?.detail || '用户名或密码错误'
  } else {
    msg = '未登录或登录已过期'
    removeToken()
    router.push('/login')
  }
}
```

### 2.2 B 线-小：JWT 携带密码指纹，改密即失效

**现状**：token payload 只有 `sub` / `exp` / `iat`，与密码无关。改密码后旧 token 依然可用直到自然过期。

**改法**：token 里带一个密码指纹 `pv`（`sha256(password)` 前 16 位），`check_auth` 每次校验时与**当前密码**的指纹比对，不一致即 401。

```python
# auth_service.py
@staticmethod
def password_version(password: str) -> str:
    return hashlib.sha256(password.encode()).hexdigest()[:16]

# login 时
token = create_jwt({
    "sub": username,
    "pv": self.password_version(expected_pass),
    "exp": ..., "iat": ...,
})

# deps.py check_auth 末尾
expected_pv = AuthService.password_version(config.admin_config.get("password", ""))
if payload.get("pv") != expected_pv:
    raise HTTPException(401, "密码已变更，请重新登录")
```

**为什么用密码指纹而不是随机版本号**：
- 版本号要额外落库（多一个 `sys_setting` 键），且改密时忘记递增就失效不了；
- 指纹从密码本身推导，只要密码变了指纹必然变，**不存在忘记递增的可能**；
- 只取 sha256 前 16 位、且只在签名后的 payload 里出现，不额外暴露密码信息。

**兼容性影响（必须告知）**：上线后**所有已登录会话会立刻失效一次**（旧 token 没有 `pv` 字段，比对必然不通过）。这是「改密即失效」能力的固有代价，也是一次性的。

### 2.3 顺带：改密成功后主动退出

改密成功 → 后端密码已变 → 客户端手里的 token 立刻作废。若等下一次请求才 401，用户会觉得「点一下菜单突然被踢」。

因此前端 `handleChangePwd` 成功后主动 `logout()` + 跳登录页，并提示「密码已修改，请重新登录」。

### 3.1 实施中发现的第二处真问题（隐藏 bug）

首轮实现时 `check_auth` 写的是：

```python
current = request.app.state.config.admin_config.get("password", "")   # 默认 ""
```

而 `AuthService.login` 用的是：

```python
expected_pass = admin_cfg.get("password", "smart-router-2026")        # 默认有值
```

**两处默认密码不一致**。当 `sys_setting` 里还没有 `admin` 记录时（全新库、回归脚本建的空库就是这种情况），login 用 `smart-router-2026` 推导 `pv`，check_auth 用 `""` 推导 → 指纹不等 → **所有管理接口 401**。

回归立刻逮到了：`verify_filter_engine_ch041` 从「全部通过」变成「10 项失败 ❌」。

修法：把默认密码抽成 `DEFAULT_PASSWORD` 单一常量，并新增 `current_password_version(admin_cfg)` 统一推导，`login` / `change_password` / `check_auth` 全部走它。

## 六、风险与说明

| 风险 | 说明 |
|---|---|
| **上线后所有已登录会话立刻失效一次** | 旧 token 无 `pv`，比对必然不通过。这是「改密即失效」的固有代价，一次性 |
| 任何不经 `/login` 裸签的 token 都会失效 | 生产只有 login 一条签发路径，无影响；测试脚本已改用 `make_admin_token()` |
| 改密后前端立即退出 | 用户改完密码要重新登录，符合安全预期，已在弹窗提示 |
