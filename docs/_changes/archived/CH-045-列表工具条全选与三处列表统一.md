## 三、关键决策

### 3.1 全选为什么放在工具条，而不是加在每个列表容器上

| 方案 | 评价 |
|---|---|
| 在 `ListPage` 里内置全选 | ❌ `ListPage` 不知道条目结构（可能是卡片，也可能是表格），无法判断怎么「全选」 |
| 在 `EntityCard` 里做「全选宿主」 | ❌ 卡片是被选对象，不该管全选 |
| **放在 `ListToolbar` 左侧（选此）** | ✅ 工具条本来就持有 `count` / `total`，是「选中态」的唯一展示位；全选框与「已选 N 项」在同一行，语义连贯 |

### 3.2 全选只作用于「当前页」

与 `el-table` 表头全选的行为保持一致 —— 表头全选也只勾当前页。实现上：

- 勾选：`selected = 去重(selected ∪ 当前页)` —— **不覆盖其它页已勾的项**；
- 取消：`selected = selected − 当前页` —— 也只减当前页。

### 3.3 半选态（indeterminate）必须做

只做「全选 / 未选」两态会让用户困惑：当前页勾了 3/10 时，全选框显示未选，一点反而变成全选。因此：

```
hit = 当前页已勾数
allChecked   = hit === 当前页总数 && 总数 > 0
indeterminate = 0 < hit < 当前页总数
```

### 3.4 上游源的批量操作用「启用/禁用/删除」

与 API Key 页对齐（都是「有实体生命周期的资源」）。删除走 `confirmDanger` 并提示「引用它的路由候选将失效」。

### 3.5 「聚合模型发现」与「聚合模型」结构完全对齐

第一版只换了 `ListPage` 外壳、传了 `pagination=false`，被用户指出「只改了名，没有用上我们新弄的组件」。修正为与聚合模型**逐项一致**：

| 部件 | 聚合模型 | 聚合模型发现 |
|---|---|---|
| 右上操作 | 刷新 / + 新建聚合 | 刷新 |
| 常驻工具条 | 共 N 条 · 已启用 X 个 + 批量启用/关闭/移除 | 共 N 条 + 批量合并 |
| 全选 | ✅ | ✅ |
| 条目 | `AggregationCard`（`selectable`） | `EntityCard`（`selectable`） |
| 卡片内成员 | `ChipFlow` 平铺 | `ChipFlow` 平铺 |
| 底部 | `TablePagination` | `TablePagination` |

对应的脚本也补齐：`suggPage` / `suggPageSize` / `pagedSuggestions` / `selectedSuggestions`（按 `normalized` 存）/ `allSuggChecked` / `suggIndeterminate` / `toggleAllSuggestions` / `batchMergeSuggestions`。

**批量合并**的语义：逐条调用 `saveModelGroup`（与单条「一键合并」同一套逻辑），逐条容错，失败的保留选中；成功后与最新列表求交集清掉已消失的项。

## 五、风险

| 风险 | 缓解 |
|---|---|
| 全选语义被误解为「全站全选」 | 全选框旁标注「全选」且位于工具条内（紧邻「共 N 条」），并在代码注释与小节 3.2 写明「只作用于当前页」 |
| 上游源加批量删除的破坏性 | 沿用 `confirmDanger`，文案明确「引用它们的路由候选将失效」，与单条删除一致 |
| 上游源卡片内部模型列表的批量选中与本级选中混淆 | 两级选中互相独立：卡片级勾选框在标题行（`EntityCard`），模型级全选在 `ModelList` 内部，作用域不同 |
