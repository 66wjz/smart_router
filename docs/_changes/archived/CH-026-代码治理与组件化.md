## 一、背景：审计发现的三类问题

用户提出「把特别长的文件合理拆分、检查是否都组件化了、可复用但没封装的就封装」。审计结果：

### 1.1 超长文件（前端）

| 文件 | 总行 | template | script | style | 问题 |
|---|---:|---:|---:|---:|---|
| `views/Aggregated.vue` | 1347 | ~500 | 643 | 287 | 3 个 tab-pane + **4 个弹窗** + 38 个顶层函数挤在一个文件 |
| `views/Upstreams.vue` | 1056 | ~300 | 579 | 236 | **4 个弹窗** + 33 个顶层函数；新增/修改两个表单 ~90% 重复 |

## 二、目标

1. 单文件行数：前端 view 主容器 ≤ 400 行，业务组件 ≤ 350 行；后端单文件 ≤ 500 行
2. 补齐高频重复模式的封装，并**实际落地替换**（不只是新建组件）
3. 硬编码色值归零（改用设计令牌）
4. **对外行为零变化**：API 契约不变、页面交互不变、构建产物功能等价

## 四、不做

- **不引入 `BaseTable` 全量替换 `el-table`**：`el-table` 有排序/固定列/合计/虚拟滚动，自研 `BaseTable` 功能不对等，全量替换有功能退化风险。本轮保持 `el-table`，`BaseTable` 标注为「新页面可选」。
- 不改任何 API 契约、数据库结构、路由逻辑
- 不引入新的状态管理或请求库
- 不动 CH-025 新增的日志/异常兜底链路

### 7.4 发现并修复的问题

**切分 `config.py` 时 `resolve_group_candidates` 丢失 `return result` 行**：按行号切分时该 `return` 恰好落在边界线上。由 `verify_api_ch023.py` 的「static 聚合解析出 N 个候选」用例捕获（FAIL 0 个候选），补回后通过。**这也是本轮坚持跑回归脚本的价值所在**——纯 AST 方法名比对发现不了，必须靠行为测试。
