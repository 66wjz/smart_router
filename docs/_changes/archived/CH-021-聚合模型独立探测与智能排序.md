# CH-021：聚合模型独立探测与智能排序

> 分类：B 线-大（新数据链路 + 调度改造）
> 流程：维护迭代模式 · 迷你 stage-1→5
> 日期：2026-10-17
> 状态：设计待用户确认（未动代码）

---

## 一、背景

CH-019/CH-020 让模型聚合从"黑盒自动发现"变成"可查看、可编辑、可控"。但聚合链路存在三个真实缺口：

| # | 缺口 | 现状 |
|---|---|---|
| 1 | 聚合成员不在探测清单 | `get_all_models()` 只收集「路由规则候选 + 别名目标」，上游源 `models` 里的聚合成员从不被探测 |
| 2 | 聚合链路不使用探测结果 | direct/新聚合走 `resolve_group_candidates`，严格按配置顺序，不查延迟与冷却 |
| 3 | 探测实为串行 | `probe_all` 用 `for ... await` 逐个执行，单元一多一轮跑不完 |

另有 2 个隐患：

| # | 隐患 | 说明 |
|---|---|---|
| 4 | 探测失败会把 Key 打进冷却 | 用户目前只有一个上游 Key，3 个模型同时超时 → 唯一 Key 冷却 120s → 期间所有真实请求失败 |
| 5 | 用量按"聚合名"记账 | `log_usage.model` 是客户端请求名，不是上游真实模型名，无法按「源 × 真实模型」核算号池消耗 |

---

## 二、目标

1. **每个聚合组自己管自己的探测**（开关 / 间隔 / 慢阈值 / 排序模式），互不影响。
2. **探测对象全局去重**：同一 `(上游源, 真实模型名)` 只探一次，不论被多少个聚合组引用。
3. **慢的往后排**，且全部不可用时仍按人工顺序兜底，不出现"无候选 503"。
4. **探测不再污染真实请求的 Key 冷却**（默认关闭，留开关）。
5. **把用量记到「源 × 真实模型」粒度**，为后续按号池积分配额自动关停（CH-022）打底。

### 已确认的决策（2026-10-17 用户拍板）

| # | 决策 |
|---|---|
| 1 | 探测配置用**独立表** `agg_probe_config`，不往 `agg_model_group` 加列（避免把自动发现组变成"已手动配置"） |
| 2 | 排序只做两档：`stable`（稳定优先）/ `latency`（速度优先） |
| 3 | 探测失败**不计入** Key 冷却，默认关，留全局开关 |
| 4 | 单元级单独开关本轮不做；先把「量」记准并展示，自动关停放 CH-022 |

## 三、核心设计：把「测什么」和「怎么排」拆开

这是本变更最重要的一条边界：

| 概念 | 归属 | 是否去重 | 决定什么 |
|---|---|---|---|
| **探测单元** `(upstream, real_model)` | 全局唯一 | ✅ 天然唯一 | 消耗多少上游额度 |
| **探测策略**（开关/间隔/慢阈值/排序） | 每个聚合组一条 | ❌ 各自独立 | 用不用这份数据、怎么排 |

聚合组**引用**单元，不**拥有**单元。因此：

- A 组开探测、B 组关探测 → 只影响 A/B 的排序；共享成员的探测次数不变（只要还有别的启用组引用）。
- 同一单元被多个启用组引用时，**间隔取最小值**（最严格的那个组需要新鲜数据，宽松的组多探几次不吃亏）。
- 没有被任何启用组引用、但被路由规则/别名命中的单元 → 走全局间隔 `latency_probe.interval_seconds`。

## 四、数据模型

### 4.1 新表 `agg_probe_config`

```sql
CREATE TABLE IF NOT EXISTS agg_probe_config (
    model TEXT PRIMARY KEY,                   -- 聚合名（组标识）
    enabled INTEGER NOT NULL DEFAULT 0,       -- 该组是否启用定时探测
    interval_seconds INTEGER,                 -- NULL = 跟随全局
    slow_threshold_seconds REAL,              -- NULL = 跟随全局
    sort_mode TEXT NOT NULL DEFAULT 'stable', -- stable | latency
    schedule TEXT NOT NULL DEFAULT '{}',      -- JSON：探测时段（见 4.2）
    updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

说明：

- 与 `agg_model_group` 完全解耦——**自动发现的聚合组也能有探测配置，且不会因此变成"已手动配置"**。
- 存"显式覆盖值"，`NULL` 表示跟随全局，避免全局参数调整后组配置变成死值。
- 优先级：`组配置` → `sys_setting.latency_probe` → 代码内置默认。
- **UI 用 0 表示"跟随全局"**：`el-input-number` 的 `min` 会强制填值，无法真正留空；后端把 0 归一化为 `NULL`。

### 4.2 探测时段 `schedule`（本次新增需求）

需求：不只是"每 N 秒"，还要能配"夜间不探测 / 周末不探测 / 只在工作时间探测"。

```json
{"mode": "always"}
{"mode": "window",
 "days": [1,2,3,4,5],
 "windows": [{"start":"08:00","end":"23:00"}]}
```

| 字段 | 含义 |
|---|---|
| `mode` | `always` 全天候；`window` 仅指定时段 |
| `days` | 1=周一 … 7=周日；**空数组 = 每天** |
| `windows` | 时段窗口列表；**空数组 = 全天**；`end < start` 表示跨夜（如 `23:00→07:00`） |

行为约定：

1. 时段外**不探测**，但不清空已有延迟数据；面板标记「时段外」，数据超过 `3 × interval` 未更新则标「数据陈旧」。
2. 同一单元被多个组引用时，**任一组处于探测时段即探测**（并集语义：最宽松的组决定这个单元能不能被探）。
3. 时间段配置解析失败一律回退 `always`（宁可多探，不要因写错完全不探）。
4. 全局 `latency_probe.schedule` 只作用于「路由规则 / 别名」命中的单元；聚合组各配各的。

前端提供三个快捷模板：工作日全天、每天 08:00-23:00、仅周末。

### 4.2 `log_usage` 补列

```sql
ALTER TABLE log_usage ADD COLUMN upstream_model TEXT;
CREATE INDEX IF NOT EXISTS idx_usage_unit ON log_usage(upstream_id, upstream_model, ts);
```

- 记录**实际命中的上游真实模型名**（异名聚合时与请求名不同）。
- 存量数据为 NULL：按单元统计时回退为请求名（避免整行被丢掉）。
- 启动时 `_ensure_unit_column()` 自动检测并补列（幂等），无需手工执行 SQL。

### 4.3 新增全局参数（`sys_setting.latency_probe` 扩展键）

| 键 | 默认 | 说明 |
|---|---|---|
| `max_concurrency` | 5 | 单轮并发探测数上限 |
| `count_key_failures` | false | 探测失败是否计入 Key 冷却（默认否） |

## 五、探测计划（去重算法）

新增 `AppConfig.collect_probe_plan()`，返回：

```python
{
  "buddy:deepseek-v4.1-flash": {
     "upstream": "buddy",
     "model": "deepseek-v4.1-flash",
     "interval": 60,
     "groups": ["deepseek-v4.1-flash"],
     "sources": ["group"]        # group / rule / pointer
  },
  ...
}
```

### 收集来源（三者并集）

| 来源 | 取法 |
|---|---|
| 路由规则候选 | 遍历 `rule_rule.candidates`，取 `(upstream, model)` |
| 别名目标 | `pointer.target_model` → `collect_model_upstreams(target)` |
| 聚合组成员 | 遍历 `list_model_groups()`（自动发现 + 人工配置），成员取 `(upstream, 该源真实模型名)` |

### 过滤规则

1. 跳过 `up_upstream.enabled = 0`
2. 跳过 `up_upstream.probe_enabled = 0`
3. 跳过 `models[].enabled = 0`（模型级禁用）
4. 上游无 Key 的单元仍保留（探测时会判 `no_key`，面板可见，便于排查）

### 间隔计算

```
intervals = [该组的 interval  for 组 in 引用它的组 if 组.probe_enabled]
interval  = min(intervals) if intervals else 全局 interval
```

> 全局探测总开关 `latency_probe.enabled = false` 时，只保留聚合组显式开启的单元；若连组也没开，则整体不探测（与现状一致）。

## 六、排序算法

新增 `LatencyProbe.sort_group_candidates(candidates, group_cfg)`，纯函数式，不改 `get_ordered_candidates` 的既有行为。

输入：`resolve_group_candidates()` 返回的成员列表（配置顺序）+ 该组的 `{sort_mode, slow_threshold_seconds}`。

### 分层

| 层 | 判定 | 排序 |
|---|---|---|
| T0 正常 | `status == ok` 且 `latency <= 慢阈值` 且不在冷却 | `stable` 保持配置顺序；`latency` 按延迟升序 |
| T1 偏慢/未知 | `status == ok` 但超慢阈值，或从未探测（latency=None） | `stable` 保持配置顺序；`latency` 按延迟升序（None 最后） |
| T2 不可用 | `status == down` 或 health 冷却中 | 保持配置顺序 |

### 兜底（关键）

> **全部候选落入 T2 时，直接返回配置顺序，照常发请求。**

理由：探测把 3 个成员全判 down（上游临时抖动）时，绝不能返回空候选导致 503——排错序远轻于不可用。

### 慢阈值

`group_cfg.slow_threshold_seconds` 为 `NULL` 时读全局 `probe_config.slow_threshold_seconds`（当前生产 10s）。

## 七、调度改造

### 7.1 从「全局定时」改为「按单元到期」

现状：`run_loop` 全局 `sleep(interval)`，一轮全量。

改后：

```
loop:
  plan = collect_probe_plan()            # 每轮重算，配置改动下一轮生效
  due  = [k for k in plan if next_due[k] <= now]
  results = await gather(probe_one(k) for k in due, semaphore=max_concurrency)
  for k in due: next_due[k] = now + plan[k].interval
  清理 plan 中已不存在的单元
  await sleep(1)
```

要点：

- 进程内记住 `_next_due`，不落库（重启后立刻全量探一次，可接受）。
- 单轮并发受 `max_concurrency` 限制（默认 5），避免对上游瞬时打爆。
- `probe_all` 保留为手动/兼容入口，内部改为 `gather`。

### 7.2 探测与 Key 冷却解耦

`probe_one` 中三处 `key_pool.record_fail()` 用 `count_key_failures` 包住（默认 false）。

- 探测仍会切换 Key 重试（保证探测自身能拿到结果）。
- 探测成功仍调用 `record_success`（清失败计数，无害）。
- 真实请求的失败计数逻辑完全不变。

### 7.3 时段调度

`_tick` 对每个单元先判 `probe_plan_active(item)`：

- 时段内 → 按 `_next_due` 正常到期探测
- 时段外 → 不探测，`_next_due` 推到 60s 后（回来时能较快恢复），**保留旧数据**

> 说明：`probe_plan_active` 的组语义是**并集**——单元被多个启用组引用时，只要有一组在时段内就探。
> 这与"间隔取最小值"的取向一致：新鲜度取最严格的需求，可探测性取最宽松的许可。

## 八、API 契约

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/api/model-groups` | 响应不变（组列表） |
| GET | `/admin/api/model-groups/probe-configs` | **新增**：所有组的探测配置 + 生效值（含继承结果） |
| PUT | `/admin/api/model-groups/probe?model=xxx` | **新增**：保存组探测配置 |
| DELETE | `/admin/api/model-groups/probe?model=xxx` | **新增**：恢复该组为默认（不探测） |
| GET | `/admin/api/model-groups/probe-plan` | **新增**：去重后的全局探测计划 + 成本汇总 |
| GET | `/admin/api/usage/by-unit?range=7d` | **新增**：按「源 × 真实模型」聚合用量 |

> 探测配置**不塞进** `GET /model-groups` 的响应，独立走 `probe-configs`。原因：一次页面加载两个请求可以并行，而把探测配置塞进组响应会让 `list_model_groups()` 这个纯展示函数依赖探测模块，耦合变差。

### PUT `/model-groups/probe` 请求体

```json
{
  "enabled": true,
  "interval_seconds": 60,
  "slow_threshold_seconds": 6,
  "sort_mode": "stable",
  "schedule": {"mode": "window", "days": [1,2,3,4,5],
               "windows": [{"start":"08:00","end":"23:00"}]}
}
```

校验：

| 字段 | 规则 |
|---|---|
| `interval_seconds` | `null` / `0` = 跟随全局；否则 ≥ 10 |
| `slow_threshold_seconds` | `null` / `0` = 跟随全局；否则 ≥ 1 |
| `sort_mode` | `stable` \| `latency` |
| `schedule.mode` | `always` \| `window` |
| `schedule.windows` | 每项 `start`/`end` 必须同时存在且不相同；支持跨夜 |
| `model` | 必须存在于当前聚合组列表，否则 404 |

### GET `/model-groups/probe-plan` 响应

```json
{
  "summary": {
    "unit_count": 12,
    "member_refs": 16,
    "dedup_saved": 4,
    "daily_requests": 17280,
    "global_interval": 360
  },
  "units": [
    {"key": "buddy:deepseek-v4.1-flash", "upstream": "buddy", "upstream_name": "Buddy",
     "model": "deepseek-v4.1-flash", "groups": ["deepseek-v4.1-flash"],
     "sources": ["group"], "interval": 60,
     "latency": 1.2, "status": "ok", "last_check": 1792228899,
     "stale": false, "active_now": true}
  ]
}
```

- `member_refs`：所有组的成员引用总数（含重复）
- `dedup_saved`：`member_refs - unit_count`，即省下的重复探测次数
- `daily_requests`：`Σ(86400 / interval)`，直观看到探测成本
- `active_now`：当前是否处于该单元的允许探测时段（前端据此标「时段外」）
- `stale`：`last_check` 超过 `3 × interval` 未更新

### GET `/usage/by-unit` 响应

```json
{"units": [
  {"upstream_id": "buddy", "upstream_name": "Buddy",
   "upstream_model": "deepseek-v4.1-flash",
   "requests": 320, "success_count": 318, "error_count": 2,
   "request_models": 3, "prompt_tokens": 900000, "completion_tokens": 350000,
   "total_tokens": 1250000, "avg_duration_ms": 2100, "last_ts": 1792228899}
]}
```

- `upstream_model`：`COALESCE(upstream_model, model)` —— 老数据没有真实模型名时回退请求名
- `request_models`：这一单元被多少个不同的客户端请求名命中过（异名聚合的关联度指标）
