## 一、迷你 stage-1：需求

### 1.1 背景

当前 Smart Router 是纯聊天中转，入站只有 `/v1/chat/completions`、`/v1/messages`、`/v1/responses`，
没有向量（Embedding）入口。服务器 `192.168.31.10` 已部署本地嵌入服务：

| 项目 | 值 |
|---|---|
| 服务 | `embedding-server.service`，监听 `127.0.0.1:8090` |
| 协议 | OpenAI 兼容（`POST /v1/embeddings`、`GET /v1/models`、`GET /health`） |
| 模型 | `bge-small-zh-v1.5`（对外模型名） |
| 维度 | 512 |
| 鉴权 | 当前未启用（可选 `EMBED_API_KEY`） |

目标：让中转站能像代理聊天模型一样代理向量模型，客户端用同一个 API Key、同一个地址，
把 `base_url` 指向中转站、模型名指向 `bge-small-zh-v1.5` 即可调用。

### 1.2 心智模型（铁律 6）

中转站新增「第二种请求形态」——聊天请求与向量请求共享同一套上游源、Key 池、分组权限
和用量记账，但**候选池按模型能力类型隔离**：

- 聊天端点只从 `chat` 类型模型组候选
- 向量端点只从 `embedding` 类型模型组候选

核心实体：

| 实体 | 说明 |
|---|---|
| 入站端点 | `/v1/chat/completions`（已有）、`/v1/embeddings`（新增），决定请求体形态 |
| 模型能力类型 | 每个已配置模型属于 `chat` 或 `embedding`，决定它能被哪个端点选中 |
| 上游源 + Key 池 | 已有实体，向量请求复用同一套选源、换 Key、重试 |
| 用量记录 | 已有实体，向量请求记一条 `protocol=embedding` 的用量（只有输入 token） |

关系：一个上游源 → 多个模型（每个带类型）→ 向量端点只从 embedding 模型组候选；
一次向量请求 → 一条用量记录。

### 1.3 本期范围

| 编号 | 功能点 | 用户故事 |
|---|---|---|
| R1 | 新增 `POST /v1/embeddings` | 作为客户端，我用中转站地址和 Key 调用向量接口，获得标准 OpenAI 格式的向量响应 |
| R2 | 模型类型标记 | 作为管理员，我能把某个已配置模型标为「向量模型」，它只被向量端点使用 |
| R3 | 聊天/向量候选隔离 | 作为运维，我希望聊天请求不会误选向量模型，向量请求也不会误选聊天模型 |
| R4 | Key 池与重试 | 作为运维，向量请求复用上游源的 Key 池；401/403/429/超时自动换 Key，失败可切同模型的其他源 |
| R5 | 用量记账 | 作为运维，我在用量页能看到 `protocol=embedding` 的请求，token 为上游返回的 prompt_tokens |
| R6 | 模型测试适配 | 作为管理员，我对向量模型点「测试」时，测试发的是嵌入请求，并显示维度 |
| R7 | 模型列表可见 | 作为客户端，`GET /v1/models` 能看到向量模型，并带 `type=embedding` 标识 |
| R8 | 探测隔离 | 作为运维，向量模型不参与聊天的延迟探测，避免被误判 down |

### 1.4 不在本期范围

- 向量模型聚合 / 跨模型故障转移（维度与语义空间不一致，会静默污染向量库）
- 向量模型延迟探测（可后续单独设计 embedding 探测）
- rerank / 多模态向量接口
- 向量维度校验、知识库重建工具
- 请求过滤引擎（Pre-flight）对向量请求的规则匹配
- 会话亲和（向量请求无会话概念，不钉住）

### 1.5 已确认决策

| 决策 | 结论 |
|---|---|
| 首个验证模型 | 服务器本地 `bge-small-zh-v1.5`（512 维，`127.0.0.1:8090`） |
| 类型标记方式 | 后台模型列表手动选择，默认 `chat`，向后兼容 |
| 模型列表可见性 | `/v1/models` 可见，附 `type` 字段 |
| 探测 | 向量模型不参与聊天探测 |
| 聚合 | 本期不做，向量端点遇到聚合名直接返回 400 |

## 二、迷你 stage-2：设计

### 2.1 数据模型

不新增表、不新增列。复用 `up_upstream.models` JSON 数组，在模型条目上增加可选字段：

```json
{"name": "bge-small-zh-v1.5", "type": "embedding", "enabled": true}
```

- `type` 取值 `chat` / `embedding`，缺省视为 `chat`
- `UpstreamRepository._parse_models` 必须保留 `type`（当前实现会丢弃未知字段）
- `ModelEntry` schema 增加 `type` 校验

### 2.2 API 契约

#### 新增：POST /v1/embeddings

请求（OpenAI 兼容，原样透传，除 `model` 外不改写）：

```json
{
  "model": "bge-small-zh-v1.5",
  "input": "文本" | ["文本1", "文本2"],
  "encoding_format": "float"
}
```

响应：上游标准 OpenAI 向量响应原样返回（`object=list` / `data[].embedding` / `usage.prompt_tokens`）。

错误：

| 状态码 | 场景 |
|---|---|
| 400 | 请求体非 JSON / 非对象 / 缺 model / 缺 input / 模型不是向量模型 / 用聚合名调向量 |
| 401 | 中转站 API Key 缺失或无效（中间件统一处理） |
| 403 | 该 Key 分组无权访问该上游源 |
| 503 | 所有候选均不可用（附尝试链） |

#### 修改：GET /v1/models

每条模型增加 `type` 字段：`chat` / `embedding`；指针按目标模型类型；聚合固定 `chat`。

#### 修改：POST /admin/api/upstreams/{id}/test

对 `type=embedding` 的模型自动改发嵌入请求，返回：

```json
{"ok": true, "content": "维度 512，向量长度 512", "dimension": 512}
```

### 2.4 路由规则（向量端点）

```
POST /v1/embeddings
  → 校验 API Key（中间件）
  → 校验 body.model / body.input
  → 别名指针？ target = 指针目标，校验类型必须是 embedding
  → 聚合名？ 直接 400（本期不支持）
  → 直连：collect_embedding_upstreams(model)（仅 type=embedding + 启用源 + 启用模型）
  → 分组校验（Key groups ∩ upstream groups）
  → 候选顺序：按上游源配置顺序（不探测、不权重、不亲和）
  → 逐个候选：Key 池轮询 + 401/403/429/超时换 Key + 5xx 智能重试
  → 成功：原样返回上游 JSON，附加 X-Served-By / X-Retry-Count
  → 失败：下一个候选；全失败 503
  → 用量：protocol=embedding，prompt_tokens 来自上游 usage，completion_tokens=0
```

### 2.5 前端改动

| 文件 | 改动 |
|---|---|
| `api/upstreams.ts` | `ModelEntry` 增加 `type`；测试返回增加 `dimension` |
| `composables/useUpstreamModels.ts` | 新增 `setModelType`；`setModelProtocol` 改为保留其余字段；测试弹窗显示维度 |
| `components/upstream/ModelList.vue` | 模型行增加「类型」下拉（对话 / 向量） |

### 2.6 兼容与边界

1. `base_url` 含 `/v1` 与不含 `/v1` 两种写法都要能拼出正确端点。
2. `input` 可以是字符串、字符串数组；不改写、不解析 `embedding` 数组。
3. 上游 200 但响应体是错误包 → 按失败处理（复用 CH-040 逻辑）。
4. 向量端点不做 `developer → system` 角色改写、不注入 `include_usage`、不处理流式。
5. 冷启动超时：默认 60s（高于聊天的 12s），可通过 `sys_setting.embedding_timeout_seconds` 覆盖。
6. 向量模型不出现在聊天候选，因此不会影响现有聊天链路。
