# CH-025：请求可观测性与入站健壮性（日志落文件 + 请求上下文 + 异常兜底）

> 分类：B 线-中（新增可观测性链路 + 三处入站行为修正）
> 流程：维护迭代模式 · A/B 混合（A：保存按钮卡死；B：复制交互 + 日志/兜底）
> 日期：2026-10-18
> 状态：已实现，本地验证通过
> 前序：CH-024（rule 聚合路由绑定）

---

## 一、背景

用户连续反馈三类问题：

1. **新建聚合点「保存」按钮永远显示「保存中」**，无法保存
2. **API Key 管理点「复制 Key」弹确认框**，希望直接复制 + 提示
3. **请求频繁中断**：客户端报 `WebSocket error: Network IO error ... (HTTP Status: 500)`，后又报 `Connection timeout (HTTP Status: 500) (4028)`

### 1.1 第 3 类问题的取证

连生产（10.10.0.2）取 journal 日志，结论：

| 事实 | 说明 |
|---|---|
| journald 持久化完好 | `/var/log/journal` 存在、`Storage=auto`，覆盖 9/21 至今；今早 09:57 重启后 boot -1 日志完整保留 |
| 500 只集中在 10-16 | 34 个 = CH-019 部署事故的 `TypeError: ModelHealth.record_success()`（FB-022 已修）；3 个 = `json.decoder.JSONDecodeError` |
| 10-18 当天 | 311×200 + 31×304，**0 个 500 / 0 个 Traceback** |
| 慢请求 | 2753 次转发中 **44 次 >60s**（最长 219s）；47 次「上游已返回但客户端未拿到响应」 |

**拿到的决定性问题**：`JSONDecodeError` 完整堆栈直指 `app/api/v1/chat.py:23 body = await request.json()`。

对照三个入站：

| 文件 | 请求体解析 |
|---|---|
| `messages.py` | ✅ 包 try → 规范 400 |
| `responses.py` | ✅ 包 try → 规范 400 |
| `chat.py` | ❌ **裸调用** → 非 JSON body 直接裸 500（无错误体） |

### 1.2 日志能力缺口

现有日志能回答「崩在哪一行」，但**不能回答「客户端发了什么」**——没有请求体、没有 model/stream、没有请求头。所以即使定位到 `chat.py:23`，也无法知道客户端到底发了什么才触发。

## 二、目标

1. 修掉前端「保存」按钮卡死（A 线 bug）
2. 复制 Key 改为直接复制 + 提示
3. 消灭入站裸 500：畸形请求返回规范 400，未捕获异常返回规范协议错误体
4. 补请求上下文日志并落文件（轮转），使下次同类问题可自证

## 三、改动内容

### 3.1 A 线：新建聚合保存按钮卡死

**根因**：按钮文案与禁用条件都用 `savingName === editName`。
- `savingName` 初值 `''`；[openCreate()](file:///e:/80-project_dev/04_smart-router/frontend/src/views/Aggregated.vue) 把 `editName` 也设为 `''`
- 新建弹窗一打开 → `'' === ''` 成立 → 按钮立即 `disabled` 且显示「保存中…」
- `savingName` 同时被列表卡片的启停/移除按钮复用，混用是根因

**修法**：编辑弹窗改用独立布尔 `savingEdit`，与列表卡片的 `savingName` 解耦。

### 3.2 B 线：复制 Key 去确认框

`showCopy()` 原来是 `ElMessageBox.confirm` 把完整 Key 显示在确认框里（同文件 `copyText()` 已是直接复制写法）。改为直接 `copyToClipboard` + `ElMessage.success`。

### 3.3 C1：入站请求体校验对齐

三个入站统一补齐：

```
body 解析失败            → 400 规范错误体
body 不是 JSON 对象      → 400「请求体必须是 JSON 对象」
model 缺失               → 400
messages 缺失/非数组     → 400（仅 chat）
```

### 3.4 C1b：`estimate_tokens` 真实崩溃点

`messages: null` 时 `body.get("messages", [])` 返回 `None`（默认值只管键缺失，不管显式 null）→ `for msg in None` → `TypeError` → 裸 500。

**这是线上真实存在的崩溃入口**，与历史 FB-010（`data.get("api_key", "")` 对显式 None 不生效）同一类坑。

修法：`estimate_tokens` / `extract_text` / `has_image` 三个函数补类型防御。

### 3.5 C2：全局异常兜底

`main.py` 注册 `@app.exception_handler(Exception)`：未捕获异常按入站协议路径返回规范化错误体（不再返回 FastAPI 默认纯文本 500），并记录含请求上下文的 ERROR 日志。

### 3.6 C3：请求上下文日志 + 落文件

新增 `core/logging_setup.py`：

- **文件日志**：`RotatingFileHandler` 写 `logs/smart-router.log`（10MB × 5 轮转），可用 `SMART_ROUTER_LOG_DIR` 覆盖
- **请求上下文中间件**（纯 ASGI，非 BaseHTTPMiddleware）：
  - 缓存 `/v1` 请求体 → 解析出 `model` / `stream` / `messages` 数量 → 存入 `scope["state"]`
  - 请求体非法时立刻 WARNING 并留摘要
  - 输出访问日志：`status / elapsed / client / model / stream / messages`，4xx/5xx 附请求体摘要
- **脱敏**：摘要中 `sk-xxxx...` 替换为 `sk-abcd****`
- **读取接口**：`GET /admin/api/logs`（尾部 N 行，可关键词过滤）、`GET /admin/api/logs/info`

## 六、遗留（未纳入本次）

**流式转发缺超时保护**：`try_stream` 的 `http_client.send()` 是裸调用（对比 `try_non_stream` 有 `asyncio.wait_for`）。首包有 `first_chunk_timeout=30s` 守着，但**等响应头这一步无超时**，直接落到 httpx 全局 300s。

证据：2753 次转发中 44 次 >60s、最长 219s；47 次「上游已返回但客户端未拿到」。与用户报的 `Connection timeout (500)` 疑似相关，**待用户确认后再改**。
