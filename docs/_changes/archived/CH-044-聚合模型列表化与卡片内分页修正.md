## 一、CH-043 做错的两件事

### 错误 1：仪表盘方向改反了

| 项 | CH-043 做法 | 实际后果 |
|---|---|---|
| `.two-col` | `align-items: start`（两栏各自独立） | 右栏（贡献占比）高时，左栏卡片停在 137px，下方露出一大片**灰色页面底** |
| 期望 | 左栏卡片跟着撑到和右栏一样高，空白落在**白色卡片内部** | —— |

**用户原话**：「右边那么高，左边的是不是应该至少补下来这么高，不然空着一块灰色的区域了。」

### 错误 2：分页的位置放错了

| 项 | CH-043 做法 | 问题 |
|---|---|---|
| 聚合成员分页 | 做进 `ChipFlow` 内部，每张卡片底部分别显示 `共 12 个 ‹ 1 2 ›` | 用户打叉处：**分页不属于卡片，属于列表** |
| 真正的结构 | 聚合模型页本身就是一个列表：顶部标题 + 右上批量操作、中间条目（形态是卡片）、**底部统一分页** | —— |

**用户原话**：「聚合模型，它本身就是一个列表，只是列表里面的卡片逻辑复杂一点……那个显示多少是在我图片右下角红框，不是你放到里面的卡片里，然后我在右上角说了批量操作的框。」

### 关于「列表组件能不能放卡片」的核查

| 组件 | 是否支持卡片条目 | 结论 |
|---|---|---|
| `DataTable` | ❌ 内部是 `el-table`，只能渲染表格行 | 不适用 |
| `ListPage` | ✅ 默认插槽接受**任意内容**，源码注释明确写了「不强制一定用 DataTable（默认插槽可以是卡片列表）」 | **本就支持，是 CH-043 没用对** |

## 三、关键决策

### 3.1 为什么移除拖拽排序

用户原话：「没有拖拽也行，一般的展示列表的好像也不太让拖拽移动位置（你自己分析需不需要留这个）。」

分析结论：**建议去掉**，三条理由：

1. **无功能职责**：它只决定纯展示顺序，架构设计 6.7 已写明「不参与路由决策」，去掉没有功能损失。
2. **与分页冲突且易误解**：加分页后只能拖「当页」，用户容易以为能全局排序，歧义大于收益。
3. **不是列表的通用形态**：标准展示型列表靠筛选 + 表头排序组织顺序，拖拽是特例不是通例。

保留后端接口，是因为「顺序」这个概念仍存在于数据层（老数据可能有自定义顺序），删接口属于破坏性变更且无收益。

### 3.2 分页归列表，卡片只负责展示

`ChipFlow.pager` 默认改成 `false`：

- **卡片作为列表条目时**（聚合模型 / 疑似同一模型 / 仪表盘聚合组）→ 平铺全部成员，分页交给外层列表。
- 只有当某处确实需要「组件内自带翻页」时才显式传 `pager`，目前没有调用方这么用。

这样避免了同一页面出现「列表分页 + 卡片内分页」两套页码。

### 3.3 选中按业务键存，不按行对象存

`selectedAggs` 存的是聚合名数组（而非行对象）：

- 批量操作后重新拉取数据，行对象全是新引用，按对象比对必然失效；
- 按名字存则天然稳定，只需在操作后与最新列表**求交集**，清掉已消失的项即可（与 API Key 页 `setSelection` 同思路）。

## 五、风险

| 风险 | 缓解 |
|---|---|
| 去掉拖拽后用户想调顺序 | 顺序仍可通过后端接口调整；若后续确有需求，可改成「表格列排序」而非拖拽 |
| `ChipFlow.pager` 默认值变更影响既有调用 | 既有 3 处调用（聚合卡 / 疑似合并 / 仪表盘）本就不需要内部分页，行为符合预期 |
| 卡片内成员极多时卡片很高 | 分页放在列表层后，单个聚合的成员数通常有限；若出现超大成员集，再评估「卡片内折叠」 |
