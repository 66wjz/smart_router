# CH-034 聚合模型独立分组（聚合作为权限门面）

> 类型：B 线-大（权限语义变更，影响路由 / 模型列表 / 聚合配置 / 前端）
> 状态：已实现，已部署生产 10.10.0.2（2026-10-18），门面语义生产实测通过
> 日期：2026-10-18
> 来源：需求规格 9.2「聚合模型独立分组」，由「暂不实现」转为「实现」

---

## 一、背景与现象

用户在客户端调用聚合模型时收到：

```
{"error":{"message":"API Key 无权访问分组 ['no_single_use']（模型 buddy/hy4-preview）",
          "type":"api_error","code":403}}
```

聚合名本身能拉到（`/v1/models` 有），但一用就 403。

### 根因

`_check_group()` 是**成员级**权限校验：

```python
upstream_groups = self.config.get_upstream_groups(upstream_id)
if key_groups is not None and upstream_groups.isdisjoint(key_groups):
    raise HTTPException(403, f"API Key 无权访问分组 ...")
```

而 `agg_unified` 表**没有 `groups` 字段**，聚合名不具备任何权限属性。所以：

- static 聚合：`_resolve_candidates()` 在 direct 分支对**每个候选**调 `_check_group()`，任何成员所属上游源的分组与 Key 无交集 → 该候选被跳过；全部被跳过 → 403
- rule 聚合：`get_ordered_candidates(allowed_groups=key_groups)` 在 `router_engine.py` 里按上游源分组过滤候选，结果同上

本质是**设计缺陷**：聚合是「对外门面」，但权限被门面内部的成员决定。用户把分源统一放进 `no_single_use` 分组（禁止单独调用），结果聚合也跟着不可用——聚合的编排能力被成员的权限配置绑架。

---

## 二、分类（铁律 7）

**B 线-大**。不是代码没按设计实现，而是原设计本身缺了这一层语义：聚合缺 `groups` 字段，权限被错误地继承自成员。需要新增数据字段 + 改路由权限语义 + 改模型列表过滤 + 前端配置入口。

---

## 三、设计决策（用户已确认）

| 项 | 决策 |
|---|---|
| 校验位置 | **只在聚合上校验**，成员分组彻底不参与（真正的门面语义） |
| 适用范围 | **static 与 rule 一视同仁**，都按聚合自身 `groups` 判断 |
| 空分组语义 | `groups` 为空 / 未配置 → **所有 Key 可用**（兼容现状，不破坏已有客户端） |
| 原有过滤保留 | 上游源禁用、模型级禁用、候选全部不可用仍按原逻辑处理（这些是可用性，不是权限） |

### 语义对照

| Key 分组 | 聚合 groups | 结果 |
|---|---|---|
| `free` | `[]`（空） | ✅ 可用（所有 Key 可用） |
| `free` | `["free"]` | ✅ 可用 |
| `free` | `["premium"]` | ❌ 403 聚合无权 |
| `free`,`premium` | `["premium"]` | ✅ 可用 |
| `free` | `["premium"]`，成员全在 `no_single_use` | ✅ **可用**（成员分组不再生效，这是本次核心） |

## 四、改动清单

### 4.1 数据层

**新增** `sql/increment/09_增量_20261018_聚合分组.sql`：

```sql
ALTER TABLE agg_unified ADD COLUMN groups TEXT;
```

幂等：重复执行报 `duplicate column`，由 `sync_unified_tables()` 的容错逻辑忽略（与 08 同款处理）。

**存量数据**：全部留 `NULL`（= 所有 Key 可用），升级后行为不变。

### 4.2 仓储层

`backend/app/repositories/aggregation_repo.py`：

- `list_all()` SELECT 增加 `groups`，解析为 `list[str]`（空 / 非法 → `[]`）
- `upsert()` 写入 `groups`（JSON 数组字符串，空则 `NULL`）

### 4.3 配置层

`backend/app/core/config_aggregation.py`：

- `save_aggregation()` / `save_model_group()` / `save_probe_config()` / `delete_probe_config()` / `delete_aggregation()` 的 upsert payload 带上 `groups`，避免部分更新把分组冲掉
- 新增 `get_aggregation_groups(name) -> set[str]`：返回聚合分组集合；聚合不存在或 `groups` 为空时返回 `set()`
- 新增 `is_static_aggregation(name) -> bool`：**只有显式配置过的聚合**（`agg_unified` 有行且 `kind=static`，或旧视图 `_model_groups` 有行）才返回 True

> **实施中的修正**：初版还让「自动发现聚合」（`collect_group_members()` 推导）也算门面，单测立刻暴露漏洞——同名模型横跨多源时会被静默放宽为「任何 Key 可用」，绕过 `no_single_use` 保护。改为只认显式配置，用户想让某聚合成为门面，在聚合页保存一次即可落库。

`backend/app/core/config_aggregation.py` 的 `sync_unified_tables()`：

- 脚本清单追加 `09_增量_20261018_聚合分组.sql`（启动时幂等补列）

`backend/app/api/admin/groups.py`：

- 删除分组的引用校验纳入聚合：`agg_unified.groups` 里出现的分组名也算「被引用」

`backend/seed.py`：

- `SQL_FILES` 追加 09

### 4.4 路由层

`backend/app/services/router_service.py`：

新增 `_check_aggregation_group(name, key_groups)`：

```python
def _check_aggregation_group(self, agg_name: str, key_groups: set[str] | None) -> None:
    """聚合级权限：只看聚合自身 groups；空 = 所有 Key 可用（CH-034）"""
    if key_groups is None:
        return
    agg_groups = self.config.get_aggregation_groups(agg_name)
    if agg_groups and agg_groups.isdisjoint(key_groups):
        raise HTTPException(403, f"API Key 无权访问聚合 {agg_name}（该聚合分组 {sorted(agg_groups)}）")
```

`_resolve_candidates()` 三处调整：

1. **rule 聚合分支**：先 `_check_aggregation_group(model_name, key_groups)`，再 `get_ordered_candidates(..., allowed_groups=None)` —— 传 `None` 让成员分组不再过滤
2. **static 直连分支**：若 `model_name` 是已配置的 static 聚合（在 `get_aggregations()` 且 `kind=static`），先 `_check_aggregation_group`，再 `resolve_group_candidates()` 且**跳过逐候选 `_check_group`**
3. **普通模型直连**（非聚合）：保持原样，逐候选 `_check_group`

判定「是否 static 聚合」用一个明确的辅助方法，避免与「同名真实模型」混淆：

```python
# config_aggregation.py
def is_static_aggregation(self, name: str) -> bool:
    entity = self._aggregations.get(name)
    return entity is not None and entity.get("kind") == "static"
```

**优先级**：别名（pointer）优先级不变，仍最前。别名指向聚合名的情况本次不特殊处理（别名本身已有 upstream 绑定）。

### 4.5 模型列表

`backend/app/api/v1/models.py`：

- rule 聚合条目：`cfg.get_aggregation_groups(name)` 非空且与 `key_groups` 无交集 → 跳过
- static 聚合条目：同上
- 真实模型条目：不变（仍按上游源分组过滤）

### 4.6 前端

- `frontend/src/api/aggregations.ts`：`Aggregation` 接口加 `groups: string[]`
- `frontend/src/components/aggregation/AggregationEditModal.vue`：新增「可用分组」多选（不选 = 所有 Key 可用）
- `frontend/src/views/Aggregated.vue`：加载分组列表、传入弹窗、保存时提交 `groups`
- `frontend/src/components/aggregation/AggregationCard.vue`：显示分组徽标（空则显示「所有分组可用」）
- 提示文案：「聚合分组决定哪些 Key 能用；成员所属分组不再参与校验」

## 六、验收标准

1. **static 聚合**：聚合 `groups=[]`，成员全在 Key 无权访问的分组 → 请求聚合名 **200**
2. **static 聚合收紧**：聚合 `groups=["premium"]`，`free` Key 请求 → **403**，错误文案指向聚合而非成员
3. **rule 聚合**：同上两条全部成立（与 static 行为一致）
4. **空分组兼容**：升级后存量聚合（`groups=NULL`）行为与升级前**完全一致**
5. **模型列表**：`groups=["premium"]` 的聚合不出现在 `free` Key 的 `/v1/models` 中
6. **普通模型不受影响**：直接请求真实模型名时，成员级分组校验照旧（`no_single_use` 分组仍然拦住单模型调用）
7. **分组删除保护**：被聚合引用的分组不能直接删除
8. **回归**：`verify_api_ch023` / `verify_rule_binding_ch024` / `verify_aggregation_ch023` 全通过
9. **编译**：`compileall` 0 错误；前端 `npm run build` 通过

## 七、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 聚合分组配得过宽 | `free` Key 可用到 `premium` 上游的真实额度 | 属用户明确取舍；UI 必须提示「聚合分组决定谁能用，成员分组不再生效」 |
| 存量聚合误配 | 升级后行为突变 | 存量一律 `NULL` = 全部可用，不改任何既有权限 |
| `save_probe_config` 等部分更新丢字段 | 分组被清空 | 所有 upsert payload 显式带 `groups`；加单测覆盖 |
| 同名真实模型与 static 聚合混淆 | 普通模型被误判为聚合 | 用 `is_static_aggregation()` 精确判定（查 `agg_unified` + `kind`） |

回退：`git revert` 本次提交；数据库新增列不影响旧代码（旧代码不 SELECT 该列）。
