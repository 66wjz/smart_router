# CH-037 出站消息角色规范化（developer → system）

> 类型：A 线（bug）——客户端合法请求被上游兼容性拒绝，且无降级路径
> 状态：已实现，本地验证通过，**未部署**（用户要求避免中断当前会话）
> 日期：2026-10-19
> 来源：DSH 通过网关接入后全部请求 503，日志显示三成员全部 HTTP 400

---

## 一、现象

用户将中转站接入 DSH 后，所有消息报错：

```
503: {"message":"所有模型均不可用 (尝试了: buddy/deepseek-v4.1-flash@buddy,
       loomy/DeepSeek-V4.1-Flash@loomy, trae/deepseek-v4.1-flash@trae)",
      "type":"api_error","code":503}
```

但同一中转站在其他客户端（包括当前对话链路）完全正常。

## 二、定位过程与证据

**日志侧**（生产 `logs/smart-router.log`）：

| 请求来源 | messages 数 | 首条消息角色 | 结果 |
|---|---|---|---|
| DSH 接入 | 16 / 17 / 19 | `developer` | 三成员全 400 → 503 |
| 当前对话链路 | 612~617 | 无 developer | 200 |
| 网页手动测试 | 1 | `user` | 200 |

**上游侧**（生产直连号池 `127.0.0.1:8326`，`max_tokens=1`）：

```
[system        ] -> 200 OK
[developer     ] -> 400  {"error":{"message":"unsupported message role: developer",
                                   "type":"invalid_request_error","code":"invalid_request"}}
[developer-非流式] -> 400  同上
```

**排除项**（以下参数单独测试全部 200，均非诱因）：
`max_completion_tokens`、`parallel_tool_calls`、`tools=[]`、`reasoning_effort`、
`stream_options.include_usage`、流式/非流式。

### 根因

`developer` 是 OpenAI 后期引入的角色，**语义等价于 `system`**（旧名）。当前号池的实现只认 `system`，遇到 `developer` 直接 400。

DSH 把它放在**首条消息**，因此：

1. 每个候选成员都必然 400（三个成员共用同一号池，缺陷相同）
2. 返回的是 400（不可重试类），每个成员只试一次
3. 三个成员耗尽 → 503「所有模型均不可用」
4. 连续失败还会触发每个模型 120 秒冷却，进一步放大故障窗口

### 用户补充的关键背景

号池本身也是 DSH 的一个插件。该插件对内可用，但通过它自己的对外网关暴露后，其他 DSH 实例发来的新格式请求就落到了它不支持的路径上。**这不是本仓库引入的问题，但中转站作为网关应当兜住。**

## 三、分类（铁律 7）

**A 线（bug）**。客户端发送的是合法 OpenAI 请求，网关因上游兼容性缺陷导致全链路失败，且没有任何降级路径。不是设计调整——不涉及需求或架构变更。

## 四、方案（用户已批准 A）

在**出站适配器**统一把 `developer` 规范化为 `system`。

### 4.1 为什么放在出站适配器

`openai_adapter.py` 是三个入站协议（`/v1/chat/completions`、`/v1/messages`、`/v1/responses`）最终的转发出口，在此处改写可一次性覆盖所有路径，且不影响：

- 入站校验与错误格式
- 路由/聚合/探测
- 用量统计里记录的**客户端原始 model 名**
- 响应回传给客户端的内容

### 4.2 具体改动

**`backend/app/upstream/openai_adapter.py`**

1. 新增 `_normalize_messages(body: dict) -> None`
   - 遍历 `body["messages"]`，把 `role == "developer"` 就地改为 `"system"`
   - 非 list / 非 dict 一律跳过（防御畸形请求）
   - 只改角色，不动 content 与顺序

2. 在三个发请求的位置调用（都在 `modified = copy.deepcopy(body)` 之后）：
   - `try_non_stream()` —— 非流式转发
   - `try_stream()` —— 流式转发
   - `test_non_stream()` —— 管理端单模型测试（保持与真实链路一致）

3. 顺带补日志：非 200 且不可重试时，把上游响应体摘要写进 warning
   （当前只记 `HTTP 400`，导致本次排查必须直连号池才能看到真实原因）

> 三个调用点都在 `copy.deepcopy` 之后的副本上操作，**不会污染调用方的 body**。

### 4.3 不做的事

- 不改入站层（客户端发什么，我们照收；只在出站前适配）
- 不改 anthropic / responses 适配器（各自有自己的消息构造逻辑，且它们的入站已做角色映射）
- 不做双向映射（不把 `system` 改成 developer；没有上游需要）
- 不处理其它潜在新角色（如 `critic`、`tool` 变体）——无证据，不猜测

## 六、验收标准

1. **核心**：带 `role: "developer"` 的请求经中转站转发 → 上游收到 `role: "system"` → 返回 200
2. **流式/非流式**均通过
3. **真实模型名直连**与**聚合名**两条路径均通过
4. **不污染入站**：同一次请求里，若客户端还带了 `user`/`assistant`/`tool` 消息，角色保持不变
5. **多角色顺序**：`developer` 转 `system` 后，消息顺序与内容完全一致
6. **回归**：无 developer 的普通请求行为不变（现有三套 CH-023/024 回归 + CH-034/036 两套）
7. **管理端测试接口**同样能测通带 developer 的请求
8. `compileall` 0 错误

## 六之二、验证结果（2026-10-19）

| 层级 | 脚本 | 结果 |
|---|---|---|
| 单元 | `test/verify_role_normalize_ch037.py` | 11 项全通过 |
| 集成（mock 上游） | 同上 | 非流式 / 流式聚合名 / 无 developer 透传，全通过 |
| **真实端到端** | `test/verify_e2e_ch037.py` | **全通过** |

真实端到端链路：`脚本 → 本地 smart-router(10197) → 本机 DSH 网关(8326)`，使用真实网关 Key 与真实模型 `commandgo/deepseek/deepseek-v4.1-flash`：

```
[0] 基线：直连网关发 developer     -> 400  unsupported message role: developer
[2] 经中转站：system               -> 200
[3] 经中转站：developer（非流式）   -> 200   ✅ 修复目标
[4] 经中转站：developer（流式）     -> 200
[5] 服务日志                       -> 无 role 不支持错误
```

结论：缺陷在真实网关上可复现（400），经中转站转发后消失（200），修复真实生效。

> 说明：本机网关与生产号池是同一实现，因此该结论可直接迁移到生产；未做生产部署验证是因为用户要求避免重启中断会话。

## 七、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 某些上游**真的**区分 developer 与 system | 极少数，语义本就等价 | 若出现，可按上游源加开关（本次不做，避免过度设计） |
| 改写误伤正常请求 | 严重 | 只在 `role == "developer"` 时改写，条件极窄；单测覆盖 |
| 日志补响应体导致日志膨胀 | 轻微 | 截断到 200 字 |

回退：`git revert`。改动集中在单文件，回退零副作用。
