# CH-041 请求过滤引擎（Pre-flight Filter）

> 类型：B 线-大（新功能 —— 新增模块 + 新数据链路 + 前端配置页）
> 状态：已实现 + 本地验证 43 项通过 + 回归 6 套通过 + **已随 v5.2.3 部署生产**（2026-10-21 10:56，备份 `backup/20261021-105506`）
> 日期：2026-10-21
> 来源：用户提问「如果别人一直用 DSH 调 buddy，号池会不会封号？能不能配置过滤，发现命中就不发给 buddy，并回执提示」
> FB 编号：FB-033

---

## 一、要解决什么问题

### 1.1 现状

WorkBuddy/buddy 渠道按 **system 消息首行精确匹配** 维护非官方 agent 客户端黑名单（CH-040 已实测确认）：

```
You are an AI agent powered by DeepSeek Harness.   → 拦截
You are Claude Code, Anthropic's official CLI...   → 拦截
```

命中后上游返回 `200 + {"error":..., "choices":[]}`。

CH-040 已经能识别这种软失败并切换候选，**但请求已经发出去了**：

| | CH-040（现有） | 本变更（新增） |
|---|---|---|
| 时机 | 请求**已发送** | 请求**未发送** |
| 号池违规计数 | **+1** | **0** |
| 作用 | 失败后恢复 | 不产生失败 |

### 1.2 风险

12 个上游源（dsh / buddy / loomy / trae / accio …）**共用同一把 Key、同一个网关**。因此拦截记录很可能挂在**账号**上，而非渠道上。持续命中 → 违规计数累积 → 可能影响**全部 12 个源**。

CH-040 是兜底，不是防护。本变更补上防护。

### 1.3 目标

在转发之前就判断「这个请求发到某个上游注定会被拦」，直接跳过该上游，**不产生任何上游请求**。

## 二、需求确认（迷你 stage-1）

### 2.1 用户已确认的决策

| 问题 | 用户决策 |
|---|---|
| 聚合模型命中时怎么处理？ | **静默切到下一个成员（方案 A）**——聚合就应该让用户无感 |
| 单模型直连命中时怎么处理？ | **拦截并返回明确提示**——让用户知道为什么 |
| 是否要把 buddy 从聚合移除？ | **不需要**，buddy 速度最快，保留 |
| 规则作用范围？ | **全局，所有使用者生效，不依赖客户端配合** |

### 2.2 行为契约

| 场景 | 行为 |
|---|---|
| 聚合请求，成员 A 命中规则 | 静默跳过 A，试成员 B；**不返回任何提示给客户端** |
| 聚合请求，全部成员都命中 | 503 + 明确说明「全部候选被过滤规则拦截，列出规则名与被过滤的源」 |
| 单模型直连（如 `buddy/deepseek-v4.1-flash`），命中规则 | **400** + 明确说明「该请求命中过滤规则《规则名》，已阻止发送到 X」 |
| 未命中任何规则 | 行为完全不变（零影响） |
| 规则表为空 / 引擎关闭 | 行为完全不变（零影响） |

### 2.3 已确认的实施细节

| 项 | 决策 |
|---|---|
| 规则表初始内容 | **预置 DSH + Claude Code 两条，`enabled=0`（不生效）**，用户在界面上手动开启 |
| 单模型直连命中返回码 | **400**（请求内容不符合该上游要求，非权限问题） |
| 拦截记录展示 | **用量页可见**：新增「已过滤」筛选项 + 统计，不能只埋在日志里 |

### 2.4 不在本次范围

- 不做「按客户端 UA/IP 过滤」（与本次内容过滤无关）
- 不做「自动学习规则」（人工配置）
- 不改 DSH 侧任何配置

## 三、设计（迷你 stage-2）

### 3.1 核心流程

```
chat_completions()
  ↓
_resolve_candidates() → candidates + mode（aggregated / direct / pointer）
  ↓
【新增】filter_engine.apply(candidates, body, mode)
  ├─ 规则表为空 / 全局开关关闭 → 原样返回（零开销）
  ├─ 逐候选判断：该 upstream 是否命中任一规则？
  │    ├─ 未命中 → 保留
  │    └─ 命中   → 剔除，记入 filtered[]
  ↓
按 mode 决定：
  ├─ aggregated（聚合）且还有剩余候选 → 静默用剩余候选继续 _forward
  ├─ aggregated 且全部被过滤          → 503 + 明细
  ├─ direct / pointer 且命中           → 400 + 明细（不回退到别的源）
  └─ 无命中                            → 原样 _forward
  ↓
_forward()  ← 签名不变，只是候选变少
```

**关键约束**：过滤发生在 `_forward()` **之前**，所以不会产生任何上游请求。

### 3.2 数据表

新增 `filter_rule` 表（增量 SQL 12）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT | 规则名，如「DSH 身份声明」 |
| `enabled` | INTEGER | 1/0 |
| `target` | TEXT | 匹配位置：`system_first_line` / `system_any` / `body_regex` |
| `pattern` | TEXT | 匹配内容（`system_*` 用字面包含；`body_regex` 用正则） |
| `upstream_ids` | TEXT | JSON 数组，空/null = 作用于全部上游源 |
| `action` | TEXT | `skip`（跳过）/ `reject`（直接拒绝） |
| `remark` | TEXT | 备注 |
| `created_at` / `updated_at` | TEXT | |

**全局开关**：复用 `sys_setting`，键 `filter_engine_enabled`，默认 `false`（安全默认，不改变现有行为）。

### 3.3 匹配实现

```python
def _extract_system_text(body) -> str:
    """取 messages[0] 的 system 内容"""
```

只取**位置 0** 的 system 消息，与网关的判定方式保持一致（CH-040 实测：网关就是匹配位置 0）。

匹配方式分两档：

| target | 判定 |
|---|---|
| `system_first_line` | 字面包含 `pattern`（子串匹配，避免大小写/标点差异误判） |
| `system_any` | 遍历所有 system 消息，任一包含即命中 |
| `body_regex` | 对 `json.dumps(body)` 跑正则 |

**为什么默认用子串而不是精确相等**：CH-040 实测显示只要内容里出现那串特征就能被拦（前置空格/换行都不影响网关判定，但网关要求位置 0）。用子串更宽松、更安全——宁可多拦，不要漏拦。

### 3.4 API 契约（新增）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/api/filter-rules` | 规则列表 |
| POST | `/admin/api/filter-rules` | 新建规则 |
| PUT | `/admin/api/filter-rules/{id}` | 修改规则 |
| DELETE | `/admin/api/filter-rules/{id}` | 删除规则 |
| GET | `/admin/api/filter-rules/test` | 试跑：传入请求体，返回会命中哪些规则 |

**「试跑」端点很重要**：规则写错会误伤正常流量。让用户先拿真实请求体验证，再启用。

### 3.5 可观测性

复用 CH-038 的详情机制：

- 在 `log_usage.error_msg` 记 `被过滤规则拦截: 规则X`
- 在尝试链（`attempts`）中追加一条，`http_status=None`、`error="被规则X过滤（未发送）"`
- 用量表新增 `filtered` 计数（可选，或直接看 `error_msg` 前缀）

### 3.6 前端

新增「请求过滤」页（或并入「系统设置」）：

- 规则列表（名称 / 目标位置 / 匹配内容 / 作用源 / 动作 / 启用开关）
- 新建/编辑弹窗
- **试跑面板**：粘贴一段请求体 → 显示命中结果

### 5.1 实现过程中发现并修正的两处判断

**① static 聚合与 direct 的语义差异**（重要）

`_resolve_candidates()` 原本对 static 聚合也返回 `"direct"`。但 static 聚合是**聚合门面**——多个成员可互相替代，命中过滤应静默换成员；而真正直连（用户点名某模型）命中后不能偷偷换源。

修正：static 聚合返回 `"static_agg"`，过滤逻辑按 `route_mode in ("aggregated", "static_agg")` 判定聚合语义。

> 这个 bug 是测试逼出来的：第一版把 `shared-model`（同名模型分布在两源，但 `auto_same_name_aggregate` 默认关闭）当成聚合，结果走了 direct 分支返回 400。**同名 ≠ 聚合**，只有 `agg_unified` 行才是门面。

**② 过滤必须在 tracker 之后执行**

初版把过滤放在 `_apply_filter` 之前创建 tracker，导致被拦请求根本不进用量表——与用户「用量页要能看到」的要求冲突。修正为先建 tracker、再过滤，命中时 `finish_error("【已过滤】...")` 落库。

## 六、风险与缓解

| 风险 | 缓解 |
|---|---|
| 规则写错误伤正常流量 | ① 全局开关默认关；② 试跑端点；③ 规则按源限定 |
| 每个请求多一次判断开销 | 规则表为空或开关关闭时**直接短路返回**，零开销；规则数量有限（个位数），子串匹配是微秒级 |
| 过滤后候选变少，可能 503 | 这是正确行为——比发出去被拦更好；503 消息里明确说明原因 |
| 上游行为变化（黑名单更新） | 规则是配置项，不改代码即可调整 |
