# CH-038 请求详情可观测性与断连记录

> 类型：B 线-中（新增数据表 + 新接口 + 前端详情页 + 日志增强）
> 状态：已实现，本地验证 48 项全通过 + 回归 7 套通过 + `npm run build` 通过；未 push 未部署
> 日期：2026-10-19
> 来源：用户反馈「Trae 21:54 报 500，但中转站日志查不到」，并参考同类产品的流量日志交互（列表 → 点进详情）

---

## 一、背景

### 1.1 本次排查暴露的两个问题

用户 21:54 左右在 Trae 里遇到：

```
WebSocket error: Network IO error: error sending request for url
(http://10.10.0.2:10002/v1/chat/completions) (HTTP Status: 500) (4028)
```

但查中转站日志，**21:53~21:56 全是 200，全天 500 计数为 0**，进程 `NRestarts=0` 未重启。

**结论**：这条请求**没有到达应用层**（连 uvicorn 的 access 记录都没有）。所以不是"我们故意不回"，也不是服务端 500——是客户端在**建连/发送阶段**就失败了（`error sending request` 这个措辞即指发送前）。

### 1.2 但这暴露了我们的观测盲区

| 盲区 | 说明 |
|---|---|
| **A. 断连无记录** | 请求已到达、客户端中途断开（未走到响应开始）时，当前中间件不发 access 日志 → 看起来"没来过" |
| **B. 无请求详情** | 只有一行摘要（model / stream / messages 数 / 前 300 字片段），看不到完整请求体、看不到实际转发给上游的报文、看不到上游响应体 |
| **C. Token 维度不足** | 只记 prompt / completion / total，没有**缓存命中**（cache_read / cache_write）——而这在长上下文场景是主要成本来源 |
| **D. 重试不可见** | 一次请求试过哪几个候选、各自失败原因与耗时，只在日志里散落，用量表看不到 |

### 1.3 参考交互（用户提供截图）

- **列表页**：状态 / 方法 / 模型 / 协议 / 账号 / 路径 / Token 消耗（输入·缓存·输出）/ 耗时 / 时间
- **详情页**：三栏并列 —— **REQUEST（原始请求） / FORWARDED（实际转发） / RESPONSE（上游响应）** + Token 明细 + 耗时

其中 **FORWARDED 这一栏最有价值**：它能直接看出网关对请求做了什么改写（模型替换、`max_tokens` 裁剪、`developer → system` 等）。

## 二、分类（铁律 7）

| 项 | 分类 | 说明 |
|---|---|---|
| 断连无记录 | **A 线**（可观测性缺陷） | 请求确实到达却无任何痕迹，属实现遗漏 |
| 请求详情 / token 维度 / 重试链 | **B 线-中** | 新增能力，涉及表结构、接口、前端 |

本变更两项一起做（同属一条观测链路）。

## 三、先明确一个无法解决的边界

> **TCP/连接建立阶段就失败的请求，服务端物理上收不到任何字节，任何日志方案都记不到。**

本次 Trae 的报错正属此类（`error sending request`）。因此：

- 本变更能把「已到达但中途断开」补上（A 线部分）
- 「压根没发出来」的场景只能靠**客户端侧日志**闭环 —— 客服/排查话术需要如实说明

这一点会写进文档与 UI 提示，避免下次再被误判成"网关丢日志"。

## 四、设计

### 4.1 数据层

#### 4.1.1 主表补字段（`log_usage`）

```sql
ALTER TABLE log_usage ADD COLUMN cache_read_tokens  INTEGER DEFAULT 0;
ALTER TABLE log_usage ADD COLUMN cache_write_tokens INTEGER DEFAULT 0;
ALTER TABLE log_usage ADD COLUMN attempt_count      INTEGER DEFAULT 1;
```

- `cache_*` 从上游 `usage` 里取，兼容多种命名：
  - `prompt_tokens_details.cached_tokens`（OpenAI 新版）
  - `cache_read_input_tokens`（Anthropic 风格）
  - 取不到则 0，不估算（缓存命中无法靠字符数估算）
- `attempt_count`：本次请求实际尝试了几个候选（1 = 一次成功）

#### 4.1.2 新表 `log_usage_detail`（与主表 1:1，可缺行）

```sql
CREATE TABLE IF NOT EXISTS log_usage_detail (
    log_id          INTEGER PRIMARY KEY,   -- 对应 log_usage.id
    request_headers TEXT,                  -- 入站请求头（已脱敏）
    request_body    TEXT,                  -- 客户端原始请求体
    forward_body    TEXT,                  -- 实际发给上游的请求体
    response_body   TEXT,                  -- 上游响应体（流式存首尾摘要）
    attempts        TEXT,                  -- JSON: [{upstream,model,status,http,ms,error}]
    created_at      TEXT DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_usage_detail_created ON log_usage_detail(created_at);
```

**为什么单独建表**：主表是最热的聚合查询对象（summary / by-model / by-key / by-unit / logs 分页）。把可能数百 KB 的报文塞进主表会拖慢所有聚合查询并放大表体积。拆表后主表保持窄行，详情按需读取。

#### 4.1.3 存储策略（用户已确认）

**分档策略**：

| 请求结果 | 存什么 |
|---|---|
| **成功** | 只存现有结构化字段 + 新增 `cache_read/write_tokens`、`attempt_count`。**不存报文** |
| **失败** | 存完整报文（REQUEST / FORWARDED / RESPONSE）+ 尝试链 |

新增 `sys_setting`：

| 键 | 默认 | 说明 |
|---|---|---|
| `usage_detail_mode` | `error_only` | `off` 不存 / `error_only` 只存失败请求 / `all` 全存 |
| `usage_detail_max_bytes` | `1048576`（1 MB） | 单报文上限。超出保留**头部 3/4 + 尾部 1/4**并标注 `…[truncated N bytes]…` |
| `usage_retention_days` | `14`（沿用现有键，默认值从 30 改为 14） | 主表与详情表**共用同一保留期**，避免两表数据错位 |

**为什么不截断到 8KB**：用户明确要求「直接完整的」。实测长会话请求体约 300 KB（messages 中位数 647、最大 876），1 MB 上限足以容纳绝大多数真实请求，同时为异常超大报文兜底。

**为什么默认 `error_only`**（按生产数据测算）：

| 保留期 | 请求量 | 全存预估 | 仅失败预估 |
|---|---|---|---|
| 7 天 | ~15 400 | ~4.6 GB | ~0.1 GB |
| 14 天 | ~30 800 | ~9.2 GB | ~0.2 GB |
| 30 天 | ~66 000 | ~19.8 GB | ~0.5 GB |

生产实测：日均 ~2 200 请求、失败率 0.6%~5.9%、磁盘可用 80.9 GB。
**全存 30 天虽能扛住（约 20 GB），但每请求多一次 ~300 KB 序列化开销，且备份/迁移/清理变慢。** 成功请求通常不需要逐字分析，有 token/耗时/命中上游就够。

用户可随时在系统设置改成 `all`，界面显示预估体积提示。

#### 4.1.4 定期清理机制（用户新增要求）

- 复用 `UsageBuffer` 已有的**每小时清理线程**（`purge_older_than`）
- 主表 `log_usage` 与详情表 `log_usage_detail` **按同一 `usage_retention_days` 同步清理**，用 `created_at`/`ts` 对齐
- 清理顺序：先删详情（子表），再删主表，避免外键悬挂（当前无外键，仅逻辑一致）
- 设置页可选：7 / 14 / 30 / 90 天，默认 **14**
- 清理动作记日志：`[usage] 清理过期记录 主表 N 条 / 详情 M 条`

> **有了这个机制，「全存」在磁盘上确实没问题。** 但仍默认 `error_only`，理由是写入开销与查询/备份效率，而不是磁盘容量。用户可自行权衡改成 `all`。

#### 4.1.5 已写入的旧数据

- 新增列默认值兼容，无需回填
- 详情表缺行时，详情接口返回 `{available: false, reason: "该请求早于详情功能上线"}`

### 4.2 采集层

#### 4.2.1 断连记录（A 线修复）

`core/logging_setup.py::RequestContextMiddleware`：

- 包装 `receive`，捕获 `http.disconnect`
- 记录 `response_started` 标志
- 在 `await self.app(...)` 的 `finally` 中：若 **未发出 response.start** 且检测到断连 →
  记一条 access 日志，`status=499`（Client Closed Request），并在尾部标注 `disconnected=true`

> 499 是我方约定的语义码，不是真实 HTTP 状态（真实响应从未发出）。

#### 4.2.2 转发报文捕获

`upstream/openai_adapter.py`：

- `try_non_stream` / `try_stream` 已有的 `modified` 副本即"实际转发体"
- 通过 `contextvars` 传给用量采集器（与 `current_api_key_id` 同一套机制）：
  ```python
  current_forward_body: ContextVar[dict | None]
  current_attempts: ContextVar[list | None]
  ```
- 每次候选失败追加一条 attempt（upstream / model / http / 原因 / 耗时）

`services/router_service.py::_UsageTracker`：

- `feed_chunk` / `finish_success_non_stream` 解析 `usage` 时同步取 `cache_read_tokens` / `cache_write_tokens`
- `_log()` 落库时带上 `attempt_count` / `cache_*`
- 新增 `detail` 字段（request_body / forward_body / response_body / attempts），由 `UsageBuffer` 决定是否落 `log_usage_detail`

`core/usage.py::UsageBuffer`：

- `record()` 时按 `usage_detail_mode` 判定是否保留 detail
- `_flush_locked()` 时先插主表拿 `lastrowid`，再插详情表（同一事务）

#### 4.2.3 脱敏

沿用现有 `_redact()`（`sk-xxxx` → `sk-xxxx****`）。详情体额外处理：

- `Authorization` / `x-api-key` 头整体替换为 `<redacted>`
- 请求体里的 `api_key` 字段（若有）替换

## 六、验收标准

**断连（A 线）**

1. 客户端发起请求后立即断开（未到响应阶段）→ 日志出现 `status=499 disconnected=true` 的一条 access 记录
2. 正常请求不产生 499
3. 异常兜底路径仍能记录（不因包装 receive 丢失原有异常语义）

**详情采集**

4. `usage_detail_mode=error_only`（默认）：失败请求有详情行，成功请求无详情行
5. `mode=all`：成功请求也有详情行
6. `mode=off`：两者都没有，且**不影响主表写入**
7. 超过 `max_bytes`（1 MB）的报文按「头 3/4 + 尾 1/4」截断并带标注
8. 报文中的 `sk-` 凭据与 `authorization` 头被脱敏

**清理机制**

9. 保留期设为 7 天：超过 7 天的**主表与详情表记录同步删除**
10. 清理后两表行数一致（无孤儿详情行）
11. 修改保留期后，下一轮清理（≤1 小时）按新值生效

**Token / 重试**

9. 上游返回 `prompt_tokens_details.cached_tokens` 时，`cache_read_tokens` 正确落库
10. 上游返回 `cache_read_input_tokens` 时同样正确（两种命名兼容）
11. 多候选失败重试时 `attempt_count` = 实际尝试数，`attempts` JSON 完整
12. 单次成功时 `attempt_count=1`

**接口 / 前端**

13. `GET /admin/api/usage/logs/{id}` 返回三栏数据；不存在的 id → 404；无详情 → `available=false` 且有原因
14. 列表接口新增字段不破坏现有前端（旧字段全保留）
15. 用量页点击行打开抽屉，三栏正确渲染，复制可用
16. 窄屏（<1280px）下三栏自动改单栏

**回归**

17. CH-019/021/022/023/024/034/036/037 相关脚本全通过
18. `compileall` 0 错误；`npm run build` 通过
19. 现有 `GET /admin/api/usage/*` 出参结构不变（只增不改）

## 七、风险与回退

| 风险 | 影响 | 缓解 |
|---|---|---|
| 详情表体积增长 | 磁盘占用 | 定期清理（默认 14 天，可调 7/14/30/90）+ 1 MB 单条上限 + 默认仅存失败 |
| 捕获报文影响性能 | 请求变慢 | 仅失败请求序列化（默认模式）；`off` 模式零开销；截断在序列化后做 |
| 凭据泄露到日志 | 安全 | 统一 `_redact` + 请求头白名单（只留 user-agent / content-type 等） |
| contextvar 在流式任务间串味 | 数据错配 | contextvar 随请求任务创建，流式生成器在同一 task 内消费；补单测覆盖并发请求 |
| 包装 receive 破坏原有断连语义 | 请求挂起 | 只在检测 `http.disconnect` 时记录，原样透传消息 |
| 大报文渲染卡顿 | 前端卡死 | 抽屉内报文默认折叠，展开时按 8KB 分块渲染 |
| 清理时主表/详情表不同步 | 孤儿详情行 | 同一 `usage_retention_days`、同一清理线程、先删详情再删主表 |

**回退**：`git revert`。新增列与表不影响旧代码（旧代码不 SELECT 新列/表）。

## 九、明确不做

- 不做全链路 trace/span（超出本次范围）
- 不做请求体全文搜索（需要 FTS，另议）
- 不记录响应头（价值低、体积敏感）
- 不解决「TCP 阶段失败」的可见性（物理限制，见第三节）
