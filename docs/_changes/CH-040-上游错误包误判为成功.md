# CH-040 上游「200 + 错误包」误判为成功

> 类型：A 线（bug —— 代码未按设计意图实现）
> 状态：已完成（代码已改，36 项验证 + 回归通过；触发条件已由本机实测确认）
> 日期：2026-10-20
> 来源：用户反馈「DSH 中偶发 `本轮运行失败 buddy: 请求被拦截，请重新发送 Illegal API invocation from an unapproved channel`，但中转站日志里查不到这条失败」

---

## 一、现象

用户在 DSH 中偶发失败：

```
本轮运行失败
buddy: 请求被拦截，请重新发送
Illegal API invocation from an unapproved channel
```

但在中转站用量日志里，同一时刻的请求显示为**成功**，且看不到任何错误信息。

用户补充两个关键观察：

1. **只有 DSH 出现**，用别的工具不出问题 → 怀疑与客户端特征有关
2. **用着用着突然这样**，不是一开始就失败 → 怀疑偶发

---

## 二、定位（铁律 2：先定位再改）

### 2.1 生产取证

利用 CH-038 的详情表（`usage_detail_mode` 已为 `all`），直接查到原始响应体。

`log_id=8661` 的 `response_body`：

```json
data: {"id":"chatcmpl-...","object":"chat.completion.chunk",
"model":"buddy/deepseek-v4.1-flash","choices":[],
"error":{"message":"buddy: 请求被拦截，请重新发送 Illegal API invocation from an unapproved channel",
"type":"server_error","code":"INVALID_REQUEST","status":400}}
data: [DONE]
```

**关键事实：HTTP 状态码是 200，错误写在响应体里，`choices` 是空数组。**

### 2.2 主表记录（误判为成功）

| id | upstream | status | http | prompt | completion | estimated | 耗时 |
|---|---|---|---|---|---|---|---|
| 8661 | buddy | **success** | **200** | 331973 | **0** | **1** | 4541ms |
| 8660 | buddy | success | 200 | 601941 | 4952 | 0 | 84980ms |

`completion=0` + `estimated=1` 就是「一个字都没收到」的特征。

### 2.3 按客户端 UA 分组（验证「只有 DSH」）

| 客户端 UA | 成功 | 失败 |
|---|---|---|
| `deepseek-harness/0.2.0-rc.2`（DSH） | 2 | **1** |
| `hertz` | 12 | 0 |
| `ZCode` | 1 | 0 |

全库带 `unapproved` 的只有 1 条，就是 DSH 那条。**用户观察成立。**

### 2.4 偶发性验证（验证「用着用着突然这样」）

同为 DSH、同一 Key、同一上游：`8660` 成功（84s / 4952 tokens），`8661` 失败。**确属偶发，不是稳定复现。**

### 2.5 补充事实：11 个上游源共用同一个 Key 与同一个 base_url

```
dsh / accio / aggregate / buddy / deepseek-official / jet-hub-auto /
lobsterai / loomy / raccoon / trae / workbuddy
→ 全部指向同一个本机 DSH 插件网关（127.0.0.1:8326），且共用同一把 Key
```

因此「换源」实质是换 model 名打到同一个网关，**不是换物理后端**。

## 三、根因

### 3.1 主因：流式路径只看状态码

`backend/app/upstream/openai_adapter.py`：

```python
if resp.status_code != 200:
    ...各类失败处理（换 Key / 换源）...
# 200 就直接认定成功 ↓
app_config.key_pool.record_success(upstream_id, api_key)
health.record_success(upstream_id, model)
```

号池把业务错误包在 HTTP 200 里返回，于是：

| 后果 | 说明 |
|---|---|
| 记账失真 | 记成 `success`，`prompt_tokens` 用请求文本估算（22 万～33 万），`completion=0` |
| 详情丢失 | CH-038 默认 `error_only` 只存失败请求；被判为 success 后报文体按成功策略丢弃 |
| **不切源** | `try_stream` 返回了 StreamingResponse（非 None），路由层认为命中，直接返回给客户端 |
| 坏 Key 免责 | `record_success` 清零该 Key 的失败计数，轮询下次还选它 |

第 3 条正是用户感知到的「中转站没有自动切换」。

### 3.2 非流式路径同样问题

```python
if resp.status_code == 200:
    return JSONResponse(status_code=200, content=json.loads(raw), ...)
```

只要 200 就返回成功，不检查响应体。

### 3.3 为什么偶发

`pick()` 是轮询（`key_pool.py`）。虽然 11 个源共用同一个 Key 字符串，但号池侧对不同调用会有不同判定（详见第五节），因此同一客户端会在某些时刻被拦截、另一些时刻放行。**这是号池侧策略，我们无法完全消除，但必须正确识别并重试。**

## 四、修复方案

### 4.1 新增两个判定函数（`openai_adapter.py`）

```python
def _extract_wrapped_error(payload) -> str | None:
    """识别「HTTP 200 + 错误包」软失败"""

def _parse_sse_error_line(line: str) -> str | None:
    """从 SSE 单行判断是否为错误包"""
```

判定条件（保守，避免误伤正常响应）：

1. 响应体是 dict 且有 `error`
2. 且 `choices` / `output` / `data` / `content` **全为空**

第二条很重要：个别上游会同时带 `error` 和正常 `choices`（例如部分降级提示），那种情况不算失败。

### 4.2 流式路径（`try_stream`）

在读到 `first_line` 之后、`record_success` **之前**插入判定：

```python
first_error = _parse_sse_error_line(first_line)
if first_error:
    await resp.aclose()
    app_config.key_pool.record_fail(upstream_id, api_key)
    health.record_fail(upstream_id, model)
    rl.on_failure(api_key)
    _note_attempt(..., first_error)
    _capture_response(first_line)
    continue          # 换 Key / 换源
```

**为什么在首包处就能切**：此时响应头虽已由我们接收，但还**没有向客户端发出任何字节**（`generate()` 尚未开始 yield），所以物理上可以安全放弃并重试。

### 4.3 非流式路径（`try_non_stream`）

200 时先解析再判定，命中错误包则同样的失败处理 + `continue`。

### 4.4 不做的事

- **不改** `record_success` 在正常路径的语义
- **不改** 已发出响应头之后的错误处理（物理上无法切源，属于协议限制）
- **不引入** 全局开关（这是纯粹的缺陷修复，不是可选行为）

## 五、真正触发条件（本机实测确认，2026-10-20 补充）

### 5.1 推翻 v1 结论：「号池侧偶发策略」是错的

v1 判定「是号池侧偶发策略，无法定位区分变量」。**实测证明这是一次误判**——不是偶发，是**内容精确匹配**。

### 5.2 对照实验（本机 127.0.0.1:8326 直连网关，模型 `buddy/deepseek-v4.1-flash`）

| system 消息首行 | 结果 |
|---|---|
| `You are a helpful assistant.` | 200 成功 |
| `You are an AI agent powered by DeepSeek Harness.` | **拦截（INVALID_REQUEST）** |
| 前面加**一个空格** | 200 成功 |
| 前面加**一个换行** | 200 成功 |
| 前面加**一句无关的话** | 200 成功 |
| `agent` → `assistant` | 200 成功 |
| `agent, powered`（加逗号） | 200 成功 |
| 结尾 `.` → `?` | **拦截** |
| 无 system 消息 | 200 成功 |

**判定规则**：网关对 `messages` 中**位置 0 的 system 内容**做**精确前缀匹配**，不 trim 前导空白、不容任何字符变化。黑名单里至少含 DSH 这一行；同份分析指出也含 Claude Code（实测 `You are Claude Code, Anthropic's official CLI for Claude.` 同样被拦）。

这解释了为什么按 UA / Key / IP / upstream 分组都看不出规律：**是内容判定，与请求元数据无关**。
也解释了 v1 里「同一客户端一次成功一次失败」——取决于那一轮是否走了注入该开场白的 agent 模式。

### 5.3 为什么 v1 会误判为「偶发」

v1 只用元数据分组（UA / Key / upstream / 状态码），从未检查 `request_body` 的 system 内容。结论错在取样维度，不在推理。

### 5.4 聚合切换能绕过去吗？（这是用户最关心的）

本机实测（流式，贴近 DSH 真实用法）：

| 模型 | DSH 开场白 | 正常 system |
|---|---|---|
| `smart-route/deepseek-v4-1-flash`（聚合，含 buddy/loomy/trae） | **失败**（卡在 buddy） | 成功 |
| `smart-route/trae/deepseek-v4.1-flash`（trae 渠道） | **成功** | 成功 |
| `smart-route/buddy/deepseek-v4.1-flash`（buddy 渠道） | 失败 | 成功 |
| `aggregate/auto` | 失败（错误信息里明确点名 `buddy（minimax-m3.1-flash）上游失败`） | 成功 |

**结论：聚合切换有效，但前提是能切到非黑名单渠道。**

- `trae` 渠道不校验这行开场白 → 切过去就通了
- `buddy` 渠道校验 → 切不出去就还是失败

这也修正了 v1 的一个判断：v1 说「11 个源共用同一网关，所以聚合切换是逻辑隔离、绕不过」。**实际是「按渠道判定」，不是「网关整体判定」，所以聚合切到别家渠道是真实有效的救火手段。**

### 5.5 一处重要差异：状态码在不同链路不一样

| 链路 | DSH 开场白请求的返回 |
|---|---|
| 直连网关**非流式** | HTTP **400** + `{"error":{"code":"INVALID_REQUEST"}}` |
| 网关聚合名**非流式** | HTTP **502** + `{"error":{"code":"PI_AI_ERROR"}}` |
| 直连网关**流式** | HTTP **200** + SSE 里塞 `error`，`choices: []` |
| 网关聚合名**流式** | HTTP **200** + SSE 里塞 `error`，`choices: []` |

**生产库里记录的是第 4 行**（DSH 用流式）。这正好解释了为什么 CH-040 的修复必须落在「首行解析」而不是只看状态码——流式一旦开了 SSE，响应头已经是 200，网关只能把错误写进流里。

## 六、关于「透传 UA」的决策（推翻原计划）

初版方案打算把客户端 `User-Agent` 透传给上游，理由是号池按「channel」判定，而我们只发 `python-httpx/x.x`。

**取证后放弃该方案**，依据：

1. 失败与成功请求**来自同一个客户端**（`deepseek-harness/0.2.0-rc.2`），UA 完全相同 → UA 不是区分变量
2. 真正变量是 **system 首行内容**（见第五节实测），与 UA 无关
3. 强行改写 UA 会让上游看不到真实客户端，反而增加排查难度

因此判定：**我们侧不伪装 UA，也不篡改请求内容**。做的是**正确识别、正确记账、正确重试**。

### 7.1 排查过程中的一个假失败（记录备查）

首轮跑测时 [7][8] 失败，表现为「非流式 `attempt_count=1`」「全失败尝试链为空」，且插桩显示 `current_attempts` 长度异常。真实原因**不是 contextvar 串扰**，而是测试自身副作用：

```
key_pool 状态: {'fails': {'src_bad': {'sk-mock-bad': 3}},
                'cooldown': {'src_bad': {'sk-mock-bad': 119}}}
pick(src_bad) → None
```

测试脚本反复把 `src_bad` 唯一的 Key 打成失败，达到默认 `max_fails=3` 触发 120s 冷却；后续用例在 `pick()` 处直接 `break`，根本没发请求，自然没有 `_note_attempt`。

修复：测试内放宽阈值（`config.key_pool.update_config(max_fails=1000, ...)` 与 `health.update_config(...)`），专测「错误包 → 切候选」本身。**生产行为不受影响**——真实场景下 Key 冷却本就是正确设计。

## 八、验收标准

1. 上游返回 200 + `{"error":...}`（无 choices）时，**不被记为成功**
2. 有后续候选时**自动切换**，客户端无感
3. 全部候选都返回错误包时，客户端收到 503（而不是伪装成 200 的空响应）
4. 错误包请求的详情报文**能被保存**（即使 `usage_detail_mode=error_only`）
5. 正常响应（含同时带 error 和 choices 的）**不被误判**
6. CH-037 / CH-038 / CH-039 回归全通过

## 九、两个层面的处置（职责边界）

| 层面 | 措施 | 状态 |
|---|---|---|
| **中转站（本仓库）** | 识别错误包 → 自动切候选 → 全失败返回 503 → 正确记账与落详情。**不篡改请求内容、不伪装 UA** | 已实现，待部署 |
| **客户端（DSH）** | 关闭那行开场白，从源头规避 | 见 9.1 |

### 9.1 DSH 侧：有官方开关，不必改配置文件字符串

`@deepseek-ai/dsh-system-prompt` 的 `SystemPrompt.Config` 里有现成开关：

```js
static Config = z.object({
    includeHarnessIdentity: z.boolean().default(true),   // ← 这一行控制开场白
    includeRuntimeContext: z.boolean().default(true),
    personaPrefix: z.string().default(""),
    personaSuffix: z.string().default(""),
    ...
});
```

`includeHarnessIdentity ?? true` 为真时才注入 `"You are an AI agent powered by DeepSeek Harness."`。

**因此推荐做法**：在 `~/.dsh/profiles/<profile>/cordis.patch.yml` 给 `systemPrompt` 服务加 `config: { includeHarnessIdentity: false }`，比「在 system-prompt 前加一行」更干净，也不会污染对话内容。

> 该开关未在本仓库验证（属 DSH 侧配置）。若配置不生效，退路是 `personaPrefix: " "`（一个空格），因为实测网关**不 trim 前导空白**。

## 十、遗留

- `unapproved channel` 的触发条件已确认是 **system 首行精确匹配黑名单**（见第五节实测），不再列为未知
- 黑名单完整内容未知（已知含 DSH 与 Claude Code），新增客户端若被拦需重新做一次对照实验
- **`smart-route/deepseek-v4-1-flash` 聚合里 buddy 排在首位**，而 buddy 正是黑名单渠道。若要在中转站侧提升存活率，应把 `trae` 等不校验的成员排到前面，或至少确保聚合内有非黑名单成员
- 11 个上游源共用同一 Key 与同一 `base_url` 的现象仍成立（登记需求规格 9.7），但「绕不过」的推论已修正为「按渠道判定，可跨渠道绕过」
