## 2026-10-28（CH-052 会话亲和：缓存优先路由）

**反馈（用户）**：聚合模型不要每请求换源。上游 prompt cache 按「提供商 + 账号/Key + 前缀」隔离，同一会话来回切会导致缓存全量重算、费用升高。要求：不依赖客户端改动；新会话按负载/权重选一家后**钉住**；只有那家失败才换，换完不切回；不依赖号池；权重与统计保留；短请求不钉；按聚合可单独开关，默认开。
**分类**：B 线-大（路由行为调整 + 新状态层 + 观测字段），走维护迭代迷你 5 阶段，变更文档 `docs/_changes/archived/FB-046-会话亲和缓存优先路由.md`。

### 实现

**会话识别（无客户端改动）**
- 新增 `backend/app/core/affinity.py`：`affinity_key = sha256(model + 请求体 user 字段或第一条 user 消息)[:16]`，不 hash 全量、不存原文；`user` 字段优先；多模态只取 text part。
- 亲和表内存态：`affinity_key -> (upstream, model, key, expires_at, last_seen)`，TTL 45 分钟（请求续期）、LRU 2 万条；另记「近 5 分钟请求数 + 活跃会话数」用于放置。

**路由**
- `services/router_service.py` 新增 `_apply_affinity()`：新会话按 `score =（近 5 分钟请求数 + 活跃会话数）/ weight` 选健康候选（权重语义从「每请求配额」改为「新会话容量比例」），钉住后排候选首位。
- 命中钉子：目标健康且在候选里 → 排首位，`affinity_hit=1`；目标冷却/不在候选 → 重新放置并改钉（`health` / `candidate_missing`）。
- 请求中兜底切换且最终成功 → `_finish_affinity()` 把钉子改到成功那家，`switch_reason=failover`，**不切回**。
- 不钉场景：短请求（估算 < 2000 tokens，`short`）、单候选（`single`）、聚合 `affinity=0` 或全局关闭（`disabled`）、无法识别会话（`no_key`）。
- rule 聚合走同一套钉住逻辑；候选变化时自动重钉。

**Key 钉住**
- `core/key_pool.py`：`pick()` 通过 contextvar 读取会话偏好的 Key，可用则优先复用；不可用/冷却则同源轮询换 Key；成功后把实际使用的 Key 写回亲和表（同源换号后钉子跟随，避免缓存对不上）。

**配置与观测**
- `core/config.py` 新增全局参数：`affinity_enabled`（默认 true）/ `affinity_ttl_seconds`（2700）/ `affinity_min_prompt_tokens`（2000）/ `affinity_max_entries`（20000），可由 `sys_setting` 覆盖。
- `agg_unified` 新增 `affinity`（NULL=跟随全局 / 0=关 / 1=开）；`aggregation_repo` 运行期幂等补列；列表与保存 API 透出/校验（只允许 0/1/null）。
- `log_usage` 新增 `affinity_key` / `affinity_hit` / `switch_reason`；`usage_repo` 既有列白名单 + 运行期补列。非流式落库早于钉子完成，`_UsageTracker` 记 `affinity_target` 并在 `_log` 时按实际命中修正观测字段。

**前端**
- 聚合编辑弹窗新增「会话亲和」三选（跟随全局 / 开启 / 关闭），保存 payload 带 `affinity`；卡片在显式开启/关闭时显示「亲和: 开/关」徽标。

### 验证

- 新增 `test/verify_affinity_ch052.py`：**38 项全过**——指纹稳定性、TTL/LRU/active 计数、1000 新会话 4:2:1 放置（571/286/143）、同会话 100 次同源同 Key、多轮追问钉住、失败换源重钉且不切回、Key 冷却换 Key 且钉子跟随、短请求不写表、`affinity=0` 恢复 4/2/1 轮询（40/20/10）、测试端点不写表、`log_usage` 三字段落库（`new/none/failover/disabled/short` 全覆盖）。

**反馈（用户，截图）**：新接入两个上游源（ID 为「星-国模013」「星-国产模型」），单独在站内测试正常；做成聚合 `test_demo` 后经客户端调用，返回

**定位（只读取证 + 本地复现）**：
- 报错体来自 `main.py` 全局兜底（`中转站内部错误: <异常类型>`），说明异常发生在**本系统进程内**，不是上游返回。

- Starlette 构造 `JSONResponse` / `StreamingResponse` 时按 **latin-1** 编码响应头 → `UnicodeEncodeError: 'latin-1' codec can't encode character '\u661f'`（本地 starlette 1.6.0 复现一致）。

- 影响面：不是聚合特有 —— 任何走 `/v1` 命中这两个中文 ID 上游的请求都会 500。

- 新增 `backend/app/upstream/headers.py`：`ascii_header_value()`（纯 ASCII 原样返回；含非 ASCII 时按 RFC 3986 percent-encode，保留 `/` 便于阅读）与 `ascii_safe_headers()`。

- 三处响应头透传统一兜底：`router_service._wrap_stream_with_usage`、`v1/messages.py`（流式 + 非流式）、`v1/responses.py`（流式 + 非流式）。

## 2026-10-22（CH-049 登录 401 提示纠正 + 改密后令牌失效）

### A 线（bug）：登录失败被误报为「未登录或登录已过期」

**现场**：用户在后台改密码后一直登不上，只看到「未登录或登录已过期」。生产日志显示：

```
22:54:56  PUT /admin/api/admin-password → 401   ← 改密请求被鉴权挡住，密码从未写入
22:55:02~22:57:17  POST /admin/api/login → 401  ← 用户反复试新密码，都失败
```

库中 `admin.updated_at` 仍是 8 天前，证明新密码没落库。

**根因**：`request.ts` 把所有 401 统一处理成「未登录或登录已过期」+ `removeToken()` + 跳登录页。但登录接口的 401 语义是「账号或密码错」，不是会话过期 —— 提示被掩盖，还做了无意义的状态清理。

**修复**：401 分支区分登录接口。登录接口的 401 用后端 `detail`（「用户名或密码错误」），不清 token、不跳转；其它接口行为不变。

### B 线-小（设计调整）：改密后旧 token 不再有效

**改动**：JWT payload 增加密码指纹 `pv = sha256(password)[:16]`。`check_auth` 每次校验时与当前密码的指纹比对，不一致返回 401「密码已变更，请重新登录」。

**为什么用密码指纹而不是随机版本号**：版本号要额外落库（多一个 `sys_setting` 键），改密时忘记递增就失效不了；指纹从密码推导，密码一变必然变。只取 sha256 前 16 位、仅在签名后的 payload 内出现，不额外暴露密码信息。

**顺带**：改密成功后前端主动 `logout()` + 跳登录页，提示「密码已修改，请重新登录」，避免用户点菜单才突然被踢。

### 实施中发现的第二处真问题

首轮把 `check_auth` 写成 `admin_config.get("password", "")`，而 `login` 用的是 `get("password", "smart-router-2026")` —— **两处默认密码不一致**。当 `sys_setting` 里还没有 `admin` 记录时（全新库、回归脚本建的空库），login 用默认值推导 `pv`、check_auth 用空串推导，指纹不等 → **所有管理接口 401**。

回归当场逮到：`verify_filter_engine_ch041` 从「全部通过」变成「10 项失败」。

修法：抽出 `DEFAULT_PASSWORD` 单一常量 + `current_password_version(admin_cfg)` 统一推导，`login` / `change_password` / `check_auth` 全部走它。

## 2026-10-20（CH-040 上游「HTTP 200 + 错误包」误判为成功）

### A 线：DSH 偶发失败，但中转站记成功、也不切源

**现象**：DSH 偶发 `buddy: 请求被拦截，请重新发送 Illegal API invocation from an unapproved channel`，而中转站同一时刻的请求显示**成功**、无任何错误信息，且没有自动切到聚合里的下一个成员。

**定位（先定位再改）**：

1. 生产详情表（`usage_detail_mode=all`）取到 `log_id=8661` 原始响应体：**HTTP 200** + `choices: []` + `error{code:INVALID_REQUEST, status:400}`
2. 主表 `8661`：`status=success` / `http_status=200` / `prompt=331973` / `completion=0` / `estimated=1` —— 「一个字都没收到」却记成功
3. 按 UA 分组：`deepseek-harness/0.2.0-rc.2`（DSH）2 成功 1 失败；`hertz` 12 成功 0 失败 —— 用户「只有 DSH 出现」的观察成立
4. 同客户端同 Key 同源：`8660` 成功（84s / 4952 tokens）、`8661` 失败 —— 确属偶发
5. 11 个上游源共用同一 Key 与同一 `base_url`（本机 DSH 插件网关）→ **推翻「透传 UA」方案**：失败与成功请求 UA 完全相同，UA 不是区分变量

**根因**：`openai_adapter.py` 两条路径都只看 `status_code`，200 即认定成功：

- `try_stream`：拿到 200 直接 `record_success` 并返回 `StreamingResponse`，路由层认为命中 → **不切候选**
- `try_non_stream`：200 直接 `return JSONResponse(...)`

连带后果：记账失真（success + completion=0）、详情按成功策略丢弃（`error_only` 下查不到）、坏 Key 被 `record_success` 免责清零。

**改动**（`backend/app/upstream/openai_adapter.py` + `backend/app/services/router_service.py`）：

- 新增 `_extract_wrapped_error(payload)` / `_parse_sse_error_line(line)`：识别「有 `error` 且 `choices`/`output`/`data`/`content` 全空」的软失败（保守条件，避免误伤同时带 error 与正常 choices 的降级响应）
- `try_stream`：读到 `first_line` 后、`record_success` 之前判定。此时**尚未向客户端发出任何字节**，可安全 `aclose()` 并 `continue` 切下一候选
- `try_non_stream`：200 分支先 `json.loads` 再判定，命中则 `record_fail` + `_note_attempt` + `_capture_response` + `continue`
- `_UsageTracker.stream_error`：覆盖「首行之后才报错」的情况（此时响应头已发给客户端，物理上无法再切源），`finalize_stream` 按 `error` 记账，避免成功率虚高、失败详情进不去

**行为变化**：

| 场景 | 改前 | 改后 |
|---|---|---|
| 200 + 错误包，有后续候选 | 记 success，返回空流给客户端 | **切下一候选**，客户端无感 |
| 200 + 错误包，无后续候选 | 返回 200 空流 | **503**（不再伪装成功） |
